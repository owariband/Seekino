# Motion Showreel

这个 Skill 把想法做成以图形、文字或界面动画为主的视频，交付 MP4 和能重新构建的源码。先想清楚观众看完要带走什么，再决定画面和声音怎么服务这一点。短片该有的动效密度和创作自由都保留；长内容按章节展开，最长 20 分钟。

**原理**：页面暴露确定性的 `render(t)`，脚本逐帧截图，ffmpeg 再把这些帧合成 MP4。画面、口播、配乐与音效读同一份 `timeline.js`。没有口播，画面按内容和音乐节拍组织；有口播，先以真实语音时间为准，再安排音乐与音效。

**默认先预览，再导出**：无论做哪种片子，都先打开剪辑工作区，让用户看到真实画面、听到真实声音。用户点「导出视频」，或在对话里确认预览通过、可以导出，才合成 MP4。第一次说「做一个视频」并不等于预览已经通过；只有用户明确表示免除预览，才可以直接导出。静帧、自查和音频准备可以提前做，但不默认生成代理 MP4 或整片样片。

**按需观看制作过程**：需求问答时留意「边做边看、实时进度、每个阶段看看」这类意愿。用户表达后，提前打开进度页，从需求说明一直展示到风格帧、口播样例、镜头和混音。按 `references/progress.md` 发布已经自查的阶段成果，不把半成品代码直接摊给用户。收到确认后，先运行 `progress.mjs <project> --stage <当前阶段> --confirm --message "已确认，正在……"` 解除等待，再去调研、下载或制作，不要等产物做完才补进度。用户没提这件事，就保持默认的最终工作区预览；制作标准、确认节点和成片验收都不因此改变。

**好片子从哪来**：观感通常由四件事决定：变化密度、运动质感、一个记忆点，以及声音与画面的关系。内容里如果本来就有一个和预期不一样的结果，留到观众看见的那一刻；没有这种落差，也不必硬造。至于具体怎么动、动多少，要看风格和内容，不必每支片子都上多机位、弹簧和满屏音效。全局只有「底线」里那几条不能破，其余都是起点，不是上限。

**视频感**：讲解、产品演示和叙事片里，对象的行为与关系要跟着内容变化，前后镜头要保持空间承接。把口播逐句变成静态标题卡，再补上淡入、缩放和背景粒子，仍然缺少内容的推进。分镜先回答三个问题：观众要看懂什么变化，主体前后各是什么状态，这个镜头怎么接上一个。答案清楚了再挑动效，用画面解释内容；有故事性的片子可以让目标和处境的变化推动镜头顺序。Logo、动态排版、循环和刻意静止各有自己的语法；持续运动或强制使用 60fps 都不等于影片质量更好。具体方法见 `references/craft.md` 的「连续叙事」。

## 适用范围

| 用户想要 | 用这个 Skill？ |
|---|---|
| 产品宣传短片、动效作品集、UI 动效、动态排版 / 卡点、Logo 演绎、片头、循环动图 | ✅ |
| 视频模型生成的绿幕人物 + 代码做的场景、大字、动效 | ✅ 人物素材由用户提供（`references/formats.md` H 类） |
| 用户提供口播稿或录音，要导出有讲解的 MP4 | ✅ 口播驱动模式；TTS 只使用用户提供的原稿 |
| 需要点击推进、现场演讲、交互式网页演示，或文章转口播稿 | 用 `web-video-presentation` |
| 网页、落地页、交互原型、静态视觉稿 | ❌ 用 `web-design-engineer` |
| 写实人物表演、实拍质感、剪辑已有素材、用视频模型直接出画面 | ❌ |

**时长**：最长 20 分钟（1200 秒），以用户确认的时长为准。短片适合 5–60 秒，长片也不必从头到尾维持高密度卡点。超过 2 分钟，按 `references/long-form.md` 分章规划、制作和审片。用户指定的时长与口播实际长度或内容量对不上时，先停下来商量怎么调整，不要自行截断、加速口播或改片长。

## Opus 的长处和默认坑

- **长处**：同一个文件里可以混用 Canvas、SVG/DOM、WebGL、Three.js，也可以按段落换媒介；运动可用公式计算，包括闭式弹簧、节拍网格和子帧运动模糊；声音和画面共用一张时间表；能长时间自主执行「渲静帧 → 看图 → 修改」。原指引认为 Opus 的审美判断力强，并举出「全力以赴」这类提示可能带来出色结果；实际成片仍按后文标准检查。
- **默认坑**：没有约束时，画面容易滑向深色背景、居中大字、所有元素一起淡入、紫蓝渐变加发光、机位一动不动；配乐也容易变成 A 小调四踩、每个重拍 impact + crash、钟声落版，几支片子听下来像同一首。因此要先找对标，画面和声音都要找，再把风格与禁止清单写清楚。约束也别写死：风格库和手法库都是起点，主题需要时可以改、可以混搭，也可以自己定。
- **做不好的**：写实人物，复杂的手部、布料和毛发，需要真实物理精度的东西，以及照片级产品（除非用户提供模型或图片）。碰到这些，要么风格化处理，要么改成绿幕人物加代码场景的分工。

## 工作流

```
0 环境检查（一次）
1 需求确认 ──────── 补齐必填项，汇总要求 → 🛑 等用户确认
2 brief.md ──────── 对标 → 用途 + 风格 → Reel Read → 分镜 + 声音计划
3 风格帧 ────────── 已定风格：3 张帧；未定风格：3 个方向各 1 张 → 🛑 等用户确认
4 制作 ──────────── 有口播先准备真实音频及时间戳 → timeline → 逐镜头 → 网页自查
5 配乐与混音 ────── BGM、音效独立选来源；有口播时人声优先
6 工作区预览 ────── 主动打开剪辑工作区，修改后复看 → 🛑 等用户确认导出
7 导出与验收 ────── 合成 MP4 → 技术检查（必须全过）+ 成片复核
8 交付
```

工作目录：在用户当前目录下新建 `<slug>/`，下面这些文件都放进去：`brief.md`、`index.html`、`motion.js`、`timeline.js`、`score.mjs` 或 `score.tone.js`（按 scaffold 的 `--audio` 选择）、`build.sh`、`fonts/`、`assets/`、`audio/`、`qa/`、`out/`。

### 第 0 步：环境

第一次使用先运行 `sh <skill>/scripts/setup.sh`。它装 Playwright 和 Chromium，然后跑 `check-env.mjs`。环境需要 Node 18+ 和 ffmpeg；缺什么就告诉用户怎么装，不要代装系统软件。工具自带测试：`cd <skill>/scripts && npm test`。

### 第 1 步：需求确认（停下来等用户）

把缺的信息一次问清，用户已经说过的不要再问。下面这些都要明确，不能拿固定默认值替用户做决定：

| 必填信息 | 需要明确什么 |
|---|---|
| 核心主题、制作内容 | 要呈现什么；哪些内容非出现不可 |
| 时长 | 给出秒数或分钟数，说明能否小幅浮动；上限 1200 秒 |
| 横屏或竖屏 | 按选择确定实际尺寸；用户明确要 1:1 等画幅时照办。分辨率与帧率可以提建议，并写进确认摘要 |
| BGM 来源 | AI 合成、用户提供，或明确关闭 |
| 音效来源 | AI 合成、用户提供，或明确关闭；与 BGM 分开选择 |
| 口播方式 | 无口播 / AI TTS / 用户提供录音 |

**条件必填**：选 TTS，用户必须提供口播稿。不要代写、补写，也不要改写后再合成。TTS 服务和所需 API 配置也要定下来：已有配置可以复用，凭据走环境变量，不写进 brief。支持 Gemini、MiniMax 和自定义适配器，按需读 `references/narration.md`。选用户录音，要有录音文件或可访问地址；选用户 BGM 或音效，也要有对应文件。口播语言、音色等能从稿件或配置看出来的，写进摘要；看不出来的，一并问。

**可选信息**：相关资料、受众与发布平台、主题风格。受众和平台没给，就按内容推断，并在摘要里说明。风格没给，留到风格帧阶段给三个方向。

**制作进度偏好**：从用户已有反馈里判断他想不想看过程。明确说了就记下来并启用，不为此反复确认，也不加必答题。启用后读 `references/progress.md`，尽早启动 `editor.mjs <slug> --progress` 并主动打开；这时目录里可以还没有动画或音频。需求摘要里写明会逐阶段展示，后面的需求确认和风格确认照旧。

**素材怎么处理**：用户给了具体内容，也授权 AI 生成，就按这些内容做。内容不够，先问必需的资料；也可以围绕主题上网调研，但保留来源。有口播稿，先从原稿里取信息，别再让用户填一遍。插画、场景、抽象图形和明确标注的示意内容可以由 AI 生成；真实产品功能、数字和品牌素材仍按「底线」处理，虚构资料不能冒充真实内容。品牌 Logo 和真实产品截图的要求见 `references/stack.md`。

- 用户给了参考视频：先跑 `inspect.mjs sheet <ref> --cells 30` 看全貌，再用 `inspect.mjs grid <ref> --strips` 量剪点，看它们落在哪个节拍网格上（BPM 候选、每段占几步、每个转场的连续帧），最后用 `inspect.mjs heat <ref>` 看每段里哪里在动、动了多大面积。量到的数字写进 brief 的对标一栏。只学结构和手法，不搬素材。
- 用户给了曲子：没有口播，先跑 `audio.mjs beats <track> --out <slug>/audio/beats.json`；有口播，音乐拍点跟着讲述节奏走。
- 画面里出现的产品、品牌或技术名词，拿不准就先查证。

补齐后，把主题、时长、画幅、BGM 与音效各自的来源、口播方式和素材情况汇总成摘要，**停下来等用户确认，再写 brief**。第一次请求就把信息给全了，也要先发摘要确认。「全力以赴」「给我惊喜」「你看着办」只授权创意选择，不等于可以省掉必填信息或跳过确认。只有用户明确要求跳过某次确认，才继续，并记下这个授权。

**放手模式**：创意交给 AI，底线和技术管线照守，风格、结构、手法自己定，也可以完全不用风格库。brief 仍要写，三个方向仍要给，需求确认和风格确认仍要做。制作完成后一样先在工作区预览，确认后再导出；用户明确免除的确认除外。

### 第 2 步：brief.md

brief 先回答一个问题：观众看完要带走什么。答案定了，后面的对标、结构、风格和分镜都围着它转。

**先找对标**：动笔前，为这支片子挑 1–2 个对标作品——主题和用途要对得上，电影片头、广告、游戏、动效作品、设计流派都行。brief 里写清「学什么」（构图、节奏、镜头语法、配色逻辑、配乐结构）和「不学什么」（角色、具体镜头、旋律、logo、字体文件）。想把上限拉高，找对标比套规则更管用。

**再想三个候选结构**：一段旅程、一次前后对比、一次倒数、一个变成另一个、一个不切镜头的长镜头，都可以是起点。每个用两三行写清楚，选一个并说明理由。第一个冒出来的想法，常常正是这个风格里最俗的那一个。

**用途**和**风格**分开选：
- 用途决定拍什么、按什么结构讲。看 `references/formats.md`，只读对应的那一节。
- 风格决定长什么样、怎么动、什么声音。先看 `references/styles/INDEX.md`，再**只读选中的 1–2 个风格文件**。可以直接用，可以改造（换掉其中一两条规则），可以混搭（一主一辅，或按段落切媒介），也可以照 `styles/_template.md` 自定义。改造之后，风格规则仍要成立；故事、镜头和结构要来自用户的主题，不要搬别的片子。每个风格文件都有「辨识信号」和「最俗的版本」两节：按主题挑 2–3 个信号，至少有一个不在俗套里，并在 brief 里写明翻掉了哪几条俗套，或者为什么保留。用户选了风格，就是要一眼认出来，两三个信号足够。
- 需要时再翻 `references/craft.md`（手法库）。

按 `references/brief-template.md` 写 brief，核心字段如下：

```yaml
Reel Read:
  format: [用途，formats.md 里的类型]
  benchmark: [对标作品 · 学什么 · 不学什么]
  structure: [三个候选结构 → 选中哪个、为什么]
  style: [styles/ 里的风格（含改造点），或者混搭方案，或者自定义规则]
  signals: [挑了哪 2–3 个辨识信号、为什么；翻掉了俗套的哪几条]
  takeaway: [观众记住的一句话或一个画面]
  hook: [前 1 秒发生什么]
  signature: [记忆点：第几秒、什么手法]
  palette / type / motion / camera / texture: [按所选风格写出具体值]
  sound: [无声 / 合成（声音对标、律动、和声、配器、曲线，见 sound.md 第 2 节）/ 用户曲子（BPM、drop）]
  audio-sources: [BGM 与音效各自为 AI / 用户 / 关闭]
  narration: [无 / 用户原稿 TTS / 用户录音；有口播时句段时间轴路径、人声优先]
  forbidden: [这支片子的禁止清单]
```

然后写分镜表。没有口播，**节拍网格和分镜表**都要有；有口播，把句段挂到镜头和事件上，逐项写明 `镜头 / 句段 ID | 要解释的变化 | 对象起止状态 | 继承的对象与空间 | 关键事件及时间依据 | 镜头与声音`。一个镜头可以覆盖几句话，一句话也可以包含多个动作。口播分句不是切镜指令，原稿也不必逐句铺满屏幕。实际区间等音频准备好再回填，按字数估算的时间不能当作最终对齐依据。长片另写章节表、各章时长和跨章一致性规则。

用户只说「全力以赴」，也要把它翻译成上面这些具体约束；否则做出来就是碰运气。

### 第 3 步：风格帧（第二次停下来等用户）

建项目：`sh <skill>/scripts/scaffold.sh <slug> [--audio synth|tone|layer|file|none]`。synth 指第 1 档合成，只会拷贝选中的那份 score；`file` 则使用已经准备好的最终音轨。脚手架的引擎默认值只负责技术初始化，不能替代需求确认。starter 只用来确认管线跑得通，画面和文案都要换。

**A. 用户已经定了风格**（或者给了明确的参考）：
下面命令里的秒数只是示例，实际要取本片开场、记忆点和结尾的有效时间；短片长片都一样，别照抄 14.5 秒。
1. 用真代码搭出 hook 帧、记忆点帧和结尾帧，配色、字体、文案都按最终版来。
2. 跑 `render.mjs <slug> --still 0.6,7.2,14.5 --sheet`，自己先看一遍，明显的问题修掉再给用户。如果方向依赖连续运动，按本节要求在剪辑工作区里展示连续片段，不要先编码成 MP4。
3. 把 Reel Read 摘要、分镜概要和风格帧发给用户，问一句「方向对吗？」。

**B. 用户没定风格（包括放手模式）**：给 **3 个拉开差距的方向**，规则见 `styles/INDEX.md`：
- A 贴合主题或品牌；B 换一种画面语言，取自另一个分组；C 大胆一些，用自定义、混搭或结构上的冒险，至少有一个方向不是库里现成的。
- 每个方向写一段迷你 Reel Read（风格、对标、记忆点、配乐方向，3–5 行），再用真代码渲**一张**最能代表它的关键帧。三个方向的页面放在同一个项目里，用 `?dir=a|b|c` 切换。B、C 只服务这一张关键帧，不必做成能播的整片。
- 跑 `render.mjs <slug> --directions a,b,c --at 14.5,2,0`，三张一次渲出，拼成带标签的 `qa/directions.png` 发给用户，问「选哪个，或者怎么混合？」。

两种情况都**要真的等用户回复**，再进入制作。TTS 项目还要附上用户原稿的分段方案和音色短样（只使用用户给的文字），把声音方向一起确认，不再额外加一个必停节点。用户事先明确说过不用确认的，就自己选一个，写明理由，自查后继续；交付时把没选的方向也给用户（B 情况附上 `qa/directions.png`，A 情况各写一句另外两个可能的方向），用户回头想换，也还有别的选择。

如果方向依赖连续动作，除了静帧，还要在工作区里放一段 6–10 秒的代表性运动（短于 6 秒的片子就放全片），用播放头和循环试听选区定位，覆盖一次状态变化以及前后的承接；自己先看连续帧，排除跳变。片段和风格帧一起确认，不用提前导出样片。口播还没生成时，明确标成动作预演，不能说已经和语音精确对齐。风格确认管方向，最终预览确认管成片内容，两件事分开。

### 第 4 步：制作

制作前读 `references/stack.md`，页面契约、确定性和各技术的坑都在里面。想要现成写法，查 `references/recipes.md`。

**有口播时先锁定口播时间轴**：按 `references/narration.md` 合成用户原稿，或导入用户录音，拿到真实时长和句段时间戳，再安排画面。用户录音要用可用的转录工具，或用户提供的 SRT/JSON，取得文本与时间；没有可靠时间戳，就不能说逐句已经对齐。发现时长冲突，先和用户确认，不要悄悄填充、裁切或变速。真实区间要导进镜头表，口播的停顿和重点保留，别硬对齐音乐小节。超过 2 分钟，按 `references/long-form.md` 分章制作，保留章节缓存。

句段只给出同步范围，镜头和主体运动可以跨句连续。某个关键变化需要词级同步时，用真实词时间或人工标注的锚点，通过 `narration.js` 查询，让画面和音效引用同一个事件；只有句级时间，就保持句级同步，不要编出逐字时点。制作过程中默认用 `editor.mjs` 带声音预览、拖动和逐帧检查；`preview.mjs` 留作轻量调试工具。预览驱动的仍是同一个 `render(t)`，不进入正式渲染。

1. 所有时间点写进 `timeline.js`，页面和 `score.mjs` 都从这里 import。镜头表放进 `SHOTS`，验收时按镜头报运动；刻意的停留放进 `HOLDS`，比如落版写 `[[b(36), DUR]]`；需要留呼吸的重拍放进 `DROPS`。验收工具会读这三处。转场要对拍，就用 `revealOn(拍点, 转场时长, 揭开点)` 倒推起点，让新画面露出来的那一帧正好落在拍上。
2. 一个镜头一个镜头做。用户要看过程，就在每镜自查通过后发布该镜头的独立可播放成果（`progress.mjs --stage scenes --shot <id> --total <镜头总数> --publish <该镜预览目录>`），然后才做下一镜。不要等所有镜头写完再一次补成 3/3，也不要等全片素材齐了才给第一个预览。每个镜头渲开头、中段、结尾 3 张静帧；关键状态变化和镜头接缝另看连续小样，检查主体有没有凭空重置、动作速度有没有突变、镜头有没有断。静帧好看代替不了运动检查，快速动作可以用 `inspect.mjs strip` 看连续帧。
3. 跑 `render.mjs <slug> --determinism` 做确定性检查，不过就先修。
4. 用网页预览检查节奏和连续动作，默认不渲低清代理或 MP4 小样；静帧和确定性检查照常做。确实需要离线片段，先说明原因，用户同意后只渲必要的范围。
5. 按 brief 配好 `FPS`、`SIZE`、`AUDIO`、`LOOP`，做完下面的声音准备，再进第 6 步。这时先不跑 `build.sh`、视频模式的 `render.mjs` 或 `build-long.mjs`。

**硬规则**：
- 画面只由 t 决定：不用 `Math.random`、`Date.now`、rAF、定时器或 CSS 动画，帧与帧之间不保存状态。
- 字体和素材都加载完，再设 `READY = true`；字体放在项目里自托管。
- 布局从 `stageSize()` 返回的宽高推导，不写死像素。

用了子帧运动模糊、又有文案硬切时，可以按 `references/stack.md` 的可选采样上下文，把文案状态和连续运动区分开；导出后检查切换点的连续帧，避免子帧平均让某一帧出现文字叠印。

启用制作进度后，风格帧和口播短样在自查后发布成图片或音频成果；镜头和混音到了可播放的阶段，用 `progress.mjs --publish` 发一份稳定副本。开工前把状态更新为 `running`，完成后把成果挂到对应阶段：需求或脚本发 Markdown，风格帧发图片，声音发音频，镜头发可播放版本。等用户选择时用 `waiting`；没完成的部分写清楚，镜头数量按成功发布的算。阶段预览不增加确认节点，也不触发 MP4 合成。最终短片用 `review --final` 在同一进度页进入可调音、可导出的工作区；长片还是逐章展示，全片确认后按原流程构建。

### 第 5 步：BGM、音效与混音

先看 `references/sound.md`。BGM 和音效各按确认的来源做，用户配乐加 AI 音效这类组合也可以。下表是 AI 合成时选引擎的依据，引擎默认值不能盖过已经确认的素材来源。声音方向（对标、律动、和声、配器、曲线）在 brief 阶段就定下来：

| 档 | 用什么 | 适合 |
|---|---|---|
| 第 1 档 · 内置合成 | `score.mjs`，Node 里的合成器（鼓、手鼓、贝斯、铺底、拨弦、马林巴 / 钢片 / 卡林巴、风琴、人声铺底、FM、环境底噪、音效、侧链、混响、lo-fi 处理），零依赖 | 电子、UI、芯片音乐、氛围、lo-fi、手作与玩具、大多数动效片 |
| 第 2 档 · Tone.js | `score.tone.js`，在无头浏览器里用 Tone.js 离线渲染：采样乐器（`audio.mjs samples salamander` 下载 CC BY 钢琴）、卷积混响、更丰富的合成器和效果 | 需要真实乐器、空间感、电影感的风格 |
| 外部曲子 | 用户自己的、已授权的或 AI 音乐服务生成的曲子 | 用户已有配乐 |

- 构建：跑 `audio.mjs build <slug>/score.mjs` 或 `score.tone.js`，输出统一的 −14 LUFS `audio/music.wav`。
- 用户曲子：没有口播，先跑 `audio.mjs beats`（装了 librosa 会自动使用）把 timeline 对齐，再在 score 里用 `S.load()` 叠音效。有口播，音乐节拍只作参考，调整音乐和音效去配合语音，已经确认的口播时间轴不动。
- 无声：BGM、音效和口播都关了才跳过；只关 BGM 不等于整片无声。
- 有口播：音乐少用主旋律、密集打击和大动态；音效只留有信息作用的动作，避开关键词和句首。音轨保持独立，通过 `narration.mjs mix` 处理人声期间的避让、统一响度和峰值。画面用真实句段时间戳核对，听感仍要用户终审。

每次 build 完，都要对最终混音跑 `audio.mjs check`，看数值也看图；宿主能试听就再听一遍。数值通过不能写成「听感已确认」。`timeline.js` 里写了 `DROPS`，它还会量重拍前的凹陷和抬升，没有呼吸就报 WARN。

### 第 6 步：工作区预览（默认入口，等用户确认导出）

每次制作都读 `references/editor.md`。短片如果启用了制作进度，就在同一个进度页用 `review --final` 发布最终工作区，规格和导出质量参数沿用已确认的那套，不用另开入口；其余情况运行 `node <skill>/scripts/editor.mjs <slug> --size <本片尺寸> --fps <本片帧率>`，并主动打开打印出来的网址。宿主打不开浏览器，就给一个能访问的本机链接，等用户的预览反馈。无声片、无口播片、短片、循环片同样走这一步，不用等用户再说「打开工作区」。长片按 `long-form.md` 逐章打开工作区；第一版不假装有跨页面的整片时间线。

交付预览前，先自己查画面、音轨、时长和报错，再让用户播放、拖动和调音。没编辑过就直接用原混音；动过音轨要更新试听，确认当前混音已经加载。用户提修改，改完刷新、复看；上一版通过了，也不代表修改版可以自动导出。只有用户点了「导出视频」，或明确说当前预览通过、可以导出，才进下一步。这两种都算导出确认，不必再问一遍。

预览链接、用户反馈、确认导出的版本和音轨编辑记录，都写进 `brief.md` 或 `qa/review_log.md`。服务或浏览器不可用，就说明卡在哪，并给出网页预览的替代方案，不要擅自改成先生成 MP4。子帧混合、DPR 超采样和 ffmpeg 颗粒属于导出设置，要告诉用户哪些效果预览里还没有模拟，不要悄悄降低成片质量。用户明确要求不预览、直接导出，就记下这个指示，下面的技术验收一项不少。

### 第 7 步：导出与验收

预览通过后，单页面的片子优先在工作区点「导出视频」，由现有渲染器和验收工具输出编辑版 MP4。工作区里的音频修改不会自动写回 `build.sh`；有编辑时，导出必须使用已经试听过的当前会话，不能绕回原混音。没动过工作区音频，也可以在用户确认后运行 `sh <slug>/build.sh`，它会构建配乐、检查确定性、渲染、生成文字审片材料，并按同一套规格验收。混合音轨仍用 `AUDIO=file AUDIO_FILE=audio/final.wav sh build.sh`；旧的 synth/tone/layer/none 方式也保留。长片确认后，用 `build-long.mjs` 持久分章构建，见 `references/long-form.md`。

`--subframes`、`--dpr`、`--grain` 按 brief 传入，工作区导出和手动构建用同一组已确认规格。这些参数会拉长渲染时间，开渲前先报告预计耗时。循环片验收再加 `--loop`。预览确认不能替代导出后的技术检查和成片复核。

**技术检查**：由程序判定，失败就不能交付。

```bash
node <skill>/scripts/inspect.mjs qa <slug>/out/final.mp4 --out <slug>/qa/final \
  --expect-size 1920x1080 --expect-fps 30 --expect-duration 16 --audio required   # 无声片用 --audio none；循环片加 --loop
```

它检查文件能不能解码，以及尺寸、帧率、时长、帧数、音轨、黑帧、响度、真峰值和循环接缝（需要时）。只要有一项 FAIL，退出码就是 1，修好才能继续。没传的规格项会列成 `NOT CHECKED`，那就不算验收通过。`build.sh` 会自动带上规格，渲染工具本身也会拒绝发布帧数不对的文件。

**审片**：这一步靠人判断，不是程序判定。看抽帧图、手机尺寸抽帧图、冻结段（`HOLDS` 里声明过的是刻意停留，没声明的要想清楚是不是空拍）、切点、按镜头的运动和闪帧、文字框景标记图（`qa/text-*.png`）以及音频图；按 `references/review.md` 的审片表逐项写下观察，并列出最严重的 3 个问题。片子里有数字和图表，要核对内容与口径。修完只重渲有问题的段落，再出整片，过程记进 `qa/review_log.md`。宿主支持子 agent，就再找一个没参与制作的 agent，只看这些材料挑问题（review.md「独立审片」）。

有口播，再跑一次 `narration.mjs check`，核对句段时间覆盖、音频长度和确认过的规格；原稿、画面、语音是否一致要逐句看，自动检查替代不了听感审片。长片逐章审，并检查拼接处的画面、声音和时间轴。

审片结论只是给用户的参考，**不能代替用户自己看片**。不适用的项标「不适用」，比如无声作品里的音画同步，不要勉强打分。

### 第 8 步：交付

交付时告诉用户：
- 成片在哪：工作区导出的是 `out/editor-<task-id>.mp4`，原构建是 `out/final.mp4`；封面 `out/poster.png` 一并给出（poster：`render.mjs <slug> --poster <t>`）。
- `brief.md` 里有什么：完整的结构化提示词、需求与风格确认、最终预览和导出确认记录都在，可以直接复用，不包含 API 凭据。
- 有口播，附用户原稿、句段时间轴和各轨来源；长片附章节 manifest 和断点重建命令。
- 技术检查结果（全部 PASS）、审片记录里还没解决的问题、渲染用时。
- 怎么重新打开工作区，怎么重建当前编辑版（见 editor.md）；原构建仍可 `sh build.sh`，只想改一段时怎么做。
- 第三方素材（字体、用户素材、曲子）的来源和授权；事实类内容提醒用户再核对一遍。

复盘结论和复核证据存在项目的 `qa/review_log.md` 里，跟这次制作的文件一起交付。

## 底线（所有风格都要守）

1. **需求与原稿**：必填信息都确认过；视频不超过 20 分钟；TTS 原稿必须来自用户。时长有冲突先确认，不擅自改稿、截断或变速。
2. **事实准确**：产品功能、数字和名称只取自用户或可靠来源，拿不准就标出来。
3. **文字可读**：字号在手机尺寸下看得清，停留时间够读完（见 craft.md 第 7 节）；不溢出、不重叠、不被遮挡。
4. **素材有授权**：logo、截图、字体、曲子都要有使用权，交付时逐项列出。
5. **技术正确**：确定性渲染，技术检查全过，没有黑帧，结尾不能戛然而止，要用落版定格或无缝循环收住。
6. **风格一致**：选定的风格规则从头守到尾，brief 禁止清单里的东西一个不碰。

除此之外，镜头动多少、用不用弹簧、音效多密、节奏多快，都由风格和内容决定（见 references/styles/ 和 craft.md）。
