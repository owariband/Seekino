## 这条检索路径与框图方案的区别

本轮实际是：参考图 → VLM 生成构图文字查询 → 文字 embedding 检索语义/视觉索引 → 对召回视频片段取帧核验 → 返回视频卡。

`agent/chat/video_search/tools/retrieval.py` 的 `retrieve` 接受 `query: str` 和通道权重，不接受参考图片。`server/service/video_retrieval.py` 使用 `embed_query(request.text)`；因此即使 visual 权重为 1，也不代表参考图直接 embedding 后搜图。这次 7 个查询均启用了 visual 通道。

旧实验则把框画到统一画布，通过冻结 DINOv2 Small 编码，计算余弦，再与 PCP 的类别分布余弦加权。两者表达与核验方式不同，不能直接比较分数。

## 对照结果及边界

旧实验本例固定使用 PCP 80%＋框图 20%，候选池为 17 张选图中检出人物的 13 张，排除查询自身后是 12 张；A/B 使用同一池。冻结排名见 [baseline.json](baseline.json)。

| 旧实验 | Top 1 | Top 2 | Top 3 |
|---|---|---|---|
| PCP＋全部框 | 粉发正面近景 | 窗边近景 | 舞台人物靠左 |
| PCP＋人物框 | 舞台人物靠左 | 窗边近景 | 粉发正面近景 |

这三张都没有复现参考图的“大俯拍室内空间＋小人物靠边”。本轮 Chat 找到的第一候选更符合这个具体需求。但 Chat 检索的是 13 集全库，旧实验只有 17 张选图，且没有这两个新候选；这不是同库准确率或模型能力排名。

本例支持的判断是：现有 Chat 可以借助构图描述和候选看图，找到有明确空间关系相似性的片段。人物框仍有检验位置、大小和群体排列的价值。后续若做公平对照，应将相同候选帧交给两种方法，并将“构图类别”“人物位置/占比”“人数/排列”分开评议。只有本例不能确定哪种方法整体更好或是否漏检。

## 文件与复现

- `run.py`：本轮一次性请求入口，已有 `run-01` 时拒绝再次运行，避免误触发重复 Chat。
- `run-01/`：请求记录、SSE、完整助手消息、原文、配置预检快照、本会话日志与统计。
- `evidence/`：22 份取帧清单和相关原图；收集时核验每张图的 SHA。
- `baseline.json`：旧实验两组固定 Top 3，不重跑模型。
- `collect.py`：仅整理已完成会话的本地记录，不再请求 Chat。
- `comparison.json`：页面数据，Chat 原文与实验目视评议分开保存。
- `render.py` / `report.html`：离线页面，图片可放大，无远程资源依赖。

重新整理与渲染（在项目根目录）：

```bash
python3 engine/experiment/composition-models/20261017-chat-composition/collect.py
python3 engine/experiment/composition-models/20261017-chat-composition/render.py
```

本轮文件均维护在 `engine/experiment`，外加上层实验索引一行。当前项目忽略 `**/experiment/`，因此这些实验记录保存在本地，未提交 Git。
