# 文档入口与维护职责

**模块、需求、任务的当前状态，看 [项目看板](dev/kanban.html)；问题的完整分析看 [problems.md](dev/problems.md)；为什么修改、如何验证、收益与代价是什么，看 [devlog.md](dev/devlog.md)。** 看板是可离线打开的单个 HTML，下载或在本地浏览器打开即可使用。

## 文档分工

## devlog 的固定结构

每条记录只包含以下四个部分，选择理由、成本、收益、证据与未验证项归入其中：

1. **问题与现状**：现有设计、遇到的问题、产品影响及修改前基线。
2. **方案候选**：实际考虑过的方案、适用边界、收益与代价，以及最终选择原因。
3. **方案验证**：业务 case、实验方法、控制变量、验收标准、证据及验证范围。
4. **指标对比**：根据本次修改的业务功能灵活选择指标，对比业务闭环结果，同时记录架构复杂度、维护成本和认知成本的变化。

具体要求以 [devlog 开头的维护原则](dev/devlog.md) 为准。区分实测、预估与未验证；不能量化的成本作具体定性说明，不能把局部技术指标改善直接当作整体业务收益。

## 问题状态与验证结论

- **TODO / PROGRESSING / DONE 是卡片的当前执行状态，只在看板维护。** 是否完成按该卡片明确约定的范围与验收条件判断；模块 DONE 只表示标题和详情限定的能力基线完成。写了 devlog、代码已合入或单测通过，本身不等于整个需求完成。
- **“本次验证通过 / 失败 / 未验证”是实验或验收的历史事实，保留在 devlog。** 它们不承担问题状态标记，也不应因后来问题完成而被改写成成功。
- 代码修复、服务加载、真实环境验证和业务效果分别说明。尚未推进的工作为 TODO，正在实施或验收的工作为 PROGRESSING；阻塞、搁置、待核对使用标签和下一步说明。独立的后续工作另建关联卡片，不能用主体修复推定其也已完成。
- 历史 problems、TRD、报告和 devlog 中的“待实施”“已完成”等按当时日期、版本和环境阅读；当前状态以看板及所链接的最新证据为准。发现冲突时补充依据，不在多个文档中同步维护一套任务状态。

## 看板的维护与保存

- **用户维护：** 打开 `dev/kanban.html`，按分类、类型或文字筛选，点击卡片查看/编辑，拖动或在详情选择状态。修改先暂存在浏览器；点击「保存 HTML」写入文件，或下载完整 HTML 后替换仓库中的文件。浏览器草稿和下载目录中的副本不是新的权威来源；协作提交仍以分支中的 `dev/kanban.html` 为准。
- **Agent 维护：** 解析 HTML 中 `<script id="kanban-data" type="application/json">` 的 JSON，只修改相关卡片并写回该节点；沿用稳定 ID，保留历史来源和其他工作。数据中 `revision` 每次修改递增，`updatedAt` 和卡片日期使用 Asia/Shanghai；只有重新采集资料时才更新 `sourceCheckedAt`，不能把编辑日期当成验证日期。序列化时将 `<` 写为 `\u003c`，避免内容截断 script 节点。
- **结构校验：** 类型只用 `module / requirement / task`，状态只用 `todo / progressing / done`；ID 唯一，分类存在，关联 ID 存在且不指向自身，资料链接使用 http(s)。新增可形成 TRD 的需求继续遵循独立分支、PR 和 TRD 首提交要求；历史模块无需补造旧 PR/TRD。
- **协作更新：** 先读取分支中的最新文件，再按 ID 合并本次变更；避免拿旧下载副本整体覆盖别人新增的卡片。导出 JSON 用于交换或检查，不另建长期维护的 JSON 主文件。离线页面不会自动同步 PR；刷新来源时保留采集日期、PR 关闭/合并事实与业务验收的区别。

## 一次修改如何更新文档

1. 在看板找到或建立卡片，明确类型、分类、业务影响、范围与验收条件；详细问题分析在 problems 中按同一编号保存。
2. 涉及设计或接口变化时更新对应 TRD；实验输入、脚本和原始输出保留在相应证据目录。
3. 将决策、验证结果和整体指标写入统一 devlog，注明原问题编号并链接来源；没有测量的数据明确写未测。
4. 根据实际验收结果更新看板状态、下一步、验证边界及 PR/TRD/devlog 链接，保存完整 HTML。后续实验在原证据位置追加有日期的记录，保留原失败结果和适用边界；不再移动 problems 的历史条目来表达当前状态。

已有历史问题正文、TRD 和实验退役摘要保留为追溯依据；后续新增内容按以上职责维护，避免复制整段材料后形成多个独立更新的副本。
