# 文档入口与维护职责

**当前问题是否完成，看 [problems.md](dev/problems.md)；为什么修改、如何验证、收益与代价是什么，看 [devlog.md](dev/devlog.md)。**

## 文档分工

## devlog 的固定结构

每条记录只包含以下四个部分，选择理由、成本、收益、证据与未验证项归入其中：

1. **问题与现状**：现有设计、遇到的问题、产品影响及修改前基线。
2. **方案候选**：实际考虑过的方案、适用边界、收益与代价，以及最终选择原因。
3. **方案验证**：业务 case、实验方法、控制变量、验收标准、证据及验证范围。
4. **指标对比**：根据本次修改的业务功能灵活选择指标，对比业务闭环结果，同时记录架构复杂度、维护成本和认知成本的变化。

具体要求以 [devlog 开头的维护原则](dev/devlog.md) 为准。区分实测、预估与未验证；不能量化的成本作具体定性说明，不能把局部技术指标改善直接当作整体业务收益。

## 问题状态与验证结论

- **TODO / 已解决（DONE）是问题的当前执行状态，只在 problems 维护。** 是否完成按该问题明确约定的主体范围与验收条件判断，保留主体修复或疑问澄清与后续验证的区别；写了 devlog、代码已合入或单测通过，本身不等于问题完成。
- **“本次验证通过 / 失败 / 未验证”是实验或验收的历史事实，保留在 devlog。** 它们不承担问题状态标记，也不应因后来问题完成而被改写成成功。
- 代码修复、服务加载、真实环境验证和业务效果分别说明。仍属于该问题验收范围的缺口留在 TODO；独立的后续工作另列关联 TODO，不能用主体修复推定其也已完成。
- 历史 TRD、报告和 devlog 中的“待实施”“已完成”等按当时日期、版本和环境阅读；当前状态以 problems 的最新证据与验收记录为准。发现冲突时补充依据，不在多个文档中同步维护一套任务状态。

## 一次修改如何更新文档

1. 在 problems 找到或建立问题编号，明确业务影响、修改范围与验收条件。
2. 涉及设计或接口变化时更新对应 TRD；实验输入、脚本和原始输出保留在相应证据目录。
3. 将决策、验证结果和整体指标写入统一 devlog，注明原问题编号并链接来源；没有测量的数据明确写未测。
4. 根据实际验收结果更新 problems 的 TODO / 已解决状态、进展日期与 devlog 链接。后续实验追加有日期的记录，保留原失败结果和适用边界。

已有历史问题正文、TRD 和实验退役摘要保留为追溯依据；后续新增内容按以上职责维护，避免复制整段材料后形成多个独立更新的副本。
