# 文档入口与维护职责

**模块、需求、任务、里程碑与验收门槛的当前状态，看 [管理工作台](dev/workbench.html)；问题的完整分析看 [problems.md](dev/problems.md)；为什么修改、如何验证、收益与代价是什么，看 [devlog.md](dev/devlog.md)。** 工作台是项目统一维护的单个 HTML，包含概览（里程碑、闭环地图、紧急事项）、看板与验收门槛三个视图，在本地浏览器打开即可查看；内容由 Agent 随项目工作更新到仓库。

## devlog 的固定结构

每条记录只包含以下四个部分，选择理由、成本、收益、证据与未验证项归入其中：

1. **问题与现状**：业务问题与影响范围、现有设计、修改前基线，以及原因假设和排查证据。
2. **方案候选**：实际考虑过的方案、适用边界、收益与代价，以及最终选择原因。
3. **方案验证**：业务 case、实验方法、控制变量、验收标准、证据及验证范围。
4. **指标对比**：先说明影响范围和选取指标的理由，再对比用时、token、业务正确性及相关成本，最后说明收益、代价和是否采用。

标题描述问题的技术原因及其业务影响，正文用自然中文讲清我们的排查和取舍，不用“用户指出”代替问题描述。具体要求以 [devlog 开头的维护原则](dev/devlog.md#维护原则) 为准。区分实测、预估与未验证；不能量化的成本作具体定性说明，不能把局部技术指标改善直接当作整体业务收益。

## 问题状态与验证结论

- **TODO / PROGRESSING / VERIFYING / DONE 是卡片的当前执行状态，只在工作台维护。** 是否完成按该卡片明确约定的范围与验收条件判断；模块 DONE 只表示标题和详情限定的能力基线完成。写了 devlog、代码已合入或单测通过，本身不等于整个需求完成。
- **“本次验证通过 / 失败 / 未验证”是实验或验收的历史事实，保留在 devlog。** 它们不承担问题状态标记，也不应因后来问题完成而被改写成成功。
- 代码修复、服务加载、真实环境验证和业务效果分别说明。尚未推进的工作为 TODO，正在实施的工作为 PROGRESSING，实现或交付已完成、验收尚未完成的工作为 VERIFYING；阻塞关系用 `blockedBy`，搁置、待核对使用标签和下一步说明。验收门槛的通过 / 未通过 / 待测是引用报告的验收事实，不从卡片状态推导。独立的后续工作另建关联卡片，不能用主体修复推定其也已完成。
- 历史 problems、TRD、报告和 devlog 中的“待实施”“已完成”等按当时日期、版本和环境阅读；当前状态以工作台及所链接的最新证据为准。发现冲突时补充依据，不在多个文档中同步维护一套任务状态。

## 工作台的维护

- **用户查看：** 打开 `dev/workbench.html`。概览看当前里程碑能否交付、闭环地图、紧急事项与状态一致性警告；看板按分类、类型、里程碑或文字筛选；验收门槛按阶段查看用例结果。点击卡片或门槛查看详情与关联资料。需要新增工作、调整状态或补充证据时直接告诉 Agent；项目文件更新后刷新页面即可。页面不维护浏览器草稿，也不提供另存、导入或编辑入口。
- **Agent 维护：** 解析 HTML 中 `<script id="workbench-data" type="application/json">` 的 JSON（schemaVersion 2），只修改相关卡片、门槛或里程碑并写回该节点；沿用稳定 ID，保留历史来源和其他工作。数据中 `revision` 每次修改递增，`updatedAt` 和卡片日期使用 Asia/Shanghai；只有重新采集资料时才更新 `sourceCheckedAt`，不能把编辑日期当成验证日期。序列化时将 `<` 写为 `\u003c`，避免内容截断 script 节点。
- **结构校验：** 类型只用 `module / requirement / task`，状态只用 `todo / progressing / verifying / done`，优先级只用 `P0 / P1 / P2 / unset`；ID 唯一，分类与里程碑存在，关联、阻塞与门槛 ID 存在且不指向自身，日期为 `YYYY-MM-DD`，资料链接使用 http(s)。门槛状态只用 `pass / fail / untested`，必须带证据链接或待测说明；未知数值写 null，不写 0。新增可形成 TRD 的需求继续遵循独立分支、PR 和 TRD 首提交要求；历史模块无需补造旧 PR/TRD。
- **协作更新：** 全项目共用仓库中的工作台，各 Agent 先读取当前分支最新内容，再按 ID 更新本次工作，随需求通过 PR 集成到 `dev`；不能用旧分支整份覆盖其他卡片。页面始终读取文件内的 JSON，不读取旧浏览器草稿，不另建实时 JSON 主文件。离线页面不会自动同步 PR；刷新来源时保留采集日期、PR 关闭/合并事实与业务验收的区别。

## 一次修改如何更新文档

1. 在看板找到或建立卡片，明确类型、分类、业务影响、范围与验收条件；详细问题分析在 problems 中按同一编号保存。
2. 涉及设计或接口变化时更新对应 TRD；实验输入、脚本和原始输出保留在相应证据目录。
3. 将决策、验证结果和整体指标写入统一 devlog，注明原问题编号并链接来源；没有测量的数据明确写未测。
4. 根据实际验收结果更新仓库看板的状态、下一步、验证边界及 PR/TRD/devlog 链接，并随本次工作提交。后续实验在原证据位置追加有日期的记录，保留原失败结果和适用边界；不再移动 problems 的历史条目来表达当前状态。

已有历史问题正文、TRD 和实验退役摘要保留为追溯依据；后续新增内容按以上职责维护，避免复制整段材料后形成多个独立更新的副本。
