# AniVAG UI Design · Product Facts

> 核对日期：2026-09-14
> 事实来源：仓库根 `README.md`、`transfer.md`、`docs/design/各个阶段目标.md`，以及仓库远端 `https://github.com/owariband/AniVAG.git`
> 当前代码基线：`1f0662d`（`main`）

## 已确认的产品事实

- AniVAG 是面向事件级视频检索与时间证据定位的多模态视频理解产品。
- M1 的首个落地场景是“动画名场面自然语言召回与定位”，不是自动评选名场面。
- 核心用户任务是：导入多集动画视频，等待建库，输入对梗、动作、人物关系或情绪变化的自然语言描述，得到可核验的集数、时间戳、关键帧与文本证据，并跳转播放。
- M1 是本地单用户端到端产品；注册、登录、权限、会员、管理后台与多租户计费不属于首版 UI。
- 产品规划明确需要 Web UI，但当前仓库尚未实现 AniVAG Web Client；上游 `engines/VideoRAG/Vimo-desktop` 的 Electron UI 仅作为功能与实现参考，不是 AniVAG 品牌或现成 design system。
- 当前工程已具备解析、双路召回、MySQL 事实源与 Qdrant 派生索引等后端基础；完整上传、常驻 Job Runtime、Conversation Service 与正式 Web API 仍是后续阶段，设计稿不得把它们描述成已经上线的能力。

## 用户确认的交互决策（2026-09-14）

- 检索的产品形态是用户与 Agent 的连续对话，不是一次性搜索框加传统结果列表。后续追问需要继承当前 Series、已看候选和对话上下文。
- Agent 召回备选画面后，必须逐条给出面向用户的选择依据：命中了哪些人物、动作、台词、情绪或视觉元素，证据来自哪个通道，以及哪里仍不确定。
- “解释原因”指可由片段文本、画面描述和时间位置复核的依据摘要，不展示模型私有思维链，也不把候选包装成绝对正确的剧情事实。
- 视频上传／建库是可持续数分钟甚至更久的后台任务。当前进度必须在全局导航中持续可见，并能进入详情查看单文件进度、队列、暂停、恢复、失败与重试。
- 上传和建库是两个连续但不同的阶段：上传百分比只表示文件字节传输；只有校验、媒体准备、视频解析、文本／视觉向量和索引同步完成后，剧集才是“可检索”。
- 常见上传形态是 2–3 个视频并行传输，而不是单文件串行队列。UI 必须同时显示所有活跃上传会话的独立进度；总体进度只能作为按全部文件字节汇总的次级信息。
- 并行轨道按真实活跃数生成：两个视频时显示两条，三个视频时显示三条，不用空轨道伪装成固定三路。本轮截图选择三路满载状态以暴露最大信息密度。
- 每个视频的上传与后续建库独立衔接：一个视频传完即可进入自己的校验和解析流程，不必等待同批另外两个视频；空出的并行槽位可接入排队文件。

## M1 UI 必须覆盖的任务面

1. 动画库与系列状态。
2. 本地视频导入、逐文件上传进度、队列、剧集顺序确认和异常处理。
3. 上传后的建库任务总进度、分集阶段、失败原因、恢复、重试与取消。
4. 以 Agent 对话为主体的自然语言检索、对话历史与 Series Scope。
5. Agent 候选回答：集数、时间戳、关键帧、选择依据、证据文本／通道与不确定点。
6. 视频播放与精确时间跳转。
7. 基础本地设置、模型/服务状态和存储状态。
8. 空状态、加载、离线、无结果、低置信度与部分失败等系统状态。

## 设计中不得虚构为已完成的能力

- 完整用户账户与权限系统。
- 云端多租户 Workspace。
- 完整分片上传、分布式队列或 MinIO 集群。
- 自动识别并排行整部动画的“名场面”。
- 绝对正确的人物识别或 Top 1；现有资料明确记录了短查询歧义与人物误认风险。

## 原型状态说明

- v3 方向稿使用“EP 08 / 09 / 10 分别上传 64% / 42% / 20%”作为三路并行交互样例；这些数字只用于评审进度层级、文案与布局，不是对当前运行中任务的陈述。
- UI 中的上传进度对应上传字节；`VideoChunk` 只用于描述解析后的时间证据。两者不可在实现时共用同一概念或同一进度口径。
