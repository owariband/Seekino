# MyGO 第 3 集的调度、流式续租与整集实跑

2026-11-07。验收目标是用原模型、3 FPS 和相同并发，从 ASR 开始在 20 分钟内完成可检索的整集。计时起点为任务创建，终点为父任务完成且该版本的索引可读。摘要单独核验。失败任务记录从提交到失败的时间。

## 为什么同一部动画有时 14 分钟，有时超过 50 分钟

| 历史实跑 | 并行提交情况 | 提交到完成 |
| --- | --- | ---: |
| 11 月 5 日，第 4 集 | 单集 | 14 分 08.4 秒 |
| 11 月 7 日，第 1 集 | 四集在六秒内提交 | 32 分 23.6 秒 |
| 11 月 7 日，第 2 集 | 同批，发生结果校验失败和续跑 | 73 分 02.3 秒 |
| 11 月 7 日，第 3 集 | 同批，约 1 秒取得整集租约 | 54 分 47.7 秒 |
| 11 月 7 日，第 5 集 | 同批，取得整集租约前等待 7 分 46.1 秒 | 55 分 44.0 秒 |

两批运行的代码都是 `d54dfbde`。使用同类素材和配置仍然会受到多集并跑、模型响应、结果校验和整集准入影响。第 3 集最后一次 refine 到整集完成用时 149.8 秒，原来的 54 分钟大多发生在最后一次 refine 之前。

旧代码把会访问 MySQL 的 `check_active` 传给了 Gateway。它在每个 SSE 事件上执行，先校验父记录，再更新子任务租约，文本增长因此放大了调度 SQL。四集的 MySQL 摘要有 384,071 次块续租更新和 1,049,817 次窗口续租更新。对应 trace 中，understand 与 refine 各有 347,389 和 1,043,428 个 SSE 事件。数据库的统计还包括周期心跳和执行边界。单看父锁持有了几毫秒，解释不了这条高频路径的总量。

## 状态如何取得和更新

- 普通流式回调只读当前执行的本地取消标志。worker 周期续租，模型准入、工具副作用和结果提交继续核验 MySQL 租约。沿用 [PR #64](https://github.com/owariband/Seekino/pull/64) 已有的流控制修改，模型草稿的持久化交给该 PR。
- 同一个 understand 租约复用绑定时已取得的输入快照。活跃计时直接使用持锁校验过的子任务，结束回调晚于提交时只读取租约版本回执。暂停中的任务退出恢复收尾扫描。
- 调度使用提交后的成员位和就绪 ID。同一集可以同时理解、细化和索引。refine 候选按与运行中窗口共享的成员个数排序，重叠窗口仍可填空槽。暂停、接管和跨消费者容量继续由数据库作最终裁定。

## 相同输入的回放

见[回放入口](benchmark_animation_stream.py)。选择旧第 3 集各一个已成功的 understand 和 refine 请求，通过原 SDK 解码相同的 SSE 顺序。传输由内存回放，队列、租约和事务使用独立 MySQL。两版交替执行三轮，用输出字节的 SHA-256、事件数和领取阶段确认输入与最终正文一致。SQL 计数范围从 SDK 开始取流到结束，排除模型准入、写结果和后台心跳。回放用时不含生成模型输出、网络传输或真实索引的耗时。

| 同一录制请求 | SSE 数 | 父行加锁查询，旧 → 新 | 流回调发出的全部 SQL，旧版三轮 → 新版每轮 | 回放时间中位数，旧 → 新 |
| --- | ---: | ---: | --- | ---: |
| understand | 2,249 | 2,250 → 0 | 6,139 / 6,004 / 5,902 → 0 | 1.879 → 0.394 秒 |
| refine | 6,822 | 6,823 → 0 | 18,143 / 18,423 / 17,836 → 0 | 4.737 → 0.217 秒 |

每次流开始还有一次控制检查，因此 9,071 个事件共发起 9,073 次父行加锁。两段合计原版每轮有 23,738–24,427 条 SQL，修复版三轮均为 0。原版两条锁查询分别针对父行和子行。毫秒内再次续租且字段未变时，ORM 可省略 UPDATE，所以各轮的写入次数有差异。整集实跑仍有 5,282 次块租约更新和 2,685 次窗口租约更新，其中包含定时续租和其他边界检查。[逐轮计数、用时与正文哈希](animation-results.json)

## 原模型整集实跑

原片长 23 分 39.960 秒。新旧任务的源文件 SHA-256 和持久化配置分别完整比对，均使用原 DeepSeek、3 FPS、相同 ASR、embedding、10/10/1 并发。隔离库在创建新任务前没有原集的 ASR、块、窗口成果或 ES 文档。正常 reparse 入口创建一个新任务，同任务续跑通过 retry 入口。前一批四集共享服务，这次只有一集，两组耗时无法分离代码、负载和供应端差异。

最初实跑加载 `ebd30c44` 对应的解析代码。前 5 分 03 秒提交了全部 24 个 understand，5 分 20 秒时已有 14 个 refine 和 5 个索引提交。剩下的 8 个窗口还在续租，采样时 MySQL 没有数据锁等待，8 个线程在 TLS 读取上阻塞。随后日志既有模型 HTTP 500、连接中断，也有已失效的旧请求迟迟未退出。网络等待本身不足以证明每一个窗口都在取消或每个错误都由取消引起。

针对后一条路径，用本地 HTTP 与 HTTPS 服务在首个 SSE 已解码且工作线程进入下一次读取后发出取消。旧 Responses 先关闭流，再尝试唤醒读取。正在阻塞的线程接近 4 秒的读超时才退出。修复复用 Chat 已有的 HTTP/1 唤醒顺序，HTTP/2 按流关闭，保留其他复用同一连接的请求。HTTP 实测 3947.3 → 0.2 毫秒，HTTPS 实测 3947.6 → 0.2 毫秒。对应提交为 `5304e095`。本地回归还覆盖首块前取消、正常流和过期租约。以上测试没有调整模型超时、重试次数或冻结并发。
