## Q02、Q03 首段整包正文等待的原因（原 FTT 标注撤回）

**两轮首段整包正文到达耗时几乎等于第一次 Supervisor 模型调用的完整耗时。** 当时的 Gateway 使用 `stream=False`，Deep Agents 在 `after_model` 才交付整段正文，Supervisor 再发布快照。这解释了旧体验的等待，不能作为真实流式 FTT 的归因；模型何时产生首个正文增量仍未测得。

下表由原始浏览器事件和模型用量记录重建，没有新增模型调用。前后阶段用服务端时间相减，整包正文到达与 TT 使用客户端单调时钟；不把两类时钟拼接成一条毫秒级精确的网络时间线。

| 阶段或指标 | Q02：结合已有基础继续解释 | Q03：追问刚才解释的原片依据 |
| --- | ---: | ---: |
| 服务端开始处理 → 首次模型调用开始 | 0.107 秒 | 0.055 秒 |
| 首次模型调用开始 → 完整返回并校验结束 | **29.370 秒** | **27.071 秒** |
| 首次模型调用结束 → 首正文快照事件生成 | 0.009 秒 | 0.032 秒 |
| 真实流式 FTT | 未采集；旧标注撤回 | 未采集；旧标注撤回 |
| 首段整包正文到达耗时 | **29.576 秒**，实质回答 | **27.231 秒**，进度说明 |
| 客户端 TT | **29.620 秒** | **178.270 秒** |
| 首次调用 input / cached input tokens | 6,747 / 3,328 | 6,899 / 3,328 |
| 首次调用 output / reasoning tokens | 587 / 476 | 512 / 334 |

Q02 没有调用工具，三句话整段返回后才出现，整包正文到达与 TT 只差约 44 ms。Q03 的第一轮模型先生成进度说明及工具调用，完整返回后才交付该说明，随后执行实时理解。78.411 秒实时工具发生在这段正文之后，其中视觉模型调用为 77.126 秒；这影响 TT，不是前面整包正文等待的原因。

按模型调用记录计算，29.370/27.071 秒分别占首段整包正文等待约 99.3%/99.4%，其余约 0.206/0.160 秒。这只用于定位旧的完整响应等待，不是 FTT 分解，也不能继续拆成精确网络耗时。旧数据无法回答供应商真正首正文有多快或流式可节省多少秒。

历史运行工作区为 `full-video-asr/Seekino`，相关文件当前指纹与首轮 manifest 一致：`gateway/openai/agent.py:311` 明确 `stream=False`；`gateway/agent_model/deepagents.py:351` 的 `after_model` 才调用正文回调；`agent/chat/supervisor.py:370` 接收正文并发布快照。工厂使用内部 adapter，排除了只检查另一条 SDK 接线的误判。源码指纹、原始证据摘要和逐阶段时间见 [整包等待 trace 与指标更正](evidence/course-qa-ftt-trace-20261101.json)。这与首轮日志相符，但仍保留前述“未对全部进程已加载代码做证明”的运行边界。

还有一个配置细节：历史 Kimi profile 在 `reasoning_effort=none` 时**省略该参数**，并没有发出关闭推理的指令。首轮配置虽为 `none`，Q02/Q03 首次调用仍分别记录 476/334 reasoning tokens；它们是 output 的子集，不能再次相加，也不能直接换算成思考耗时。记录能确认存在这部分生成量，尚不能把模型调用里的供应商排队、网络、输入处理、推理与正文生成分别计时。

QA 分支在本次调查前的 `c93877de` 已包含 B24 的协议流式接收，但 [request_chat_stream](../../../gateway/streaming/chat.py) 仍收齐 delta 后返回完整结果，[Deep Agents](../../../gateway/agent_model/deepagents.py) 仍在 `after_model` 才交付正文。**配置 `stream=true` 与用户逐字看到回答是两个需要分别验证的环节**；B24 不能直接作为真实流式交付与 FTT 已验收的证据。

后续按 [独立 PRD](../../design/03-product-reassessment/chat-streaming-prd.md) 固定模型、问题、历史与缓存，验证正文增量从供应商到页面的持续交付，再建立真实流式 FTT 基线。采集实际请求、供应商正文、服务端和客户端事件；将非流式及上层缓冲作为必测反例。FTT 与 TT 并列评价，旧整包等待不能作为 FTT 优化前基线。本次未修改业务实现。

## 178 秒的可复现阻断路径

Q03 Assistant ID：`3e611420-b07f-4a6c-a5ca-c9b4af946fc4`。业务日志和前端事件共同支持以下拆分：

1. Supervisor 约 27.2 秒后发起 `understand_current_video`。
2. 工具耗时 78.411 秒。基础 Chunk 已有，按新问题对同一帧重新生成视觉观察；这次不用重新 ASR。
3. 工具返回后约 27.9 秒，Supervisor 给出一段判断，并调用 `submit_video_item`。参数是当前观看 Chunk，74.54–94.72 秒。
4. 工具约 1 ms 返回 `VIDEO_EVIDENCE_UNAVAILABLE`。当前系列未 READY，`video_available=false`；实时证据不属于 `retrieval_calls` 的受信卡片候选，守卫拒绝是正确的。
5. 再约 44.7 秒后，Supervisor 通过文字时间点完成回答。这个时间段包含错误反馈后的继续生成，不能把全部 44.7 秒断言为错误的净因果成本。

职责入口：[实时理解工具与视频提交](../../../agent/chat/supervisor.py)、[问题相关帧观察](../../../agent/chat/realtime_understanding/runtime.py)、[派生缓存](../../../server/service/realtime_understanding.py)。当前实时 prompt 要求出处问题优先取证，但视频卡 prompt 没有充分区分检索候选与观看证据；模型因此走了一次无法成功的提交路径。缓存又依赖当前原问题，不能把“同一位置、同一 Chunk”直接等同于“不需要新模型调用”。

建议后续最小修复先约束可用工具/交付方式：没有受信检索候选时明确采用当前视频时间链接，保留证据与版本校验。再验证已有文字证据足够的出处问题是否能避免重复视觉观察。它们是待验证方向，本 PR **没有修改业务策略，也没有绕过 READY 或证据守卫**。另观察到工具 `query` 没有传入 RealtimeRequest，当前仍使用原 `user_message`；其独立质量影响未复现，不作为已确认的本次耗时根因。
