## 0.2 既有问题与训练边界

既有实验中，33 图单请求的 Qwen 输出退化为 34 个 SCENE、0 条对白；改成短分组后恢复 14 条对白；只输出匿名视觉证据后得到 44 条观察、19 条非空字幕，但仍有重复、过度说话者归因和推断。这提示输入组织与任务负担是重要变量，训练收益仍待验证。来源：[调教日志第 7–8 节](模型调教log.md#7-本地-qwen-调教过程)。

| 问题 | 训练可尝试改善的部分 | 仍需配合的机制 |
| --- | --- | --- |
| 漏字幕、双路字幕混在一起、跨帧抄错 | OCR、行序、字幕变化与图片的对应关系 | 保持足够分辨率，必要时补字幕区域裁剪或独立 OCR |
| 吉他/贝斯、物体和动作错认 | 动画领域的视觉描述与细节辨别 | 复核困难样本；必要时单独验证视觉模块微调 |
| 说话者错配、根据剧情胡猜 | 学会依据证据归因，并在不足时输出未知 | 图片本身不一定能确认说话者；音频和身份归一独立处理 |
| 多帧复读、字幕变化被过度合并 | 学会覆盖变化与合并重复证据 | 保留短分组、确定性去重和引用检查 |
| 毫秒时间错误、事件归属错误 | 可以改善引用，但首轮不训练模型计算时间 | Frame 编号由 Engine 映射到时间，再校验事件归属 |
| 抽帧遗漏瞬间、没有音轨的对白 | 训练不能直接补回未输入的证据 | 改进采样、关键帧与 ASR |

人物真名归一和最终 Timeline 整理暂留后续阶段。若未来训练跨帧身份识别，应另设明确的参考人物图或外观匹配任务，避免把固定作品知识当成当前视觉证据。

# 一、Plans和方案选型

## 1.1 云端模型与训练 GPU 的职责

云端强模型是教师，提供答案或辅助判断答案质量；训练 GPU 运行我们掌握权重的 Qwen，并更新它的参数。只有教师 API 也能做输出层面的蒸馏，不需要教师权重或内部概率。

监督微调和 RL 都属于后训练；LoRA 是减少需要更新的参数量的一种方法，也可以用于不同的训练目标。

推荐数据流：

```text
真实动画片段
  → 与部署一致的抽帧、分辨率、顺序和 Frame 编号
  → 云端视觉教师生成匿名视觉证据 JSON
  → 规则检查 + 人工复核困难样本、随机抽审
  → Qwen3-VL-8B 的 LoRA / 量化 LoRA SFT
  → 固定评测集验证
  → 本地部署格式与运行时再次验收
```

教师与学生应看到同一批图片。教师若看完整视频、听音频或使用剧情资料，超出学生输入可确认范围的事实必须从训练答案中剔除。文本 refiner 看不到图片时，不能可靠补回视觉模型漏掉的事实。

现有云端模型也发生过漏字幕、将眼部高光识别成眼镜、将肢体重叠描述成搭肩等错误。已有解析结果只能作为标注草稿；教师失败、输出截断或证据不完整的结果不进入正确答案集。来源：[受控 A/B 记录](../../outputs/engine/ep07-full-60s/diagnostics/segment-0010-deepseek-flash-neutral-0.5fps-controlled/comparison.json)。

## 1.2 路线选择

| 路线 | 数据与训练方式 | 本项目建议 |
| --- | --- | --- |
| LoRA SFT | 给定图片与经过复核的正确回答，学习生成该回答 | 首轮主路线；优先冻结视觉编码器和对齐模块，只给语言部分添加 LoRA |
| 量化 LoRA / QLoRA | 冻结量化后的基础模型，训练高精度低秩参数 | 本地或显存有限时优先试验；不同框架的量化格式并不相同 |
| DPO 等偏好优化 | 对同一输入准备更好与更差的回答 | SFT 后仍过度推断、复读时可验证；偏好必须依据图片与标注 |
| GRPO 等 RL | 对同一输入生成多个回答，用奖励更新模型 | 有可靠评价体系后再验证；多帧生成与评分会增加资源负担 |
| 全参数微调 | 更新大部分或全部参数 | 首轮不采用；显存和实验成本较高，少量领域数据也容易造成能力退化 |

Qwen 官方提供自定义多图数据与 LoRA 的训练框架；ms-swift 提供 Qwen3-VL 微调说明及多模态 GRPO 路线。这些支持说明工具链可用，不等于已验证 Seekino 的数据、硬件和收益。[Qwen 官方训练框架](https://github.com/QwenLM/Qwen3-VL/blob/main/qwen-vl-finetune/README.md)、[ms-swift Qwen3-VL](https://swift.readthedocs.io/en/latest/BestPractices/Qwen3-VL-Best-Practice.html)、[GRPO 文档](https://swift.readthedocs.io/en/latest/Instruction/GRPO/GetStarted/GRPO.html)。

## 1.3 首轮训练目标与数据

沿用 [NEUTRAL_VISUAL_PROMPT](../../engine/parse/prompts.py) 与 [NeutralVisualEvidence](../../engine/parse/schemas.py)：输出 `evidence_frames`、匿名 `subjects`、`visual_fact`、`hard_subtitle`、`visible_speaker`，不计算毫秒，不输出人物真名或完整剧情。

可先用约 20–50 组人工核验片段建立早期验收对照，后续扩到约 100–200 组固定评测，再制作约 1,000–3,000 组多集、多场景训练样本。这里的一组是一条多图请求，不是一张图片；这是探索规模，不是质量保证。几十组只能提供早期诊断信号；已有单集实验可作为困难样本种子，不能以单集调好证明泛化。

训练集与测试集按整集或作品划分，避免相邻近重复画面泄漏。重点覆盖双语/双区域字幕、多人物镜头、吉他与贝斯、遮挡、舞台灯光、观众与台上人物、递水动作和短尾段。保留正常样本，防止只学习少数故障类型。

训练只计算助手答案的损失。先确认图片占位符、图片数量、顺序和 Frame 引用一一对应，再训练；不能将图片预处理错误产生的假改善归因于微调。

## 1.4 RL 的评价前提

奖励要兼顾字幕准确度、事实准确率与召回率，惩罚串帧、错误归因和无依据推断。仅奖励合法 JSON、少重复或少犯错，会鼓励少输出、全部填未知。

字幕可对照人工文本计算准确度；自由视觉描述需要逐项事实核验或经过校准的评审。不能只用文本相似度判断事实正确，也不能将另一模型的主观评分当唯一真值。结构、Frame 范围和确定性时间规则优先由 Engine 校验。

# 二、显卡与内存要求

## 2.1 为什么模型文件大小不能代表训练显存

8B 档基础模型以 16 位加载，单纯权重就约 16–18GB，实际包含视觉模块。训练还需要激活、中间计算、梯度和优化器状态。LoRA 大幅减少需要更新的参数，但仍要运行基础模型的前向计算，以及有关模块的反向计算。

采用 FP32 Adam 状态、可选 FP32 主权重的常见混合精度全参配置，按约 8B 参数估算，单纯权重、梯度与优化器状态已可能约 96–128GB，尚未算激活。不同优化器、状态精度和 offload 会改变占用；不能把这个算式当所有实现的硬下限。

现有本地 Q4 GGUF 与 projector 合计约 5.78GB，只说明部署文件体积。训练应使用对应 HF 或 MLX checkpoint，Ollama 的 Modelfile 不承担梯度更新。

## 2.2 实用资源分档

以下是本项目的工程选型建议，尚未实测。图像分辨率、视觉 token、总序列长度、LoRA 范围、batch 和梯度检查点都会改变峰值；容量不能等同于速度。

| 任务 | 可尝试的资源 | 接近生产多帧负载的规划 |
| --- | --- | --- |
| 单图/少图量化 LoRA 小试 | 16–24GB NVIDIA 显存，batch=1，短序列 | 24GB 是有意义的探索档；不能据此保证 15 图高分辨率训练可跑 |
| 8B 量化 LoRA，多图 SFT | 24GB 可条件试验 | 48GB 有更多余量；长序列或较多可训练模块可优先选 80GB |
| 8B 16 位 LoRA，多图 SFT | 48GB 作为首个试跑档 | 80GB 更便于保留分辨率和序列长度，仍需测峰值 |
| LoRA GRPO，多帧生成 | 短输入、小生成组可以更省 | 80GB 单卡或多卡作为规划起点；根据 rollout、KV cache 与训练模型的放置调整 |
| 常规全参 Adam 微调 | 高容量单卡、offload 或多卡 | 通常需要更高资源；48GB Mac 不作为该路线的首轮设备 |

因此，轻量微调的门槛不算很高，24GB 档已有试验价值；保留我们真实的多帧输入时，48–80GB 云端 GPU 更省试验调整成本。首轮没有必须上多卡集群的前提。

Unsloth 的通用表给出 8B QLoRA 约 6GB、16 位 LoRA 约 22GB，并明确称这些是绝对最低量级、会因模型而增加。它不是 Qwen3-VL-8B 的 15 帧动画训练保证，不能把 6GB 用作我们的选卡结论。[Unsloth 资源要求](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements)。

我们已有 15 帧 llama.cpp 输入的 prompt 约 14.3K token；MLX/HF 的实际处理可能不同，需要重新统计。把网上 2K/4K 序列的单图示例直接用到这个负载，可能发生截断或显存不足。[调教日志第 14 节](模型调教log.md#14-qwen-主动抽帧与直接视频-ab)。

## 2.3 单张 RTX 4090 是否够用

标准 RTX 4090 配备 24GB GDDR6X 显存。[NVIDIA 官方规格](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4090/)。

4090 可以作为首轮 8B QLoRA 的租卡候选。建议基础模型 4-bit、只训练语言部分 LoRA、冻结视觉编码器与对齐模块、micro_batch_size=1，并使用训练栈支持的梯度检查点与高效 attention。梯度累积用于提高有效 batch，不会消除单个最长样本的显存占用。

完整 15 帧输入能否放进 24GB，目前没有本项目实测结论。正式训练前，必须用目标分辨率、真实答案长度及最长输入短跑，确认没有图片/答案截断、显存不足或过慢的 offload。通过这一步之后，4090 可以继续做完整 QLoRA 训练；最终质量由独立评测决定。

如果选择 16 位 LoRA，或要增加视觉模块更新、batch 或序列长度，单张标准 4090 的余量较紧，不作为稳妥选型。若 15 帧只能通过降低字幕可读性才能跑通，应优先验证 48–80GB 云端 GPU。该建议属于工程规划，不是宣称这些资源必然足够。

租卡选择尚未确定：希望先用较低资源验证 QLoRA 时，可短租 4090 测真实负载；希望首轮保留更多输入与训练配置余量时，优先选 48–80GB。多帧 GRPO 另行测量，不能用 SFT 可跑来推断 RL 可跑。

# 三、本地 Mac 能不能训练

## 3.1 本机与支持情况

2026-09-15 只读查询确认：本机为 Apple M5 Pro，统一内存 51,539,607,552 bytes，即 48GiB（通常称 48GB）。这不是一张有独立 48GB 显存的 NVIDIA 卡，系统、应用和 GPU 共同使用内存，GPU 可用工作集也需实际查询和测量。

MLX-VLM 维护者的 LoRA 文档明确列出 Qwen2/3/3.5 VL 训练支持，提供 LoRA、量化 LoRA、梯度检查点、梯度累积及图片列表数据格式。因此本地有可用的轻量微调路线；不能将 CUDA/bitsandbytes 命令原样搬到 Mac。[MLX-VLM 训练文档](https://github.com/Blaizzy/mlx-vlm/blob/main/mlx_vlm/LORA.MD)。

已有 [mlx-community/Qwen3-VL-8B-Instruct-4bit checkpoint](https://huggingface.co/mlx-community/Qwen3-VL-8B-Instruct-4bit)。checkpoint 存在与框架支持是可行性证据；本机 8B、15 帧、目标分辨率的稳定训练尚待试跑。

## 3.2 本地首轮建议

1. 在独立训练环境固定 MLX-VLM 与模型版本，使用对应的 MLX 权重和 processor。
2. 从 8B 4-bit 基础模型、batch=1、冻结视觉模块、低秩适配器开始，启用梯度检查点。
3. 首次用 1–4 帧确认梯度、损失、保存与重新加载适配器正确，再逐步增加至 8–15 帧。少图试跑只验证管线，不代表生产多图质量。
4. 对真实样本统计总 token 和峰值内存；确保图片与答案未被最大序列长度截断。MLX-VLM 文档中的默认短序列不能直接作为本项目配置。
5. 先跑几十个微批，测耗时、内存与训练/验证损失，再决定完整一轮是否放本地。

量化 LoRA 更适合这台 48GB Mac 的起步试验。16 位 LoRA 也可以尝试，但长序列和视觉模块更新会使余量减少。本地 GRPO 有更多生成、评分与框架整合工作；首轮 RL 更适合成熟云端训练栈。

降低图片分辨率会节省内存，但可能损害小字 OCR。必须记录这个变量，并在相同输入设置下比较未训练与训练模型。

## 3.3 本地训练与最终部署

MLX-VLM 可在自己的运行时加载训练后的 adapter，先验证其效果。MLX adapter 与 HF/PEFT adapter 的参数命名、布局及量化格式可能不同，不能默认直接交给现有 Ollama。

若最终仍使用 GGUF/Ollama，应单独验证适配器合并、权重转换、视觉 projector 和模板兼容性；转换失败时不能用未加载适配器的模型产生假验收。云端 HF/PEFT 路线更便于保留与原始权重一致的训练产物，但也需要验证多模态 GGUF 导出。

本地 MLX 原始模型、MLX 训练后模型、最终 GGUF 部署模型分别验收。微调通常不改变 8B 的模型规模；更短输出可能节省时间，质量与速度必须分别评估。

# 四、训练一般多少小时

## 4.1 没有固定小时门槛

几十步的管线验证可以从几十分钟的时间预算开始；千级样本的 SFT 通常需要按小时规划。接近生产的多帧输入可能扩大到一天或数天。这里是实验预算量级，不是本项目机器实测。

ms-swift 发布的 Qwen3-VL-4B LoRA 演示列出两卡各约 21GiB、训练 12 分钟，其序列上限为 4096，并说明是演示。页面该示例没有完整提供可用于我们选型的 GPU 型号与负载细节；不能把 12 分钟外推为 M5 Pro 或单卡 8B 的训练时间。[官方框架示例](https://swift.readthedocs.io/en/latest/BestPractices/Qwen3-VL-Best-Practice.html#dense-models)。

## 4.2 根据一次短跑算自己的预算

一个微批指一次 batch 的前向与反向计算；梯度累积若为 4，则通常 4 个微批才更新一次参数。不能把总微批数除以梯度累积后，仍乘单微批耗时。

简单单设备、不开 packing 时：

```text
微批数 ≈ ceil(训练样本数 / micro_batch_size) × epochs
训练时间 ≈ 微批数 × 实测平均微批耗时
总时间 = 训练时间 + 图片/数据预处理 + 验证生成 + 保存/导出 + 加载等开销
```

若日志报告的是优化器一步的耗时，则应计算优化器步数，确保该耗时已经包含梯度累积。多卡、packing、变长样本、I/O 等需使用对应的实测统计。

例如：2,000 组样本、2 epochs、单设备 micro_batch_size=1，共约 4,000 个微批。

| 实测每微批完整耗时 | 纯训练时间 |
| --- | --- |
| 2 秒 | 约 2.2 小时 |
| 5 秒 | 约 5.6 小时 |
| 10 秒 | 约 11.1 小时 |
| 30 秒 | 约 33.3 小时 |
| 60 秒 | 约 66.7 小时 |

这张表是条件算式，没有宣称云端能达到 5 秒或本机需要 30 秒。它说明千级多帧训练可以是数小时，也可以是数天；测出本机/云端的微批耗时后，就能给出可靠预算。

首次建议预留 30–60 分钟进行加载与短跑；测量前先完成预热，选择同时覆盖典型长度和最长输入的几十个微批。记录有效 token、完整前后向时间、峰值内存、数据加载、保存及验证时间。固定配置后再外推，不能用短样本速度估计全部长样本。

## 4.3 RL 与其他耗时

GRPO 每个输入需要多个候选生成，再评分与训练。设置 4 或 8 个候选会增加 rollout 工作，但总耗时并不简单等于 SFT 的 4 或 8 倍：并行程度、KV cache、输出长度、评分方式和模型共置都影响结果。应单独短跑后计算预算。

云端教师标注、人工复核、数据下载和量化验收另算。Qwen 自回归生成 400 秒的记录不能直接用作训练一次微批的耗时，因为监督训练的答案 token 通常并行参与计算，且运行时不同。

目前核对资料没有提供可直接引用的“M5 Pro 48GB、Qwen3-VL-8B、15 帧、相同分辨率和适配器配置”的训练速度 benchmark。本项目应以短跑结果作为耗时选型依据。

# 五、权威 Benchmark 与项目验收

## 5.0 公开评测与项目验收各自回答什么

本文的项目评测首先指内部固定验收集：可重放的真实输入、人工确认的检查点和固定评分方式。起步不要求发布学术数据集、建设榜单或另做完整 Benchmark 平台。

2026-09-15 讨论中已认可首轮评测组合：一个相关公开评测 + 约 20–50 组项目验收请求 + 原始/微调模型的同条件对照。这是实验选择，尚未形成训练后效果结论。公开评测的起步候选见第 5.1 节；项目验收集后续随作品类型、字幕样式和新增 Bad Case 扩充。

| 数据/评测 | 用途 |
| --- | --- |
| SFT 训练数据 | 图片、指令与正确答案，用于更新模型参数 |
| 公开 Benchmark 的测试集 | 按既有协议衡量通用能力，提供外部可比性与退化检查 |
| Seekino 项目验收集 | 按实际多帧输入验证字幕完整、Frame 对齐、可见事实和错误推断等目标行为 |
| 上线后的监控与反馈 | 观察真实质量、耗时和失败情况，将新问题整理为后续验收用例 |

公开基准与业务验收结合，是有官方工程实践支持的评测组合；不同团队可以按任务和阶段选择侧重点。参考依据见第 5.5 节。业务验收检查目标任务，公开评测提供外部对照，上线后的反馈继续补充覆盖。

公开评测可以直接复用数据、标注与评测脚本。项目验收则检查特定产品要求：例如 [Video-MME 的常用协议](https://github.com/MME-Benchmarks/Video-MME)是视频选择题，即使答对选项，也不能证明完整抽出了同帧两路字幕或正确引用了字幕变化的帧。这个差异来自任务形式，不代表公开评测没有价值。

首轮建议只运行一个公开评测，并固定约 20–50 组项目验收请求，包含普通片段和典型困难情况。项目标注先集中在三项：字幕原文与对应 Frame、关键可见事实、需判为无依据的推断。困难样本与普通样本分别报告；小集合只用于诊断和早期对照，后续再扩充覆盖。

项目验收样本可在制作领域数据时从未训练的整集/作品中另行留出，无需再单独采集一套大规模数据。用于选配置的验证集与最终测试集仍需区分。公开测试题和最终项目测试样本不参与梯度更新，也不反复用于挑选训练配置。

## 5.1 推荐的公开评测

公开评测可检查训练前后通用能力是否改善或退化；不直接等价于我们的动画视觉证据 JSON。

| Benchmark | 权威来源与覆盖 | 本项目用途与限制 |
| --- | --- | --- |
| OCRBench（v1） | 作者官方数据与脚本；1,000 道人工核验题，覆盖文字识别、文字问答等任务 | 可先固定子集做低负担的通用文字能力对照；跨帧动画字幕仍由项目验收覆盖。[官方说明](https://github.com/Yuliang-Liu/MultimodalOCR/tree/main/OCRBench) |
| OCRBench v2 | NeurIPS 2025 Datasets and Benchmarks；双语视觉文字定位、识别与推理 | 重点检查文字能力；英中覆盖不能代表日文动画硬字幕和跨帧对齐全部过关。[论文](https://proceedings.nips.cc/paper_files/paper/2025/hash/8c2e6bb15be1894b8fb4e0f9bcad1739-Abstract-Datasets_and_Benchmarks_Track.html)、[代码/数据](https://github.com/Yuliang-Liu/MultimodalOCR) |
| Video-MME | CVPR 2025；不同长度和领域的视频理解 | 作为通用视频研究对照；要明确字幕等辅助输入及采样协议，数据用途遵循官方仅学术研究的限制。[官方仓库](https://github.com/MME-Benchmarks/Video-MME) |
| MotionBench | CVPR 2025；细粒度动作、动作顺序、运动物体、重复次数和镜头运动 | 检查多帧动作与顺序理解；0.5 FPS 可能丢失证据，生产采样得分应单独标注。[项目页](https://motion-bench.github.io/)、[论文](https://openaccess.thecvf.com/content/CVPR2025/papers/Hong_MotionBench_Benchmarking_and_Improving_Fine-grained_Video_Motion_Understanding_for_Vision_CVPR_2025_paper.pdf) |
| HallusionBench | CVPR 2024；语言幻觉与视觉错觉诊断 | 检查是否被先验带偏；yes/no 评测不能替代自由视觉描述的事实核验。[官方仓库](https://github.com/tianyi-lab/HallusionBench) |

首轮可从 OCRBench v1 的固定子集与少量项目验收开始；OCRBench v2、Video-MME、MotionBench、HallusionBench 根据后续错误类型和评测预算补充，不要求训练前全部跑完。2026 年已有 [Video-MME-v2](https://github.com/MME-Benchmarks/Video-MME-v2)，可作为后续补充；v1/v2 的数据和评分应分别记录。

若只跑固定子集，报告必须标明样本清单与数量，不能将子集结果称为官方完整分数。正式与论文/榜单对照时，应采用原评测协议；采用我们的 15 帧生产采样时，应另报“生产输入协议”结果。

## 5.2 评测工具

可以使用 lmms-eval 统一数据和评分流程，维护者的模型列表已有 `qwen3_vl`。先确认实际版本中所需任务及 backend 支持，再做小样本加载检查。[lmms-eval 任务与模型列表](https://github.com/EvolvingLMMs-Lab/lmms-eval/blob/main/docs/advanced/current_tasks.md)。

云端 HF 基线可用原生 Qwen3-VL 适配；MLX/Ollama 可通过合适的接口或自定义适配接入，但图片编码、帧顺序和视频采样必须核对，不能默认兼容接口就等价于原生输入。

Qwen 技术报告提供公开能力对照，但其原始模型、输入处理与生成配置并不等于我们的 Q4 多帧路径，不把厂家分数直接登记成本机得分。[Qwen3-VL 技术报告](https://arxiv.org/abs/2511.21631)。

## 5.3 Seekino 人工标准答案集

目前核对的公开评测没有完整覆盖“动画双路字幕 + 匿名人物 + 视觉事实 + Frame 引用 + 后续 Timeline”的全部要求，因此需要独立的项目评测。每条正确事实与字幕都绑定图片编号，允许标注未知或不可判定。

| 指标 | 计算或核验方式 |
| --- | --- |
| 字幕字错率 CER | 对人工文本计算编辑距离；说明 Unicode、空白、标点的归一规则，保留原文结果 |
| 字幕行准确率与召回率 | 区分漏行、错行与重复行；同一帧上下两路字幕分别核验 |
| Frame 对齐 | 正确字幕和事实是否出现在对应图片编号，是否被复制到其他帧 |
| 视觉事实准确率与召回率 | 按可核验的原子事实人工匹配，区分遗漏和无依据新增 |
| 说话者归因质量 | 明确可判定样本的正确率；同时统计错误归因与未知输出，防止全填未知 |
| 重复与覆盖 | 重复事实 surplus，以及画面/字幕真实变化的覆盖率；不能只数 observation 总量 |
| JSON 与引用合法性 | Schema、图片编号范围、必需字段；合法结构不代表事实正确 |
| 速度与内存 | 同输入下的总耗时、输出长度、峰值内存，以及实际部署版本的稳定性 |

候选模型先在相同输入条件下比较，要求 OCR、视觉事实与错误归因有明确改善，重要召回项不退化。产品验收阈值在标注规范和基线统计完成后确定，不能把任意设定的百分比说成行业标准。

视觉抽取通过后，还需检验后续 Timeline 是否保留字幕、是否错误归一人物，以及查询召回的收益；整条链路的结果不能全部归因于 Qwen。本项目已有 [recall eval](../../evals/recall/recall_eval.py)，可在固定检索配置下复用，补充检索相关的标准答案。

## 5.4 比较时固定的变量

保留未训练高精度 Qwen、未训练本地量化 Qwen、训练后模型、最终部署模型和经过复核的教师结果。固定样本、图片内容与顺序、分辨率、Prompt、Schema、解码参数、输出上限及去重规则，记录权重与框架版本。

跨运行时差异可能来自量化、processor、模板或推理实现，不能直接全部归因于量化或训练。公开测试集不参与领域训练；项目测试集也不反复用于挑选训练配置，应保留最终独立测试。

# 六、首个实验与待验证事项

第一阶段完成简要标注规范、20–50 组早期验收与基线统计，后续扩到 100–200 组固定评测；第二阶段用几十至几百组训练数据验证训练和 adapter 加载；第三阶段再扩至 1,000–3,000 组做完整 SFT，验证未训练片段和本地部署版本。

2026-09-15 用户明确正式训练采用租卡；具体卡型仍待选择。云端从 4-bit QLoRA、冻结视觉模块、batch=1 开始，对候选设备测真实 15 帧输入的峰值内存与完整前后向耗时，再决定完整训练资源。4090 的适用条件见第 2.3 节，48–80GB 是保留更多余量的选型。本机用于评测与部署回归，也保留本地训练路线的可行性记录。SFT 的问题分布确认后，再决定是否值得增加视觉模块训练、DPO 或 GRPO。

# 七、微调的完整流程与 Seekino 工程分工

## 7.1 首轮具体训练什么

首轮训练任务是“动画画面证据提取”：给定有序帧与取证指令，生成 `NeutralVisualEvidence`。目标覆盖漏字幕、字幕串帧、乐器/动作错认、重复观察和无依据归因等已发现问题。这个任务已有明确的输入、输出与故障样本，适合用来验证领域微调是否有价值。

截至本次核对，[配置](../../config.yaml)使用 0.5 FPS、30 秒一组、每组最多 15 帧、抽帧最大高度 720。训练样本首先复用这个输入协议；实际视觉 token 数仍由训练 processor 决定，需要实测。训练标签使用 Frame 编号，Engine 负责映射时间。

云端教师负责生成标注草稿；租用 GPU 上的 Qwen 负责前向、反向和参数更新。教师 API 不需要开放权重；只调用教师 API 生成答案，还没有发生 Qwen 的训练。

## 7.2 从数据到部署的步骤

| 步骤 | 实际工作 | 本阶段产物与通过条件 |
| --- | --- | --- |
| 1. 固定任务与基线 | 固定 Prompt、Schema、帧采样、解码参数，运行原始 Qwen | 原始输出、耗时、内存和错误分类；后续比较采用相同条件 |
| 2. 导出样本 | 从视频按生产协议抽帧，保存图片、顺序、来源集数、时间映射和输入参数 | 可重放的样本目录与 manifest；当前 parser 的临时抽帧会被清理，训练需要另行持久保存 |
| 3. 教师标注与复核 | 教师看同一批图片，生成匿名视觉 JSON；检查结构、引用并人工复核 | 可作为正确答案的视觉证据；不直接把含音轨、人物资料和剧情推断的完整 Timeline 当标签 |
| 4. 划分与转换数据 | 按集或作品隔离训练、验证、测试；转换为训练框架格式 | `train.jsonl`、`val.jsonl`、`test.jsonl` 与划分清单；相邻近重复帧不跨集合 |
| 5. 短跑验证 | 加载 HF 权重和 processor，添加语言部分 LoRA，验证完整前后向、保存和重载 | 没有图片/答案截断；答案损失正常；adapter 重载生效；真实长样本显存与耗时实测 |
| 6. 正式 SFT | 批量训练，记录验证结果与 checkpoint，根据验证集选择模型 | adapter、基础模型 revision、训练配置、数据版本、日志和验证生成结果 |
| 7. 独立验收 | 在固定测试集与公开评测上比较，再检验量化/部署格式 | OCR、事实、Frame 对齐、错误归因、覆盖、速度和内存的对照报告 |
| 8. 接回 Seekino | 增加模型选择与调用路径，运行 Timeline、建库与检索回归 | 真实部署版本的端到端结果；保留模型与解析策略版本，支持切回已验证版本 |

验证集用于训练期间选模型和配置，测试集用于独立报告。不要反复依据测试集改参数后，仍把它作为最终独立测试。

## 7.3 SFT 内部究竟做了什么

一条训练样本包含图片、用户指令和经过复核的助手答案。processor 把图片变成模型输入，并用模型对应的聊天模板编码文本；训练时把正确答案的前序 token 提供给模型，让它预测下一个 token，计算助手答案部分的交叉熵损失，再反向传播与更新参数。

LoRA SFT 首轮只更新选定的低秩参数。基础权重冻结，视觉编码器与对齐模块也先冻结；量化 LoRA 再通过量化基础权重降低内存需求。LoRA 是参数更新方式，SFT 是训练目标，两者可以组合。框架负责梯度累积、优化器、调度、保存和恢复。

概念上，一个不含梯度累积的更新步骤如下；`batch` 已包含正确的视觉输入和只覆盖答案的 labels。这不是完整训练脚本：

```python
optimizer.zero_grad()
loss = model(**batch).loss
loss.backward()
optimizer.step()
```

普通 SFT 不需要为每条训练样本先自由生成完整答案再打分。训练/验证 loss 降低也不能代替自由生成时的事实和 OCR 验收。

现成工具可使用 [Qwen 官方训练框架](https://github.com/QwenLM/Qwen3-VL/blob/main/qwen-vl-finetune/README.md)或 [ms-swift Qwen3-VL 路线](https://swift.readthedocs.io/en/latest/BestPractices/Qwen3-VL-Best-Practice.html)。应固定环境版本、检查模板与可训练参数列表；直接复制文档中的 4B、4096 长度演示，不能验证我们的 8B、多图负载。

下面的文件名是拟议分工，尚未创建或实现。训练可放在独立目录或环境，复用 Seekino 的输入和输出契约。

| 拟议文件/模块 | 我们负责的代码 | 可复用部分 |

工程难点主要在数据质量、预处理一致性、训练配置与效果定位。使用现成 trainer 仍需要理解哪些参数在训练、哪些 token 参与 loss、显存在哪里消耗，以及模型是否只记住训练片段。

## 7.5 一条数据怎样表示

采用 ms-swift 时，多图样本可以用 `images` 和 `messages` 表示；每个 `<image>` 与图片列表中的一张图片按顺序对应。下面只是格式示例，不包含真实标注；`verified_evidence` 是人工复核后的答案，`frame_paths` 是导出图片的路径列表：

```python
import json

from engine.parse.prompts import build_neutral_visual_prompt
from engine.parse.schemas import NeutralVisualEvidence

answer = NeutralVisualEvidence.model_validate(verified_evidence)
frame_labels = "\n".join(
    f"Frame {index}/{len(frame_paths)}: <image>"
    for index in range(1, len(frame_paths) + 1)
)
record = {
    "images": frame_paths,
    "messages": [
        {
            "role": "user",
            "content": frame_labels
            + "\n\n"
            + build_neutral_visual_prompt(len(frame_paths))
            + "\n\nJSON Schema:\n"
            + json.dumps(NeutralVisualEvidence.model_json_schema(), ensure_ascii=False),
        },
        {"role": "assistant", "content": answer.model_dump_json()},
    ],
}
# 导出时逐条 json.dumps(record, ensure_ascii=False) 写成 JSONL。
```

正式导出还需检查非空图片列表、文件可读、Frame 引用范围、数据泄漏、标注审核状态和输入长度。`model_validate` 通过只代表结构有效，不代表看图事实正确。Schema 提示或结构化生成机制应在训练与部署时保持明确、可核对的对应。

这个格式来自 [ms-swift 自定义数据说明](https://swift.readthedocs.io/en/latest/Customization/Custom-dataset.html)。Qwen 官方框架使用 `image` 与 `conversations` 的格式，需要相应转换；不能把两种格式混用。

## 7.6 与现有链路的关系和接入边界

目标部署位置是分组视觉证据阶段：

```text
视频片段 → 有序帧 → 微调后的 Qwen → NeutralVisualEvidence
                                   ↓
Lite ASR + Frame 时间映射 + 去重 + 文本 refiner
                                   ↓
                               Timeline
                                   ↓
                      文本建库与时间证据检索
```

更准确的字幕、动作和物体描述可能改善 Timeline 及文本召回，收益需要固定检索配置、重新建立对应文本索引后验证。视频向量由独立的 Embedding 模型产生，视觉 SFT 与向量模型训练是不同阶段。

当前 [DeepSeekFallbackVideoChunkParser](../../engine/parse/video_chunk_parse.py)要求 vision/refiner 的 provider 都是 `deepseek`；[配置模型](../../gateway/config.py)与 [runtime](../../engine/parse/runtime.py)也直接构造 DeepSeek。引入 Qwen 需要增加模型选择、构造或适配，并调整 parser 的 provider 限定。分别记录视觉模型与整理模型的真实版本，复核 checkpoint 复用条件，避免把旧结果误当训练后结果。

训练后的 HF/PEFT 模型先加载基础模型与 adapter 验收，再评估适配器合并、GGUF、projector、模板及本地运行时。只有最终运行时确实加载训练产物，且相同测试输入通过，才算完成部署验证。

语言部分 LoRA 可以尝试改善输出习惯和领域描述；若错误来自低分辨率、小字不可读或视觉特征辨别能力，需要先分析错误来源，再单独验证分辨率调整或视觉模块训练。微调不能补回未抽到的瞬间和未输入的音频。

## 7.7 如果后续做 RL，多出什么

DPO 可以利用同一输入的较好/较差答案做偏好训练；GRPO 则让当前 Qwen 对同一输入生成多个候选，评分后用组内相对优势更新策略。现成 trainer 可以负责采样与策略损失，我们需要负责奖励、正确答案/偏好质量、评分审计和独立验收。[ms-swift GRPO 流程](https://swift.readthedocs.io/en/latest/Instruction/GRPO/GetStarted/GRPO.html)。

本项目的奖励要覆盖字幕、Frame 对齐、事实正确与变化覆盖，同时惩罚无依据新增和重复。只奖励 JSON 合法会忽略事实错误；只惩罚错误可能诱导全部填未知或少输出。自由视觉事实难以用简单字符串比较评分，教师裁判也要用人工样本校准。

vLLM 可用于加速 rollout 或提供推理服务，梯度更新由训练框架承担。GRPO 额外的候选生成、KV cache、评分与权重同步都需要独立测量，不能依据 SFT 短跑直接判断 RL 的资源和时长。

## 7.8 首个实验的完成标准

先用约 20–50 条核验样本检查数据编码、完整前后向、保存与 adapter 重载，这个阶段只证明训练管线可用。固定独立评测与基线后，再做百级试验并依据第 1.3 节扩到千级样本。所有样本规模都是实验规划，尚无本项目训练结果。

一次有意义的闭环需要同时留下：可重放的数据及划分、训练配置与日志、可加载的训练产物、未训练片段上的质量/性能对照，以及 Seekino Timeline 与检索的回归结果。是否继续训练、增加视觉模块或升级 RL，由错误分布和独立评测决定。
