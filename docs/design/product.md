# AniVAG 产品思路：本地优先的视频解析与可验证召回

> 状态：产品方向草案（2026-09-20）  
> 当前决策：首发对标“轻量、本地可运行的视频解析与证据召回项目”，以无登录 Local BYOK 作为完整开源核心；用户若不想配置模型，可选只托管模型调用的 Managed 服务；需要后台持续解析、云存储和跨端使用时，再升级到完整 AniVAG Cloud。三种形态共用同一套解析、检索与证据模型；不建设跨用户的公共视频搜索或内容库。未来以同一核心向网盘、NAS、对象存储和视频平台提供 Partner API。

## 一句话定位

**AniVAG 是一个轻量、本地优先的视频理解与证据召回引擎：它将用户拥有或获授权的视频，转成只属于该用户或团队、可自然语言检索、可定位到具体时间证据的视频知识库。**

它不是一个“能存任意文件的通用网盘”，也不是一个“全网动画 / 影视搜索站”。它的差异是：视频一旦进入资料库，用户可以用模糊的自然语言描述找回对应的剧集、时间点、画面、对白和证据片段。

示例：

- “惊世一跪是什么？” → 第几集、起止时间、关键帧与对白证据；
- “老师解释二次函数单调性的那段” → 课程视频的精确片段；
- “主角第一次决定离队的场景” → 具体剧集和可跳转位置。

## 首发对标：轻量的本地解析项目

AniVAG 首先不与百度网盘、夸克网盘或云厂商竞争存储容量、带宽和通用云产品矩阵，而是提供一个普通开发者和个人用户能在自己的电脑上完整跑起来的视频解析、索引与检索产品。大厂提供的是平台级视频 AI 能力；AniVAG 提供的是从导入到证据片段召回的轻量成品。

这里的“轻量”描述的是部署、数据移动和使用门槛，而不是承诺视频理解本身不消耗计算资源：

- 不注册、不登录即可开始使用；
- 原视频原地读取，不为了使用 AniVAG 再复制或上传一份完整视频；
- 本地保存资料库、索引、时间轴、证据与检索历史；
- 用户通过一个经过验证的 `ModelProfile` 配置模型，而不是理解整条内部流水线；
- 优先提供桌面安装包或单命令启动，压缩从下载到第一次可信召回的时间；
- 模型、存储和索引实现均可替换，核心工作流不绑定某一家云厂商。

“轻量本地”不等于“完全离线”“无需模型费用”或“任意消费级设备都能即时解析长视频”。是否有数据离开设备取决于用户选择本地模型、第三方 BYOK 模型还是 AniVAG 托管模型，产品必须准确展示实际数据路径。

产品发布机制参考 [cmux](https://github.com/manaflow-ai/cmux) 的 local-first 路径，而不是照搬其具体功能：本地开源核心必须独立、完整、长期可用；云服务不负责解锁一个被人为阉割的本地版，而是为不想配置、希望关机后继续处理或需要跨端访问的用户出售模型、算力、存储和运维便利。

## 已确定的产品边界

### 私有，而不是跨用户内容平台

每个工作区的数据严格隔离。所有 Video、VideoChunk、ASR、关键帧、向量、检索历史和 Agent 产物都归属到 `workspace_id` 与 `library_id`。

下列能力不做，也不为以后预留暗门：

- 全站视频搜索、跨工作区召回、跨用户相似视频推荐；
- 热门内容、公共片段页、公共视频目录、榜单或发现页；
- 将一个用户的视频解析结果直接复用于其他用户；
- 将用户视频、字幕、帧图或检索记录用于训练、推荐或回答其他用户的问题。

授权协作是工作区内的显式成员关系，而非公开视频传播。若未来需要分享，采用可撤销、限时、最小权限和可审计的私有链接。

### 本地优先、按需托管的产品主轴

AniVAG 的 Local、Managed 与 Cloud 不是“免费残缺版 / 付费完整版”，而是满足不同数据控制和便利性需求的同一产品。Local 把控制权交给用户；Managed 只替用户解决模型配置和额度；Cloud 再提供存储、持续运行和跨端体验。核心解析、检索和证据结构保持一致。

| 能力 | AniVAG Local / BYOK | AniVAG Managed | AniVAG Cloud | 企业 BYOS（后续） |
| --- | --- | --- | --- | --- |
| 身份 | 不注册，使用 `local-default` 工作区 | 登录以使用官方额度 | 账号与私有 Workspace | 企业成员、服务账号与 RBAC |
| 原视频 | 留在用户设备，原地读取 | 留在用户设备，不上传完整原片 | 上传或显式导入用户专属云空间 | 留在客户 OSS / S3 / NAS |
| 模型凭证 | 用户配置自己的 API Key 或本地模型 | AniVAG 托管模型凭证 | AniVAG 托管模型凭证 | AniVAG 托管或客户自带 Key |
| 模型费用 | 用户直接向模型供应商承担 | 套餐额度或按量计费 | 套餐额度或按量计费 | 合同额度、BYOK 或按量计费 |
| 解析执行 | 本地 Worker | 本地 Worker 抽取必要输入，调用托管模型 | 云端后台 Worker，关机后继续 | 云端或客户环境 Worker |
| 数据与索引 | 本地数据库、向量库和 Artifact Store | 默认仍保存在本地 | 云端多租户隔离存储 | 客户存储边界内或专属实例 |
| 核心价值 | 无需上传原片、速度快、控制权高 | 不配置 API 与模型，同时保留本地原片 | 免配置、跨端、后台托管、备份与协作 | 数据控制、治理、审计与 SLA |

对外承诺可以表述为：

> 不登录，也能用自己的模型在本地建立私人视频知识库；不想配置 API，可以只使用 AniVAG 托管模型；需要关机后继续解析、云存储和跨端访问时，再把选定的资料库迁移到 AniVAG Cloud。

Managed 模式不上传完整原视频，但本地 Runtime 会按解析任务抽取必要的帧图、视频窗口、音频、字幕或上下文并发送到 AniVAG 模型网关。其隐私披露标准与第三方 BYOK 相同，不能把“原片未上传”宣传成“任何数据都没有离开设备”。

云端执行解析时，Worker 在必要范围内读取明文视频；因此不能同时承诺“云端理解视频”与“平台永远无法接触明文”。对于高隐私用户保留全本地模式；对于企业优先提供 BYOS 和临时授权读取。

### 本地 BYOK 的模型能力契约

本地版不宣传“任意 API Key 都能跑”。一个完整解析链可能分别需要视频 / 多图理解、ASR、Embedding、结构化输出或工具调用等能力；模型名称相似不代表输入能力、上下文限制和向量维度兼容。

产品以 `ModelProfile` 表达一套经过校验的模型方案：

```text
ModelProfile
├─ VideoNativeAdapter 或 VisionFrameAdapter
├─ ASRAdapter
├─ EmbeddingAdapter
└─ AgentModelAdapter
```

- 原生支持视频的模型可以直接接收受控的视频窗口；
- 只能识图的视觉接口由 AniVAG 按时间抽帧，以带时间位置的图片组调用；
- ASR、Embedding 和 Agent 可以使用不同供应商或模型；
- 高级用户可分别配置 Endpoint、模型名和 API Key，但每个角色都必须通过最小兼容性检查；
- 开始长视频解析前先验证鉴权、模型存在性、输入模态、结构化输出、Embedding 维度和最小请求，并展示预计成本。

API Key 只保存在本地受保护配置中，不因用户登录以外的原因上传 AniVAG 云端。浏览器页面不直接持久化长期密钥，由本地 Runtime 负责读取和调用。

### 本地模式的隐私说明

“本地运行”不等于“所有内容完全离线”。当用户选择第三方云模型时，完整原视频不上传 AniVAG 云端，但完成解析所需的帧图、视频窗口、音频、字幕、视觉描述或 Agent 上下文可能发送给用户配置的模型供应商，并适用该供应商的条款和隐私政策。产品必须在模型配置和首次解析前明确展示这一事实。

完全离线模型可以作为后续 Profile，但第一版不承诺兼容任意本地模型或消费级硬件。

### 本地与云端可迁移，但不自动同步

用户登录后可以显式选择将某个本地资料库迁移到云端，并逐项决定是否上传原视频、解析结果、背景资料、收藏、笔记和对话记录。登录本身不得触发后台自动上传。

云端资料库也应提供可移植的导出能力。Local、Managed 与 Cloud 三种形态使用同一套 Library、Video、Segment、Evidence 和清单格式，避免本地版与云端版演化成两个不兼容产品。

### 不把自己做成通用网盘

第一阶段只服务视频及其派生产物（字幕、帧图、时间证据、向量、笔记和检索结果），不进入任意文件夹、家庭备份、照片同步或大容量冷存储竞争。

对外称为“私有视频资产库”或“视频知识库”，而不是“免费云盘”。用户购买的是视频理解、检索、定位和协作能力，而不仅仅是 GB 数。

## 核心用户与最先验证的场景

### M1：动画 / 长视频中的事件级定位

用户导入若干集动画，用自然语言找回名场面、人物关系、动作、台词或情绪变化；结果必须给出剧集、时间戳、关键帧和文本证据，并可跳转播放。

### 可扩展的高价值场景

1. **备考与课程复习**：用户导入自己有权使用的课程视频，用“老师讲极值判定的例子”“政治那段关于某概念的解释”直接回到片段，而不是在长视频进度条上盲找。
2. **个人创作素材库**：创作者找回自己拍摄的镜头、采访、素材和口播段落。
3. **团队视频资产库**：课程、培训、会议、售前演示、采访和品牌素材的私有检索。

“考研视频检索”可以成为一个明确的传播场景，但广告和落地页必须表述为：**整理并检索你拥有访问权或获授权的课程视频**。不能把未经授权的课程、影视资源当作平台供给或卖点。

## 用户体验闭环

```text
选择运行方式
  ├─ Local：不登录，本地视频 + 我的 ModelProfile
  ├─ Managed：本地视频 + AniVAG 托管模型
  └─ Cloud：私人云空间 + AniVAG 托管模型
        ↓
导入我拥有 / 获授权的视频
        ↓
异步解析：切片、ASR、画面理解、事件与向量索引
        ↓
自然语言提问
        ↓
只在当前 workspace + library 范围内召回
        ↓
返回：视频 / 集数、时间范围、关键帧、字幕与解释
        ↓
跳转播放、收藏、添加笔记或与受邀成员协作
```

检索结果的最小承诺不是“模型给出一个答案”，而是“答案可回到视频证据验证”。这也是 AniVAG 与通用聊天、字幕搜索和普通网盘的根本区别。

## 竞争壁垒假设

### 竞争前提：通用能力会被快速商品化

不要把“网盘 + AI 视频总结 / 字幕 / 语义搜索”当作独占创意。大型网盘已经面向网课推广视频总结、字幕等能力；云厂商也已经提供视频切割、摘要、多模态向量化和片段检索的基础设施。AniVAG 不应与它们竞争容量、带宽、通用文件管理或“是否有一个 AI 总结按钮”。

我们的机会在于把基础能力做成一个可验证、可连续使用的垂直工作流。网盘厂商容易复制“上传视频后可以问几句”的表层功能；AniVAG 的护城河不能建立在上传按钮、对象存储或单次调用某个模型上，而要建立在以下复合能力上：

1. **可靠的时间证据链**：把语义意图稳定映射到可播放的秒级片段，并能交代命中的文字、画面与事件依据。
2. **长视频、多模态检索质量**：对白、画面、角色、动作、情绪和领域背景共同参与召回；持续积累评测集、失败样本和重排策略。
3. **领域工作流**：动画的角色 / 世界观背景，备考的课程章节、错题与复习计划，创作者的素材标签与剪辑流程。不同垂直领域应有不同的“找回后下一步”。
4. **私有资料库的信任与迁移成本**：稳定的资料库结构、笔记、收藏、个人词汇、检索历史、团队协作和跨设备连续性。一旦用户长期使用，离开意味着不仅搬走视频，还要丢失围绕视频积累的可用知识。
5. **本地—云端一体化体验**：本地速度与隐私、云端协作与后台算力、BYOS 的企业控制权，使用同一资料库与证据模型。大网盘很容易做云存储，小工具很容易做本地解析，但三者一致较难。
6. **可量化的质量与成本数据**：真实视频任务的召回率、证据正确率、解析时长、每小时视频成本和失败恢复率；这些会成为模型、提示词、切片策略和产品定价的长期反馈飞轮。

严格的私有隔离意味着不能依赖“所有用户上传的视频汇成一个公共数据飞轮”。用户私有数据带来的主要是信任和迁移成本，而不是可默认挖掘的网络效应。模型与召回质量的共同改进应来自用户明确同意的匿名质量信号、授权评测集、合作内容方和内部标注，而不是挪用用户视频内容。

### 最初的市场切口：把视频找回变成学习闭环

“考研用户在网盘里看长视频”是一个有效洞察，但不是足够的定位；单纯宣称“网课 AI 总结”会正面撞上通用网盘。

AniVAG 对备考用户的完整承诺应是：

```text
我的已购 / 获授权课程视频
  → 课程章节与知识点地图
  → 用自然语言找到老师真正讲解的证据片段
  → 生成笔记、错题关联与复习卡
  → 在遗忘前回到原讲解，而不是只看一段脱离上下文的 AI 摘要
```

可测试的对外文案：

> 不要在 80 小时网课里拖进度条。把你有权观看的课程变成可追问、能回到老师原话与原板书的私人复习库。

它强调“回到原始证据”和“完成复习动作”，而不是暗示平台提供或分发课程资源。第一批付费验证可优先面向购买了成体系课程、复习频率高、且有明确时间损失的考试人群；长期更稳的分发是与讲师、机构或拥有课程版权的内容方合作，而不是围绕来源不明的网盘资源获客。

## 开源与商业边界

### 开源不是放弃护城河

AniVAG 的代码可以是获客、信任和生态入口，尤其适合本地优先和隐私敏感的产品；它不应是唯一的可售卖物。即使竞争者能读到核心代码，仍需要解决真实用户的资料库迁移、模型质量、运维、客户支持、内容合作与持续迭代。

“短时间形成使用惯性”是重要结果，但不能是唯一策略；大网盘本身拥有更大的预装量、用户基数和分发能力。界面更轻更简洁是最好的切入体验，却很容易被复制。真正需要积累的是：用户每次找回、标注、复习和协作后沉淀的私人工作流，以及我们不断提升的证据级检索质量。

开源发布不需要等待完整云服务上线。更合理的顺序是：先发布一个能独立完成“导入 → 解析 → 索引 → 查询 → 回到证据片段”的 Local 版本，同时公开 Managed / Cloud 路线；再根据真实用户在模型配置、持续运行和跨端访问上的阻力决定云服务投入。这样开源核心负责建立品类认知、信任和开发者生态，云服务负责扩大非开发者人群，而不是在产品尚未验证时先承担通用网盘的成本和合规复杂度。

### 建议的产品分层

| 层级 | 交付内容 | 开放原则 | 商业目的 |
| --- | --- | --- | --- |
| Community / Local BYOK | 无登录本地导入、兼容 ModelProfile、完整核心解析与检索、可移植资料库格式 | 可公开、可自部署；用户承担自己的模型费用 | 建立信任、传播与开发者生态 |
| AniVAG Managed | 原视频仍在本地，由官方提供经过验证的模型、额度、路由、限流与失败重试 | 持续运营的模型服务；准确披露派生输入的数据路径 | 为不想申请和配置多个模型 API 的用户提供最短付费升级路径 |
| AniVAG Cloud | 登录后的托管存储、托管模型、跨端同步、后台 Worker、任务可观测性、备份、配额、支付与支持 | 持续运营的完整云服务 | 为希望关机后继续处理、跨端访问和协作的个人与团队提供省心体验 |
| Learning Pro | 知识点地图、错题 / 笔记关联、复习计划与学习分析 | 可先作为云端能力；是否开放取决于验证结果 | 以学习效果而非存储容量收费 |
| Enterprise / BYOS | SSO、RBAC、审计、保留策略、客户自有存储、SLA、部署支持 | 专有模块或商业授权 | 企业收入与高信任交付 |
| Partner API | 面向网盘、NAS、对象存储和视频平台的视频解析与证据召回接口 | 使用同一 Core 的平台服务 | 让第三方产品接入 AniVAG，而非与所有存储产品正面竞争 |

不必为了“有护城河”而把所有算法神秘化。优先开放可验证的本地能力、数据格式和插件接口；把持续运营才有价值的云端控制面、计费、协作、企业治理、模型运维与支持作为服务交付。私有检索质量中可复用但不必公开的资产包括：授权评测集、标注规范、错误样本分析、重排策略、模型路由策略与垂直知识本体。

### 许可证与仓库边界是待决策项

“代码公开”与“开源许可”不是同一件事。正式选择许可证前，需要盘点所有贡献者的权利和上游依赖的许可证；禁止云厂商托管的 source-available / 商业限制许可通常不属于传统开源，也会影响社区接受度与依赖兼容性。若选择真正的宽松开源许可，就应接受别人可以复用代码，并将护城河建立在服务、质量、品牌、数据治理和分发上。

将来若要采用 open-core，仓库应尽早拆分为 `anivag-core`（本地可运行的核心）和 `anivag-cloud`（托管控制面与商业服务），而不是在同一个公开仓库里临时隐藏文件。对已经按某一开放许可发布的代码，不能事后收回既有使用者已经获得的许可；贡献者代码还可能需要 CLA / 商业贡献协议才能进行双重授权。

## 合规与信任原则

AniVAG 不将“用户上传”误解为平台没有责任。产品必须提供内容权属确认、投诉受理、下架与删除、访问控制、保留期限和审计能力；具体上线形态需要在进入公有云托管前完成针对性法律合规评估。

产品级原则：

- 用户声明其拥有内容或具有处理所需授权；
- 默认私有，禁止跨用户发现和复用；
- 原视频访问使用身份鉴别和短期授权，不提供公开目录；
- 临时转码文件、音频与帧图有明确的自动清理策略；
- 用户可删除资料库，删除覆盖原片和全部派生产物；
- 不将私有内容默认为模型训练数据；
- 对权利人有效通知及时受理与处理，并保留必要审计记录。

## 分阶段路线

### Phase 1：本地单用户闭环（当前）

- 本地导入动画视频；
- 原视频原地读取，不为 AniVAG 再缓存一份完整副本；
- 无需登录，使用 `local-default` 工作区；
- 用当前已验证的模型组合形成第一个正式 `ModelProfile`；
- API Key 由本地 Runtime 读取，提供配置检查和最小请求验证；
- 对只能识图的模型保留带时间位置的抽帧适配路径；
- 可见、可重试的解析任务；
- ASR、画面理解、事件索引和向量检索；
- 查询返回时间证据并跳转播放；
- 明确展示第三方模型会接收哪些帧、音频或文本输入。

目标是先证明：**用户能不能稳定地用一句模糊描述找回正确片段。**

### Phase 2：私有资料库模型

- 将 `Workspace → Library → Video → Segment → Evidence` 固化为所有数据和查询的必经归属链；
- 存储层抽象为本地 Artifact Store 与对象存储实现；
- workspace / library 作用域进入 SQL、向量集合（或 payload filter）、媒体读取和缓存键；
- 完成资料库删除、派生产物清理和基本审计。

此阶段无需先做完整账户体系，但不再允许全局资源和无作用域的检索接口。

### Phase 3：托管模型与受控云端

先验证不托管完整原片的 Managed 服务，再扩展到完整 Cloud，避免一开始同时承担模型平台、视频网盘和多租户协作三套复杂度。

**Phase 3A：AniVAG Managed**

- 账号、套餐额度、支付与用量明细；
- 官方维护并持续验证的托管 `ModelProfile`；
- 本地 Runtime 负责切片和最小必要输入抽取，完整原片默认不上传；
- 模型网关负责路由、限流、可靠重试、成本控制和故障切换；
- 在任务开始前说明将发送的数据类型、模型供应商和预计费用。

**Phase 3B：AniVAG Cloud**

- 私有 Workspace、成员和最小 RBAC；
- 私有视频上传或从获授权存储显式导入、断点续传、配额与生命周期；
- 云端后台任务队列、可靠重试、通知与跨端状态；
- 私有播放、私有检索、收藏 / 笔记 / 协作；
- 用户显式发起的本地资料库迁移与云端导出；
- 权属声明、投诉和下架流程。

### Phase 4：垂直工作流与商业化

- 考研 / 课程：章节、知识点、错题回看、复习计划；
- 创作者：素材语义找回、粗剪候选、镜头笔记；
- 团队：自有内容资产库、权限、BYOS、审计与成本控制；
- 商业模式优先按“理解与检索价值”收费，而不是与通用网盘打低价存储战。

### Phase 5：Partner API 与存储连接器

- 将原视频来源抽象为 Local、S3 / OSS / COS、WebDAV、NAS 和获授权的第三方网盘连接器；
- 对外提供异步导入、任务状态、检索、Evidence 与回调 API；
- 官方个人资料库作为参考客户端，和合作方使用同一核心能力；
- 计费围绕解析视频小时数、查询量、派生产物存储和服务等级，而不是通用网盘容量。

## 成功指标

产品的核心指标不是上传量，而是“视频重新变得可用”的频率与质量：

- 首次导入后完成一次有效检索的比例；
- 本地用户完成 ModelProfile 配置与最小兼容性检查的比例；
- 从下载到第一次成功召回的时间；
- 查询到首次可信片段的时间；
- 用户点击 / 播放 / 收藏结果后的确认率；
- 标注集上的 Recall@K、时间定位误差、证据正确率；
- 每小时视频的解析成本、成功率和重试恢复率；
- 私有资料库的周留存、持续导入率与跨端使用率；
- Local 用户主动升级 Managed 的比例，以及托管模型调用后的持续使用率；
- Local / Managed 用户主动迁移至 Cloud 的比例，以及迁移后的持续使用率。

## 暂不做的事

- 公共动画 / 影视 / 课程资源库；
- 跨用户召回、跨用户去重复用、热门推荐；
- 通用网盘功能全集；
- 以超低价存储容量为主要卖点；
- 为迫使登录而人为削弱本地核心检索能力；
- 登录后未经用户明确选择便自动上传本地视频、索引或历史；
- 宣称任意模型、任意 API Key 均兼容；
- 在核心检索质量未经验证前，过早投入复杂的多租户、计费和大规模基础设施。

## 对外传播与架构展示原则

> 决策日期：2026-09-20  
> 当前结论：现有“私有视频库 → Parse Agent Graph → 多模态索引 → Retrieval Agent Graph → 可验证回答”的五列横向版式是正确的，应继续作为 README 首屏展示图。问题不在宏观架构排版，而在标题尺度、文字层级和内部实现细节被过度压缩。Architecture 章节仍可补充更完整的矢量系统图，但不能替换或否定首屏五列展示图。

### 已确认的问题：宏观版式正确，细节表达失真

此前横版草图的五列主链能够正确说明“私有视频经过解析和检索后返回时间证据”，暖白背景、森林绿、薄荷青、圆角卡片与 MyGO 画面构成的整体风格也应保留。与高密度系统图比较时，真正需要修正的是三个细节问题：

1. 标题和副标题占据过多首屏高度，模块标题与节点文字也整体偏大；
2. 字号、字重、图标和卡片边界接近同一视觉层级，面板、节点和注释缺少清楚的三级尺度；
3. 五列位置虽然正确，但 Parse 内部的条件回退、Context 演进、持久化控制，以及 Retrieval 内部的并行召回、融合与 Evaluator 循环没有充分展开，因此看起来像普通线性 RAG。

系统的工程难度不能靠增加大字、装饰或虚构 Agent 数量表达。读者对复杂度的判断主要来自真实存在的依赖、并行、顺序约束、条件分支、反馈循环、持久状态与最终汇聚关系。修图时必须保留原有五列外框及其宽度关系，只在各面板内部展开这些关系，并通过缩小标题、节点和注释建立层级。

### 两张图分别承担两种传播任务

#### 1. 产品价值图：用于 README 首屏与发布帖

产品价值图只回答三个问题：

- 用户放入什么：自己拥有或获授权的私有视频；
- AniVAG 做什么：解析、索引并通过自然语言召回；
- 用户得到什么：集数 / 视频、时间范围、关键帧、字幕与可跳转播放证据。

这张图允许出现一张输入缩略图和一张结果关键帧，但不用于证明内部架构复杂度，也不堆叠模型、存储和可靠性细节。

#### 2. 技术架构图：用于 Architecture 章节、技术文章与开发者传播

技术架构图必须从真实实现出发，至少明确四个平面：

1. **Offline Parse / Indexing Plane**：AnalysisWindow 规划、有界 ASR 预取、带 Context 依赖的顺序解析、主视频分析、明确 `ContentFilterError` 后的 fallback、事件整理与 Text / Vision Embedding；
2. **Data / Index Plane**：MySQL canonical facts、Artifact Store 中的原片 / VideoChunk / 帧图 / 解析产物，以及作为 derived index 的 Qdrant；
3. **Online Retrieval / Agent Plane**：Query、Transcript / Semantic / Visual 三路候选、加权 RRF、MySQL hydrate、Evaluator 循环、Chat 与 Evidence Output；
4. **Durable Execution / Control Plane**：Job Queue、Lease、Heartbeat、Fencing、Checkpoint、Retry / Reaper 与 IndexSyncIntent。

建议的宏观阅读顺序为：

```text
Offline Parse / Indexing
Private Video → Window Planner → ASR Prefetch + Ordered Parse
                                ├─ Primary Video Analysis
                                └─ ContentFilter Fallback
                              → Context Evolution → Text / Vision Embedding
                              → MySQL + Artifact Store + Qdrant

Online Retrieval / Agent
User Query → Query → Transcript / Semantic / Visual Retrieval → Weighted RRF + MySQL Hydrate
           → Evaluator ── insufficient ──→ Query
           → Chat → Episode + Timestamp + Keyframe + Playback

Durable Execution / Control
Job · Lease · Heartbeat · Fencing · Checkpoint · Retry · Reaper · IndexSync
```

该结构不是为了让图“显得难”，而是让真正决定正确性与可恢复性的机制可见。能由端点完全推断的无意义箭头标签应省略；协议、异步行为、条件和边界语义不能为了排版删除。

### Agent 与 Graph 的对外术语必须准确

- Retrieval 当前是显式 LangGraph：`Query / Evaluator` 可循环，证据充分后进入 `Chat → Output`；
- Parse 在产品拓扑上可以称为 `Parse Graph`，但当前执行形态更准确的说法是“包含智能模型节点的持久工作流图”：路由由代码、异常类型、状态机和检查点共同控制，尚未整理为单一显式 Graph 对象；
- 不把 Window Planner、Frame Sampler、Embedding、RRF、IndexSync、Lease 或 Retry 等确定性节点包装成 Agent；
- 不通过重复命名 Agent 制造复杂度，复杂度由真实的数据依赖、反馈回路和可靠性机制表达。

### 视觉系统决策

完整架构图采用可编辑的 SVG / HTML 或 Figma 矢量源，不再把生成式位图作为最终技术图。生成式图片只用于构图探索与气氛草稿。

当前不再继续探索新的第三种首屏构图，而是维护两张已经确认的基线图：一张高密度 `Detailed Architecture` 用于 Architecture 章节与技术传播；一张留白更充足的 `Overview Architecture` 用于 README 首屏和产品解释。两张图共享英文术语和事实边界，但不互相合并，也不要求同等信息密度。后续只在各自原始版式内修正语言、错误概念和细节层级。

- 标题只保留一行小型产品名 / 图名，不使用占据首屏的大宣传标题，默认不添加重复正文的副标题；
- 以白色或极浅中性背景为主，分区只使用低饱和浅色，正文使用深灰而不是大面积品牌绿；
- 通过位置、留白和一致的重复结构建立层级，不依赖粗边框和阴影；
- Section 标题、节点名、注释至少形成三级字号，节点保持紧凑；
- 英文图采用精致的 editorial humanist 字体系统：主标题使用比例优雅、笔画略带自然曲线与柔和端点的 display sans，Section 标题使用克制的小型大写，节点与微标签使用紧凑、直立、可读的现代 humanist sans。所谓“人手温度”只来自字形曲线，不使用任何可见的手写、马克笔、漫画、手账、刷字或儿童化字体；
- 连线和分区边框使用约 1–1.5 px 的稳定线宽，圆角保持克制；
- 主路径使用实线，条件 fallback 使用受控强调色，异步 / derived / control 关系使用虚线；
- MyGO 等示例帧只作为输入与 Evidence 的小型视觉锚点，不占据架构主体；
- 模型厂商标记只在澄清真实职责时使用，保持为小型中性徽标，不与 AniVAG 品牌并列、不暗示合作或背书；默认配置可以标注 `Ark / Doubao` 与 `DeepSeek`，同时通过 `ModelProfile / BYOK` 明确其可替换性；

- 首屏图只使用产品级能力名词，如 `Video Parse`、`Fallback Vision`、`Multimodal Index`、`Hybrid Recall`、`Evidence Review`。`ContentFilterError`、`IndexSyncIntent`、`Hydrate`、Lease、Fencing 等实现细节留给 Architecture 章节，不进入传播主图；
- 中间能力区采用开放画布和并列纵向主链，不再为每个阶段增加等高全幅外框；只保留左侧输入库、底部共享证据带和右侧结果栏等确有分组价值的容器，避免再次形成后台 Dashboard 观感；
- 图必须在常见桌面尺寸下可完整阅读，并同时导出可交互 HTML、SVG 与 README 使用的 PNG。

### 信息密度与“工程成熟感”

逻辑复杂度与视觉信息密度不是一回事。对标图未必拥有更复杂的运行机制，但它通过大量短节点、重复列结构、中间产物、箭头微标签、反馈回路和跨模块总线，形成了成熟系统已经被充分封装和命名的观感。AniVAG 的首屏图不能只把真实能力压缩成几个大盒子，也不能用大标题和高饱和色代替信息密度。

后续展示图遵循以下密度规则：

- 保留五段主流程和大模块的宽阔轮廓；中间三段可以拆成 Prepare / Primary / Fallback、Canonical / Artifact / Derived Index、Query / Search & Fusion / Decide & Answer，但小列只服务于真实分组，不能把每个名词都变成独立小卡片；
- 优先展示已有的中间状态与产物，如 AnalysisWindow、ContextSnapshot、VideoTimeline、Artifact、Embedding、Evidence Bundle 和 IndexSyncIntent；
- 在连线旁使用 `bounded`、`ordered`、`on content filter`、`facts`、`artifacts`、`upsert`、`hydrate`、`continue`、`complete` 等短标签说明关系语义；
- 用 Durable Execution / Control 总线连接 Job Queue、Lease、Heartbeat、Fencing、Checkpoint、Retry / Reaper 与 IndexSync；
- 目标是约 72%–80% 的中高信息密度：先保证 Parse、Index、Retrieval 三个主体具有大模块气场，再压缩模块内部的无效留白；不再追求 85%–90% 的满铺率；
- 同一概念不得为了“显得密”重复命名。模型调用、生成产物与存储结构必须分层表达，例如一个 `Doubao Multimodal Embedding` 模型节点输出 Qdrant 的 `text / vision` 两个 named vector，而不是上下重复绘制 `Text Embedding → Text Vector` 与 `Vision Embedding → Vision Vector` 四张近义卡片；
- `Event Filter` 不属于当前 Retrieval 实现，不得出现在图中。真实三路召回是 Transcript（ASR 字面匹配）、Semantic（文本向量）与 Visual（视频向量）；事件时间线属于被检索证据和生成上下文，不是独立过滤通道；
- 默认模型职责必须按实现标注：Ark / Doubao 负责 ASR、主视频分析和统一的文本 / 视频 Embedding；DeepSeek 负责 Query / Evaluator / Chat，并在主视频分析触发内容过滤时承担抽帧 fallback。DeepSeek 不属于 Embedding 路径；
- 缩略图尺寸下先看到五列轮廓、三大主体、fallback 分支、Evaluator 回路和控制总线；放大后再阅读节点名称、模型徽标与微标签。

### 真实性、版权与维护边界

- 图中只宣传当前已实现或明确标为规划中的能力，不将“本地优先”偷换成“完全离线”“任何数据都不会离开设备”或“原视频零复制已经完成”；
