现有 Gateway Chat 收集器已在内存拼接正文，完整响应交给业务校验后提交正式结果，并没有逐 token 保存模型正文。实际高频数据库访问来自另一条链路：`gateway/streaming/chat.py::_iter_chat_chunks.check` 每个 SSE 事件调用宿主 `check_control`；`server/service/video_parse.py` 注入 `manager.check_active`，后者调用 `_require_chunk_active` / `_require_interval_active`，最终进入 `VideoParseTaskQueue._heartbeat_child`，锁父记录再更新子任务租约。正文缓存、租约续期和正式结果提交必须区分。

期望是在生成中保留可诊断的模型正文草稿，同时让数据库访问不再与 SSE 事件数成正比。周期心跳及调用接纳、最终提交时的持久租约/版本校验仍需存在。用户指定按大小保存，不增加每 2 秒刷新的计时器。

本次交付：Parse 调用的正文草稿、按大小保存和退出刷新、逐 SSE 回调只检查本地取消状态、隔离测试与文档。独立保存 reasoning、工具参数、前端草稿预览、从草稿续写、旧任务回填、超时重试策略、调度顺序、并发配置和真实任务恢复不在范围内。草稿可以是不完整 JSON，不是可检索的业务事实。

| 因素与指标 | 基线及口径 | 验收目标 | 验证方式 |

# 3. 改造方案与建模

Server 持有草稿 buffer 和持久化策略；Gateway 只提供供应商无关的正文观察及调用生命周期；Engine / Agent 不直接写数据库。

1. 独立 `parse_model_output_draft` 表，一次 Gateway 调用一条记录，以 `call_id` 标识，带 `tenant_id`、所属 Parse task、阶段与执行/租约上下文。正文使用可容纳大输出的文本字段。没有指向父任务的外键或对父任务的查询/更新，避免通过外键检查重新取得父锁。数据库访问和读取均按所属租户和任务限制。
2. 每个调用使用简单内存正文列表/字符串与“上次保存之后新增字节数”。收到正文增量后追加并计数，累计达到 1,024 UTF-8 字节时保存累计草稿并清零待保存计数；不切碎单个 Unicode 字符，也不将每个 delta 单独插成一行。一次大 delta 只触发一次保存。数据库保存一条调用自身的最新快照，避免额外分片拼装协议。
3. 调用正常结束、失败、取消时保存余量和明确终态。`completed` 只表示模型调用结束，不能代表整个 Parse 完成或 JSON 业务校验通过；取消/失败保留已收到的前缀。没有收到正文的调用不创建空草稿。硬杀进程只能保留最后成功保存的前缀，不能保证未刷新的内存数据。
4. 复用 `observe_model_text` 和 Gateway usage observer 的 `on_start` / finish 生命周期，以调用 UUID 归属正文；通过现有 Parse owner scope 接入。补齐当前 HTTP Chat Completions / Responses 的通用正文观察（含非流式完成时一次交付，`before_completion=false`），不将延迟交付伪装成实时事件。不采集 prompt、密钥、reasoning 或工具参数；原生 SDK/CLI 未提供该观察的路径不宣称支持中途保存。
5. 草稿是辅助记录，保存失败记录带调用 ID 的告警，不中断原模型结果。失败后本调用停止中途重试，退出时可做一次最终尝试，避免故障期间退化为逐 token 重试数据库。保持现有输出预算和完整性校验，不引入无限后台队列。
6. Parse / Summarize 注入生成调用的高频 `check_control` 改为 `manager.raise_if_cancelled`；Canvas / 帧工具边界原有持久检查保留。调用接纳、独立周期 heartbeat 和正式提交仍做持久检查；通过 manager.cancel 关闭活动传输。草稿保存不承担续租。

选择独立调用快照的理由是隔离多个子任务写入且实现简单；代价是每次保存会重写该调用已生成的正文，后续只有测得单调用大文本写入成为瓶颈才考虑追加分片。仅节流续租不能满足新增草稿保存需求；继续写父 JSON 则会重新引入共享锁；按时间刷新与本次明确的按大小要求不符。

Schema 为新增表，无旧列改写。使用既有显式 `init-db` 注册新表的流程，隔离 SQLite 验证创建和重复执行，并核对 MySQL DDL。实际运行库建表及服务加载须在部署阶段完成，本轮不执行。旧版本可以忽略新增表，草稿不会作为恢复或检索数据源。

# 4. 对照实验与结果分析

2026-11-07：实现已通过隔离验证。最终定向回归 **941 passed，64 warnings，25.68 秒**；涵盖草稿保存、真实 SDK 模拟传输、Parse Worker、Summary、usage、schema 与 Chat 交付。命令、证据及限制见 [实施报告](../../report/server/service/parse-output-drafts-20261107.md)。

同一条模拟 SSE 流收到 65 段正文，旧接收回调额外触发 69 次持久检查，新回调 0 次；两组均保留 1 次调用接纳与 1 次显式周期心跳。两组草稿均在 1,024、2,048 字节保存中途快照，结束保存 2,051 字节。该计数对照不能代替 MySQL 持锁分布或整集耗时。

回归发现新增非流式正文观察会被 Chat 标为实时来源，因此 Chat 入口仅接收 `before_completion=true` 的实时增量；完整响应继续走原有交付。租户/任务归属由 Server scope 固定，元数据增加 refine generation，拒绝上下文覆盖归属。既有断流、取消和正式结果边界保持。

交付时整合最新 `dev` / `c3a79cbe`，仅解决追加文档冲突；针对上游认证修复追加 Auth / Bootstrap 回归，150 passed、7 skipped。跳过项不计通过，本功能 941 项验证与整合回归分开记录。

# 5. 试点验证与方案取舍

本轮试点是隔离数据库、模拟供应商流及真实业务装配的集成测试。真实解析任务保持用户要求的暂停状态。后续部署试点应先在隔离运行库建表，再用短素材测量实际 refine 活跃数量、领取失败原因、草稿保存频率和取消/失租行为；通过后再决定整集重跑。

取舍：按大小保存不会保证每隔固定时间可见草稿，长时间只输出很少正文时到退出才保存；这是时间与大小解耦后的预期行为。草稿没有自动清理或 UI 展示需求，本轮不新增后台任务，保留策略与查看入口另行决策。
