# 1. 问题与现状

分支 `perf/stream-event-coverage`。[PR #116](https://github.com/owariband/Seekino/pull/116)。关联 [查询向量路由 PR #112](https://github.com/owariband/Seekino/pull/112) 的全季游客验收。MyGO 查询进入检索后，公网与 SSH 一度无法访问。19:57 主机可用内存降至 50,000 KiB，swap 只余 12 KiB。21:31:06 内核记录 global OOM，杀掉 API Python 进程，其匿名 RSS 为 4,938,604 KiB；该容器无内存上限。Qwen 副本未重启。另一次未按租户联合索引限定的诊断查询可能增加 I/O，日志无法量化贡献。

`validate_event_coverage` 把所选集的全部 Chunk、完整内容、索引缓存和任务明细复制到列表，再按视频分组。仅这一处即可让请求持有的原始内容随整个系列增长；核对一条发布回执只需当前 Chunk。

## 2. 影响因素、假设与评价指标

主要变量是 Chunk 数量、每条回执附带的数据大小及并发检索次数。比较相同数据下的 Python 峰值、返回的来源三元组，以及损坏回执、缺 Chunk、授权与部分覆盖的处理。

## 3. 改造方案与建模

维持原事务和已授权视频范围。按视频用服务端游标每批取 4 条。在 SQL 中去掉缓存向量、任务明细和转写，只取事件内容、回执和版本等校验字段。逐条核对回执，完成一集后才接纳该集的来源标识。严格和部分覆盖沿用原合同。

## 4. 对照实验与结果分析

隔离 MySQL 8.4.13 使用 160 个 Chunk，每条附加 256 KiB 合成跟踪数据和 1024 个缓存浮点数。真实仓储读取得到相同的 160 个来源、版本和回执 ID。Python 分配峰值由 88.78 MiB 降到 0.16 MiB，耗时由 0.213 秒降到 0.013 秒。SQLite 对照为 86.57 与 0.16 MiB。测量仅覆盖仓储读取，不是整站 RSS 或线上回答延迟。208 项检索、发布和解析仓储测试通过，1 项跳过。

## 5. 试点验证与方案取舍

Cloud 恢复后按主键与租户联合索引核对原请求：3 次查询编码均成功。OOM 后原消息仍是处理中，已单独收尾。覆盖优化先进行隔离候选验证，再考虑恢复游客重放。

## 6. 结果验收与闭环

仓储用例验证游标在坏回执提前退出时释放，下一条语句可复用同一事务；空结果、错版本、部分覆盖、授权范围延用原检查。实际游客答案与时间片段仍须独立验收。[问题与状态](../../dev/workbench.html) · [故障记录](../../dev/problems.md#cloud-event-coverage-01)
