# 1. 问题与现状

分支 `perf/stream-event-coverage`。PR 创建后回填。关联 [查询向量路由 PR #112](https://github.com/owariband/Seekino/pull/112) 的全季游客验收。MyGO 查询进入检索后，公网与 SSH 一度无法访问。线上内核证据尚待获取，不能据此认定发生 OOM。

`validate_event_coverage` 把所选集的全部 Chunk、完整内容、索引缓存和任务明细复制到列表，再按视频分组。仅这一处即可让请求持有的原始内容随整个系列增长；核对一条发布回执只需当前 Chunk。

## 2. 影响因素、假设与评价指标

主要变量是 Chunk 数量、每条回执附带的数据大小及并发检索次数。比较相同数据下的 Python 峰值、返回的来源三元组，以及损坏回执、缺 Chunk、授权与部分覆盖的处理。

## 3. 改造方案与建模

维持原事务和已授权视频范围。按视频和小批量读取、逐条核对发布回执与版本，只保留该视频的来源标识与序号。严格和部分覆盖沿用原合同。

## 4. 对照实验与结果分析

用可重复的合成数据量化修改前后 Python 内存峰值，运行现有真实发布回执的仓储测试及检索服务回归。

## 5. 试点验证与方案取舍

用同一发布版本、同一查询真实重放之前，隔离实验只能证明内存保留方式改善。若云机恢复，先查看内核日志，再决定上线范围。

## 6. 结果验收与闭环

核对不完整视频不会混入部分结果，验证失败能释放游标、后续 SQL 可继续使用同一事务。公网故障原因和游客结果独立记录。
