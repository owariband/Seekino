# 1. 问题与现状

2026-11-11，剪辑者希望在本机 Claude Code 或 Codex 的同一会话里使用 Seekino Cloud 上的 MyGO 和本地素材。分支 `feat/cloud-public-mcp`，目标 `dev`，[PR #106](https://github.com/owariband/Seekino/pull/106)。[本机 MCP](mcp-access-trd.md) 已经使用 Python SDK 注册四个工具。Cloud 启动跳过检索服务与协议应用，公网 Nginx 也只将 `/api` 和 `/healthz` 转给后端。文档的添加命令指向安装者自己的回环地址。

公开目录曾通过普通游客会话列出 MyGO 的 13 集，第一集播放端点响应字节范围请求。这个结果只验证了 Web 取材基础。本机协议测试验证了工具发现，同时复现 Cloud 模式不可用。

# 3. 改造方案与建模

在现有 FastAPI 进程中挂载同一份 Streamable HTTP MCP。Cloud 的 Nginx 将 `/mcp` 交给 API，允许的外部域名取自部署配置。Claude Code 和 Codex 各自通过 `mcp add` 添加一个 HTTPS 的 `seekino_cloud`。本机实例继续使用回环连接 `seekino_local`。客户端按服务名选择素材，两个服务各自解析证据引用。

Cloud 首版面向配置的公共租户（含平台发布的 MyGO）。用户沿用 Seekino 游客或已登录身份取得仅可读取公开素材的 MCP 凭据。协议入口与片段下载验证凭据，工具不接受调用者指定租户。搜索和取片先按云端发布状态检查范围，查询按现有规则限流。Cloud 返回与证据版本绑定的片段地址，下载时复核公开状态。工具输入输出和本机旧客户端保持兼容。

复用 [PR #81](https://github.com/owariband/Seekino/pull/81) 的证据引用、区间校验和 FFmpeg 裁片实现，并保留 `dev` 的分镜信息。该能力也出现在 [PR #50](https://github.com/owariband/Seekino/pull/50)，本需求仅使用取片相关代码，不依赖整个剪辑工作流先合并。功能 PR 进入 `dev` 后按既有流程发布到 `main`，再验证公网。

# 4. 对照实验与结果分析

基线检查 `6ac788f8` 的 SDK 握手、工具发现、调用以及 Cloud 关闭断言。修改后用相同协议请求分别进入本机和云端应用，在隔离数据库核验可见、私有、下架及跨租户系列，验证凭据用途与片段媒体响应。通过代理的真实公网检查单列，避免把测试素材当成线上 MyGO。

# 5. 试点验证与方案取舍

在一个剪辑机使用标准客户端列出 Cloud 系列，选 MyGO，浏览一个真实 Event，读取来源，按返回的毫秒区间取一段 MP4，用 FFprobe 校验音视频流、时长。浏览流程不调用模型。若执行语义检索则单独记录结果。访问控制或旧回环合同回归时停止发布，沿用既有版本。

# 6. 结果验收与闭环

以本机协议兼容性、云端协议及访问范围、真实 MyGO 取片三个结果分别判断。已实现并通过隔离回归，生产待发布。验收证据关联[工作台](../../dev/workbench.html)及 [devlog](../../dev/devlog.md)。

2026-11-11 验证所用基线为 `6ac788f8`。Cloud 通过 `POST /api/auth/mcp-token` 为普通游客或现有会话签发专用 Bearer，账号版本和到期时间均沿用身份系统。平台发布状态和 READY 条件在检索、证据和取片时校验。片段下载凭据绑定来源和区间，最长有效 300 秒。无浏览器 Cookie 的下载器已在隔离环境取得 H.264/AAC 1 秒 MP4；旧链接在下架后返回 404。
