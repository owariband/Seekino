# 2. 影响因素、假设与评价指标

关键假设：已有凭据有效，阻塞来自低请求预算或身份/IP 并发；沿用原计数并提高阈值即可接纳旧额度之外的请求。现网具体失败计数尚待核对，不把“下载 3 段”解释为独立的 3 段上限。

| 游客日请求阈值 | 20，实际容器环境 | 10,000；配置装配与现网容器各核对一次 |
| 登录用户日请求阈值 | 200，实际容器环境 | 10,000；同上 |

# 3. 改造方案与建模

复用 `AuthConfig.from_environment`，设置 `SEEKINO_AUTH_QUERY_LIMIT_GUEST=10000`、`SEEKINO_AUTH_QUERY_LIMIT_USER=10000`、`SEEKINO_AUTH_CONCURRENT_QUERIES_GUEST=4`、`SEEKINO_AUTH_CONCURRENT_QUERIES_USER=4`。实际服务通过私有 `.env.cloud` 持久保存，部署样例记录相同数值。无需修改限流算法或用无效的 0 表达无限。

先备份私有环境文件，读取运行容器的完整 Compose 文件列表，核对渲染结果与实际 API 镜像、环境一致。仅重建 API，使用 `--no-deps --no-build --pull never`，保留数据库、索引、Redis、Web 和媒体卷；发现非本次差异则停止并核对。身份验证链及计数键不变，旧会话可直接受益。回退时恢复环境文件并以相同方式重建 API。

# 5. 试点验证与方案取舍

本次为低风险现有配置调整，以单次真实片段链路和旧阈值准入对照作为试点。提高阈值会扩大可用请求次数；本次并发上限为 4，原有全局容量和任务超时继续约束资源。没有实测的吞吐、长期成本和完整宣传片制作效果均不作结论。
