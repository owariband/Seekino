# 1. 问题与现状

需求：Chat 正文真实流式交付与 FTT 可信验收（PRD）。提出日期：2026-11-01。

业务目标：用户在课程学习中提问后，能在模型仍生成答案时逐步看到正文；QA 同时评价真实流式首字耗时 FTT 和整轮完成耗时 TT，能够据此选择优化方向。当前问题状态统一维护在 [C23](../../dev/problems.md#chat-streaming-c23)，课程整体用例仍由 [课程 QA TRD](course-qa-trd.md) 维护。

## 1.1 本次错误必须明确撤回

2026-11-01 的课程 QA 把浏览器收到第一份带正文的完整消息快照所需时间标成了 FTT。被测后端调用 Kimi 时使用 `stream=false`，QA 没有取得供应商首个正文增量的时间，也没有证明模型正文正在生成时就已经送到页面。因此，**9.173／29.576／27.231 秒不能作为真实流式 FTT，相关 FTT 基线和归因结论撤回。** 不能继续用“应用侧 FTT”的改名保留这组流式验收结论。

这是 QA 的指标定义与证据核对错误：没有先验证实际流式链路，就将另一种等待时间放进了 FTT 字段。原始时间戳保留用于复核，但不能继续参与 FTT 对照、模型首字速度判断或宣传。

| 用例 | 曾误标为 FTT 的数值 | 数值实际描述的事件 | 真实流式 FTT | 仍有效的 TT |
| --- | ---: | --- | --- | ---: |
| Q01：当前在演示什么 | 9.173 秒 | 首次完整模型回复中的进度正文到达客户端 | 未采集；旧标注撤回 | 38.796 秒 |
| Q02：结合已有基础继续解释 | 29.576 秒 | 三句话整段返回后，正文快照到达客户端 | 未采集；旧标注撤回 | 29.620 秒 |
| Q03：追问刚才解释的原片依据 | 27.231 秒 | 首次完整模型回复中的进度正文到达客户端 | 未采集；旧标注撤回 | 178.270 秒 |

这些辅助时间统一改称“首段整包正文到达耗时”。TT、工具耗时、用量和已核对的内容结果按原证据保留；没有测到的 FTT 填空值并写明原因，不能填 0，也不能用另一个时间替代。

## 1.2 实现缺口与证据

| 层次 | 已核对的事实 | 对用户与验收的影响 |
| --- | --- | --- |
| 首轮运行服务 | `full-video-asr` 工作区的 `gateway/openai/agent.py:311` 使用 `stream=False`；相关指纹与首轮 manifest 一致 | 后端要等一次模型调用完整结束才能拿到正文，无法从该响应补推模型首正文时间 |
| QA 分支的协议接收 | `gateway/streaming/chat.py` 已支持 `stream=true`，但 `request_chat_stream` 收齐所有 delta 后返回完整结果 | 仅打开协议流式，还不足以让用户边生成边阅读 |
| Agent 正文交付 | `gateway/agent_model/deepagents.py` 在 `after_model` 才调用正文回调 | 首段文字仍可能被整次模型调用挡住 |
| 页面与 QA 记录 | 浏览器通过 SSE 收到 `answer.snapshot`，QA 记录其到达时间；未采集供应商正文增量 | SSE 连接存在不证明内容来自实时模型增量；事件名不能代替链路证据 |

Q02/Q03 首次完整模型调用分别耗时 29.370／27.071 秒，结束后 9／32 ms 才生成服务端首正文快照。这说明历史整包等待主要落在完整模型调用内，**不说明模型在第 27～29 秒才生成首 token，也不说明接通流式一定能省掉多少秒**。Q03 随后的 78.411 秒实时工具影响 TT，属于另一段等待。

证据见 [首轮报告更正与调用时间线](../../report/server/course-qa-20261101.md#ftt-trace)、[脱敏记录](../../report/server/evidence/course-qa-ftt-trace-20261101.json)。历史运行包含未提交修改，尚未证明全部进程加载代码；当前源码可定位缺口，最终运行版本仍需单独部署验证。

# 2. 业务影响、指标与判断边界

课程追问会反复打断观看。FTT 决定用户多久开始读到模型正在生成的文字，TT 决定何时拿到完整解释与来源。两者都必须控制；提前显示固定提示不能代替真实首字，先输出一段进度也不能代替完成出处请求。

本需求使用以下唯一口径，后续报告不得自行把快照、回调或首包时间换名填入 FTT：

| 指标 | 起止事件与用途 | 当前基线 | 采证要求 |
| --- | --- | --- | --- |
| **FTT：真实流式首字耗时，主指标** | 浏览器发出提问，到客户端收到由供应商实时正文增量转发而来的第一段非空、可展示正文 | **未采集** | 必须证明实际模型请求开启流式、收到正文 delta、未等待完整结果才交付，以及该 delta 对应客户端的正文；客户端起止均用单调时钟 |
| **TT：整轮完成耗时，主指标** | 同一请求起点，到客户端收到整轮完成事件 | Q01/Q02/Q03 为 38.796／29.620／178.270 秒 | 完成须符合原有持久化和结果校验合同；取消与失败单独记录，不当作成功 TT |
| 模型首正文耗时，诊断指标 | 每次模型请求实际发出，到 Gateway 收到首个正文 delta | 未采集 | 每次调用独立记录；不能与从用户提问开始的整轮 FTT 混用 |
| 首段正文实际展示时间，诊断指标 | 浏览器发出提问，到页面首次呈现对应正文 | 未采集 | 与客户端接收时间分别记录；网络收到内容不代表 React 已展示 |
| 首个实质回答／来源齐备时间，辅助指标 | 从提问到首次有效解释／所要求的出处实际齐备 | 原报告保留相应记录 | 分清进度说明、实质回答和可核对来源；不能相互替代 |
| 首段整包正文到达耗时，历史辅助指标 | 非流式调用完整返回后，首份带正文的快照到达客户端 | 9.173／29.576／27.231 秒 | 仅用于描述旧体验，不参与 FTT 性能比较 |

FTT 不计空包、角色字段、心跳、状态枚举、固定“正在处理”文案、工具参数或内部推理。模型真实流式生成的进度正文可记录，但须标明首段类型，并继续报告实质回答与 TT，不能据此宣称问题已解决。

当前没有真实 FTT 基线，不能给出提速百分比或宣布首字性能达标。先验收真实增量链路，再用同条件探索样本建立基线，并在正式性能对照前确定各类问题的 FTT 目标。原 QA 的 30 秒实质回答、60 秒 TT 探索目标及 120 秒 TT 阻断线保持原意，不能改称 FTT 门槛。

# 3. 产品要求与改造边界

## 3.1 P0：模型正文持续交付到页面

预期路径是：**模型实际流式响应 → Gateway 取得正文增量 → Agent 发布可展示正文 → Server SSE → 页面逐段更新**。足够长的回答必须在当前模型调用尚未完成时已经出现正文，并在生成过程中继续增长。

1. 核对实际发往供应商的请求，不能只检查配置文件中的 `stream=true`。主模型、fallback 和重试分别记录有效参数与调用身份。
2. Gateway 收到可展示正文后，交付链路应能逐段转发。完整响应仍用于最终校验与持久化，但不能成为普通正文首次交付的统一前置条件。
3. 页面展示真实到达的增量；禁止先收齐全文再切片发送或播放打字机动画，禁止用固定进度文案制造“首字已到”的指标。
4. 工具参数和结构化结果必须收齐并校验后才能执行或提交；流式正文不能绕过来源、权限、时间范围和版本校验。内部推理不展示。
5. 最终快照与已显示正文一致，不能重复拼接、回退为旧内容或因重放重复执行。取消、断线、失败与恢复保留真实终态和已有内容的明确语义。

极短回复可能只有一个正文增量，不机械要求每条回复出现多个片段；但这种样本不能单独证明长回答的持续交付能力。

## 3.2 P0：测量结果必须能追溯到真实事件

每条用户请求关联会话、消息、模型调用和重试身份，记录运行版本、有效模型配置、缓存与负载。至少采集：实际请求发出、供应商首事件、供应商首正文 delta、供应商完成、服务端正文发送、客户端正文接收、页面首次展示、整轮完成。服务器内部与浏览器内部各用自己的单调时间；跨进程关联靠请求身份和事件顺序，不把不同机器时钟直接相减。

每个 FTT 值同时保存有效性和原始证据入口。`stream=false`、只拿到完整结果、正文被收齐后转发、没有供应商增量记录，均不能填写本需求的真实流式 FTT；字段为空并写出缺口。短回复、失败、取消、fallback 和多轮工具调用保留各自条件，不能只挑成功快样本。

## 3.3 责任与范围

| 层次 | 本需求要求 | 验收依据 |
| --- | --- | --- |
| Gateway／模型适配 | 真实流式请求、正文增量交付和每次模型调用计时 | 实际请求参数、原始事件及调用记录 |
| Chat Agent／Server | 正文逐段发送，完整工具与结果校验，终态与恢复 | 服务端事件、消息状态、工具执行记录 |
| Web | 正文真实增长，最终内容一致，取消与恢复可用 | 浏览器事件、页面变化与最终消息 |
| 专项 QA | 纠正旧指标、验证端到端链路、分组测 FTT 和 TT | 同一请求可关联的完整证据及人工质量核对 |

本 PRD 承接 [模型 stream 配置 TRD](model-streaming-trd.md)，补齐它未承诺的用户正文增量交付与真实首字验收。它不重做供应商协议或课程解析，也不预先决定换模型。重复看帧及无效视频提交导致的 TT 问题仍归 C22；不能用流式改造代替这些优化。

# 4. QA 用例与对照方法

先验证链路真假，再测真实速度。接口模拟用于发现缓冲、重复拼接和终态错误；模拟时间不得写入真实模型 FTT。真实验证使用明确部署版本与正常观看页，不预先合并无关实验。

| 用例／操作 | 预期结果与工作量 | 实际 FTT | 实际 TT | 检验效果与证据 |
| --- | --- | --- | --- | --- |
| Q02：沿用课程 QA 中“结合我的矩阵基础，用三句话继续解释”原题 | 使用已有会话证据；若无需工具，正文在该次模型完成前开始交付 | 未采集，待真实流式复测 | 历史 29.620 秒；新运行待测 | 检查简单追问的首字、持续输出、最终解释及上下文质量 |
| Q03：沿用“刚才解释的原片依据”原题 | 取证过程真实反馈，最终给出可核对来源；每次模型调用均可追踪 | 未采集，待真实流式复测 | 历史 178.270 秒；新运行待测 | 分开评价首字、工具等待、具体出处与完整交付，避免只改善进度提示 |
| 流式链路用例：可控供应商先发送正文，延后发送剩余正文与完成事件 | 页面在完成事件之前呈现并继续增加正文，最终文本一致 | 仅记模拟结果 | 仅记模拟结果 | 对比供应商、Server 和浏览器事件，确定没有收齐后转发；模拟不代替真实模型 |
| 反例一：显式 `stream=false` | 允许兼容路径完成回答，但真实流式 FTT 为空并注明非流式 | 不适用，不得填入整包耗时 | 待测 | 验证指标不会再次误报 |
| 反例二：供应商流式、上层故意收齐后才交付 | QA 必须判定端到端流式验收失败，不能仅凭参数或 SSE 连接判通过 | 无效，注明正文被缓冲 | 待测 | 验证测试能识别本次实际缺口 |
| 反例三：只有心跳、推理或固定进度提示，尚无模型正文 | 不产生正文 FTT，不将内部推理或工具参数展示给用户 | 正文到达前为空 | 待测 | 验证首事件与首正文的区分 |
| 可靠性：正文输出中取消、断线后恢复、重复接收事件 | 终态明确、正文不重复、不串会话、不自动重跑收费请求；完整工具参数才执行 | 分别记录或注明未到首字 | 失败／取消另记终止耗时 | 结合现有可靠性用例验证，不能为增量展示破坏原有合同 |

Q02/Q03 的新旧内容质量按同一原片依据核对。保持问题、历史、播放位置、基础及派生缓存和后台负载可比；不能把模型、Harness 与素材同时变化后的差值归于流式改造。每组至少三个同条件真实样本用于探索中位数，失败与取消保留；样本不足不报 p95/p99。

旧数据只能与新数据比较 TT、内容质量及明确同口径的辅助时间。**由于旧 FTT 不成立，不能用 29.576／27.231 秒作“流式首字优化前”的数值计算收益。** 首次真实流式运行建立新基线，之后的优化才在相同口径下对照。

# 5. 试点与放行条件

先在独立测试实例验证上述正反例，再以一门课程的真实观看页试点。实现前后都固定代码与配置来源；配置已合入、离线测试通过、真实模型有响应和用户流式体验通过分别报告。

进入课程演示验收必须具备：

- 足够长的真实回复有证据证明正文在模型完成前持续交付，页面同时可见；配置、事件、页面三者一致。
- FTT 与 TT 的计算可由原始记录复核；非流式与缓冲反例不会产生合格 FTT。
- 回答、引用与最终持久内容正确，取消／恢复／重放没有明显回归。
- 已在正式对照前确定性能目标，并由同条件样本支持；只证明链路通了不能宣布速度达标。

若只能证明供应商 SSE 已开启，或只能展示完整回答之后的分段动画，本需求仍不通过。先前 FTT 误标已撤回，也不等于真实流式能力已经修好。
