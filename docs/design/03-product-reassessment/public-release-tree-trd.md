# 1. 问题与现状

需求为精简面向自托管用户的 main 文件树。开发约定分支为 `docs/public-release-boundary`，发布分支为 `chore/minimal-public-release`，两个 PR 创建后回填。需求跟踪见[工作台](../../dev/workbench.html)。

2026-10-25 的发布提交 `a1901c12` 保留了 main 的 .gitignore，却从 dev 合入 73 个此前不在 main 的设计文件。2026-11-11 的 `203d8ee7` 中，docs/design/ 有 145 个文件，docs/report/ 有 279 个文件。普通 clone 会把这些文件检出。此次处理 main 当前发布目录，开发资料、运行中的数据库与媒体及 Git 历史另有用途。

## 2. 影响因素与验收指标

Git 合并传递已跟踪路径，单独核对 .gitignore 无法判断发布内容。按 Git 原始路径统计，`203d8ee7` 有 168 个已跟踪文件命中自身忽略规则，目标为 0。内部文档、训练、开发评测和运行数据路径的发布数目标为 0。两版 README 的本地图表、Web 图标、Compose 输入和升级 SQL 的缺失数目标为 0。

## 3. 改造方案

从 main 单独建发布工作区。依据已提交的路径和实际调用方筛选文件，开发工作在 dev 延续。README 插图及公开的可编辑图源归入 assets，旧库升级需要的脚本归入 deploy。发布检查读取候选提交的文件树，覆盖 dev 已经跟踪、合并后仍会落入忽略范围的文件。

## 4. 对照验证计划

在旧 main 与候选提交分别统计路径和字节数。用强制跟踪的忽略文件验证检查能拒绝回归。按中英文 README 解析本地链接、图片和图源，核对网站图标的符号链接与 Docker 构建输入。

## 5. 试点与取舍

在全新检出的候选树验证 Compose 配置、前端生产构建和受迁移路径、样本提取影响的测试。清理不操作用户持久卷，不需要调用付费模型。若用户入口依赖待删文件，保留所需实现或迁移引用后重新验证。

## 6. 验收与发布

发布 PR 以 main 为目标，开发约定 PR 以 dev 为目标。前者包含发布文件树和检查，后者维护操作规则与本记录。两者独立审阅，发布结果在合并后的 main SHA 上核实。当前验证及发布结果待补。
