# 2. 影响因素、假设与评价指标

## 2.1 先判断学习任务是否交付

主场景固定为：用户说明学习目标和已有基础 → 找到相关讲解及建议顺序 → 点击原片核对 → 围绕该片段追问 → 得到足以继续学习的解释。单轮解释、单次检索和整条路径分别计分；只测观看追问不能代表这条主场景已成立。这里验证任务完成，不把代理人评分写成学习效果、用户留存或转化率。

| 层级 | 指标与口径 | 为什么影响业务 | 当前依据与通过条件 |

## 2.3 性能敏感性与优化顺序

优先级依据是闭环是否必经、会重复多少次、已证实的阻塞和改动能否缩短用户实际等待。当前没有真实流量频次，因此下面是基于产品路径和现有证据的判断，不伪造业务权重或收益预测。

1. **先控制在线回答的模型往返和编排。** W01 的实时工具只有 0.686 秒，总回答仍为 38.796 秒；W02 没有工具，也需 29.620 秒。因此模型输入、生成、串行轮次与交付方式是必须拆测的共同成本；尚不能把全部余时归因为供应商速度。先统计每次模型请求、输入/输出、开始/返回及页面可用时刻，再决定缩减上下文、简化工具回合或比较模型。
2. **优先消除追问中不必要的取证与失败回合。** W03 的实时工具占总等待约 44%，其余约 56% 在工具之外。现有文本证据能否回答出处、是否仍需新看帧、是否暴露不可成功的提交工具，分别做对照；不能直接删除视觉能力。即使假设工具零耗时且其他路径完全不变，这个样本仍约需 100 秒；它只是串行耗时的反事实估算，不是改造收益承诺。
3. **尽早补测检索与第一条可回看片段。** 这是用户进入产品后的第一次价值交付，当前未知。先区分“召回不到”“召回正确但组织答案慢”“候选出来而页面/媒体不可用”；直接召回正确才继续诊断 Agent 的组织过程，不能在没有证据时先优化 ES 或重排参数。
4. **建库以按期交付可用课程为目标。** 它是另一条 P0 工作线，QA 跟踪真实总时间、末尾未完成阶段、覆盖和重试；上游据此处理 ASR/Understanding/Refine/索引的实际瓶颈。公开预置课程的学习会话通常不应每次承担整课解析成本；缺少 Chunk 的按需路径与后台解析争用会把离线问题带回在线，必须另测。

优化效果以用户关键路径为准：并发步骤不能简单相加，低耗时环节的小幅提速也不能冒充整轮明显改善。质量与正确来源是硬约束；取消/重复执行是可靠性护栏。已有三轮证据不支持把更换模型当成必然答案，也不支持排除模型速度问题。

# 3. 改造方案与建模

复用正式 Web、HTTP Agent SSE、消息查询/取消与检索 API，沿用 [实时理解设计](../02-agent-harness/realtime-parse-trd.md) 与 [证据交付合同](../01-mvp/agent-chat-delivery-contract.md)，以源码确认历史文档的当前适用部分。已有 benchmark 按能力组织；本专项增加课程用例和可复用的采证入口，不重建业务运行时或 Consumer。

验收顺序：

1. 固定版本、API、数据库/ES/媒体隔离标识、模型配置摘要、未提交源码指纹、解析状态。QA 分支首个提交仅本初稿。
2. QA 独立前端连接现有隔离 API，真实观看、提问、回看和刷新；保留浏览器证据。
3. API 补齐幂等、取消、缺证边界及计时；单独记录模拟/离线测试，不能代替真实效果。
4. 一门课程 READY 后即验目标/基础约束、课程内检索、中文问题与原片定位；两门相关课程就绪即验跨课顺序，不必等待七集。七集均就绪后补完整覆盖。
5. 缺陷按 `problems.md` 编号归并，最小复现、影响范围、证据和建议修复层明确。修改业务实现应按独立修复需求进入相应分支/PR；修复交付后重跑原失败例，再回归核心路径。

跟版时保存上游 ref/SHA；只有上游 HEAD 变化或新运行版本加载才建立新轮。运行工作区有未提交修改时保存相关文件 SHA256，检测采样前后是否变化；即使磁盘指纹不变，也不自行断言等于进程加载版本。未取得明确加载证据时标为运行基线验证，PR 最终提交仍待重验。

不迁移数据库、不修改共享模型、不重启解析服务。独立页面和新增 QA 会话是本轮测试产生的可追溯副作用。原始视频、配置密钥、签名 URL 和完整 trace 留在忽略目录，不进入 Git；报告保留复现入口和脱敏摘要。
