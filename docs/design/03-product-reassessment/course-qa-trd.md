# 2. 影响因素、假设与评价指标

## 2.1 先判断学习任务是否交付

主场景固定为：用户说明学习目标和已有基础 → 找到相关讲解及建议顺序 → 点击原片核对 → 围绕该片段追问 → 得到足以继续学习的解释。单轮解释、单次检索和整条路径分别计分；只测观看追问不能代表这条主场景已成立。这里验证任务完成，不把代理人评分写成学习效果、用户留存或转化率。

| 层级 | 指标与口径 | 为什么影响业务 | 当前依据与通过条件 |
| --- | --- | --- | --- |

## 2.3 性能敏感性与优化顺序

优先级依据是闭环是否必经、会重复多少次、已证实的阻塞和改动能否缩短用户实际等待。当前没有真实流量频次，因此下面是基于产品路径和现有证据的判断，不伪造业务权重或收益预测。

1. **先接通并验证正文流式，再控制模型往返与编排。** Q01 实时工具只有 0.686 秒、TT 仍为 38.796 秒，Q02 无工具而 TT 为 29.620 秒。Q02/Q03 首次完整模型调用分别耗时 29.370/27.071 秒，结束后才发布整段正文；这能解释旧的整包等待，不能给出真实流式 FTT。先按 [Chat 流式 PRD](chat-streaming-prd.md) 验证端到端增量并建立新基线，再判断推理、上下文或模型的影响。看帧及失败工具回合继续作为 TT 问题单独处理。
2. **优先消除追问中不必要的取证与失败回合。** Q03 的实时工具占总等待约 44%，其余约 56% 在工具之外。现有文本证据能否回答出处、是否仍需新看帧、是否暴露不可成功的提交工具，分别做对照；不能直接删除视觉能力。即使假设工具零耗时且其他路径完全不变，这个样本仍约需 100 秒；它只是串行耗时的反事实估算，不是改造收益承诺。
3. **尽早补测检索与第一条可回看片段。** 这是用户进入产品后的第一次价值交付，当前未知。先区分“召回不到”“召回正确但组织答案慢”“候选出来而页面/媒体不可用”；直接召回正确才继续诊断 Agent 的组织过程，不能在没有证据时先优化 ES 或重排参数。
4. **建库以按期交付可用课程为目标。** 它是另一条 P0 工作线，QA 跟踪真实总时间、末尾未完成阶段、覆盖和重试；上游据此处理 ASR/Understanding/Refine/索引的实际瓶颈。公开预置课程的学习会话通常不应每次承担整课解析成本；缺少 Chunk 的按需路径与后台解析争用会把离线问题带回在线，必须另测。

优化效果以用户关键路径为准：并发步骤不能简单相加，低耗时环节的小幅提速也不能冒充整轮明显改善。质量与正确来源是硬约束；取消/重复执行是可靠性护栏。已有三轮证据不支持把更换模型当成必然答案，也不支持排除模型速度问题。

# 3. 改造方案与建模

复用正式 Web、HTTP Agent SSE、消息查询/取消与检索 API，沿用 [实时理解设计](../02-agent-harness/realtime-parse-trd.md) 与 [证据交付合同](../01-mvp/agent-chat-delivery-contract.md)，以源码确认历史文档的当前适用部分。已有 benchmark 按能力组织；本专项增加课程用例和可复用的采证入口，不重建业务运行时或 Consumer。

验收顺序：

1. 固定版本、API、数据库/ES/媒体隔离标识、模型配置摘要、未提交源码指纹、解析状态。QA 分支首个提交仅本初稿。
2. QA 独立前端连接现有隔离 API，真实观看、提问、回看和刷新；保留浏览器证据。
3. API 补齐幂等、取消、缺证边界及计时；单独记录模拟/离线测试，不能代替真实效果。
4. 一门课程 READY 后即验目标/基础约束、课程内检索、中文问题与原片定位；两门相关课程就绪即验跨课顺序，不必等待七集。七集均就绪后补完整覆盖。
5. 缺陷按 `problems.md` 编号归并，最小复现、影响范围、证据和建议修复层明确。修改业务实现应按独立修复需求进入相应分支/PR；修复交付后重跑原失败例，再回归核心路径。

跟版时保存上游 ref/SHA；只有上游 HEAD 变化或新运行版本加载才建立新轮。运行工作区有未提交修改时保存相关文件 SHA256，检测采样前后是否变化；即使磁盘指纹不变，也不自行断言等于进程加载版本。未取得明确加载证据时标为运行基线验证，PR 最终提交仍待重验。

不迁移数据库、不修改共享模型、不重启解析服务。独立页面和新增 QA 会话是本轮测试产生的可追溯副作用。原始视频、配置密钥、签名 URL 和完整 trace 留在忽略目录，不进入 Git；报告保留复现入口和脱敏摘要。

本轮策略修订不启动新的付费请求。后续采样先核对每题的素材与评价依据，保留 Q01–Q03 为调试回归，再增加不同位置/讲解片段作为未参与调参的验收样本。概念、代码/公式和缺证题按风险各取代表例，不做所有视频、缓存、问题、故障的全组合。固定问题及来源后再做同条件重复；模型切换仅在有对照价值时使用同一问题、证据、预算与质量标准，不同时更换 Harness 和数据集。

## 3.1 QA 测试用例集

用例集版本：2026-11-01 v2。本节是人工验收的主入口，按功能说明业务目标，再逐条记录 query、预期结果、工作量、实际结果、耗时和判定方法。表中的实际结果来自 2026-11-01 首轮；新增用例尚未执行，不代表新增能力已经通过验收。缺陷的处理状态仍只在 [problems.md](../../dev/problems.md) 维护。

Q 表示 query（问题）；首轮三题统一使用 Q01/Q02/Q03，对应原 W01/W02/W03。此次只更改编号，题目、预期和实测值不变；原始事件、截图保留旧编号，用例文件的 `legacy_id` 与报告中的映射负责关联历史证据。

“预期工作量”指系统为了回答问题需要读取多少内容、执行哪些动作，不是开发工时，也不是承诺的响应秒数。工作量不同的用例分别比较：复用已知证据、观察新画面、补解析和全课检索不能混算。具体用了多少模型或工具调用，另随每次运行记录；不为了凑某个调用次数而限制合理取证。

问答用例必须分别填写 **FTT 和 TT**。FTT 只在真实模型流式正文经过端到端增量交付的条件下记录，TT 仍取整轮完成事件；具体起止与有效性按 [Chat 流式 PRD 第 2 节](chat-streaming-prd.md#2-业务影响指标与判断边界)。固定进度、心跳、状态、工具参数和推理不算正文首字；真实流式生成的进度正文注明类型，继续单列首个实质回答和来源齐备时间。

历史数据只记录浏览器收到完整正文快照的时刻；被测模型请求为非流式，没有供应商正文 delta 记录。因此三题的真实流式 FTT 均填“未采集”，原数值改列为首段整包正文到达耗时。此前将这些数值称为 FTT 的结论已撤回，不能据此推算模型首字或流式改造收益。SSE 连接和事件名称本身不构成真实增量证据。

回看、刷新等不生成答案的操作，FTT 填“不适用”，单独量操作耗时；发生失败、取消时保留终态和终止耗时，不能伪装为成功 TT。没有取得首字记录则填“未采集”，尚未执行则填“待测”，均不能填 0。原定 30 秒约束的是首个实质回答，60/120 秒对应整轮完成，不因新增 FTT 而改写旧结果或追认性能通过。视频上下文的时间范围与回答耗时仍分别记录。

执行前固定被测提交、运行配置、视频/任务/索引版本、会话与播放位置，并记录基础内容、画面观察缓存和后台负载。参考答案及预期出处只供评审使用，不发送给模型。改题或换素材建立新版本；复测追加新一轮结果和证据链接，保留本轮失败记录。尚未标注原片的用例须先补齐参考依据，再运行和评分。

### 3.1.8 执行与回填顺序

先用 RT01 明确最基本的实时问答表现，再结合 Q02/Q03 复验连续解释与局部证据追问；随后用 RT03–RT05 检查提速没有带来旧画面、越界引用或顺从错误前提。RT02 补齐代码素材后执行，RT06 与故障用例在独占环境中执行。首个课程 READY 后立即开始 SE01–SE04 和 LP01，相关课程就绪后执行 LP02/PB02，不等七集才验证前半段。DP01–DP03 跟踪上游交付，ON01 放在实际发布环境。

每轮回填应附日期、运行标识和证据入口；“实际结果”同时写完成了什么、哪里不符合预期；问答必须分别填写 FTT 和 TT，并标明首段内容类型。检验效果分别说明首字等待、完整交付、内容质量，必要时再补实质内容与来源齐备时间。没有单独计时就不能给速度打分，没有原片依据就不能给内容打分。当前脚本只覆盖 Q01–Q03 和部分回看/可靠性操作，本节新增用例仍需按条件逐项执行，不能把文档覆盖当成自动化覆盖。

后续报告每个结论至少包含：用户任务、对应业务指标、失败环节、证据强度、建议改动、预期收益的适用边界、质量/成本护栏以及复验条件。性能变好但任务没有更快完成，不能据此宣布业务收益。

# 5. 试点验证与方案取舍

先以《Let's build GPT》已完成片段作为一门课程试点，在浏览器走用户入口；它能尽早暴露 QA 问题且不等待七集解析。其通过只支持这门课程的已测路径。取证后决定继续核心回归、转交最严重缺陷或等待上游 READY。若出现数据版本变化、服务不可用、连续两次远程模型失败或预算达到上限，停止新增付费请求，继续本地分析和报告，说明恢复条件。

扩大到七集与公开部署前，需补齐全课/跨课来源、目标学习路径、生产部署配置与页面实际接入。不同环境的成功不可互换。当前优先保证演示可信且等待可接受，不在本专项开展模型选型研究或长期用户画像开发。
