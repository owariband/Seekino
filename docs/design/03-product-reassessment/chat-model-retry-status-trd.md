# 1. 问题与现状

2026-11-07 local 会话 d14c64d2 的两轮回答耗时 53.57 s 和 62.32 s。首 SSE 超时分别触发一次和两次，每次等待约 15 s。Gateway 记录 chat_first_sse_retry，浏览器只看到当前阶段，用户无法判断模型是否正在恢复。原始记录位于本机 outputs/verification/parse-output-drafts-live-20261107/api.log。

分支为 fix/chat-model-retry-status，通过 [PR #71](https://github.com/owariband/Seekino/pull/71) 向 dev 集成。沿用[现有流式交付设计](chat-streaming-trd.md)，本次交付模型重试的用户反馈。整轮 30 s 是另行验证的性能目标。

## 2. 影响因素、假设与评价指标

Gateway 掌握重试原因、次数和上限。假设 Server 能在正在处理的消息上发布该状态，并在浏览器恢复连接时提供当前快照。

|指标|基线|目标|测量方法|
|---|---|---|---|
|首 SSE 超时重试可见性|两轮共三次，仅有日志|显示 `reconnecting 1/3` 并随重试更新|对齐 Gateway 事件、Chat SSE 和浏览器状态|
|恢复及终止后的残留提示|待测|零残留|分别触发响应、取消、失败并检查界面|
|正常请求误提示|待测|零次|无超时用例核对页面与模型请求数|

## 3. 改造方案与建模

Gateway 按调用 ID 上报进入与退出重试的状态，同时传递当前序号与该调用的重试上限。Server 将其关联到消息并通过现有 Chat SSE 推送。等待模型首个响应事件时在回答内容末尾以工具调用行的样式显示 `reconnecting 1/3`，后续尝试更新同一行。收到首事件即清除对应调用的提示；取消或终止时清空该消息的状态。浏览器订阅恢复时以服务端快照为准。多个调用交错时按调用 ID 处理。重试耗尽沿用现有失败处理。

## 4. 对照实验与结果分析

计划在相同配置下用可控模型端点分别模拟立即成功、超时后恢复、连续超时至耗尽和等待时取消。比较 dev 与工作分支的重试序列、浏览器提示和最终消息状态。补测两次独立调用先后超时，以及重试期间浏览器重新订阅。结果待测。

## 5. 试点验证与方案取舍

由实施者在 local 测试环境通过正常 Chat 页面发送消息，记录重试提示出现与清除时的截图及对应 SSE 顺序。若提示滞留、归属错误或影响实际重试次数，修正后重新验收。
