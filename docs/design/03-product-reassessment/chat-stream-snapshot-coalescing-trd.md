# 1. 问题与现状

**Chat 流式快照合并 TRD。状态：已实现，课程库副本实测达标；演示环境验收待做（2026-11-05）。** 分支 `fix/chat-stream-snapshot-coalescing`，PR [#45](https://github.com/owariband/Seekino/pull/45)。关联：[chat-streaming-trd.md](chat-streaming-trd.md)（PR #25，流式交付合同）。无合并顺序依赖；2026-11-05 发布验收阻塞项。

## 背景与触发场景

2026-11-05 在实验 API 19642（课程库副本）上复测整体性问题时，客户端持续读取 SSE，却在回答生成途中收到 `answer.interrupted`（`STREAM_INTERRUPTED`，“连接未能及时接收回答，请通过会话快照恢复。”），服务端执行随后正常完成。

## 实际与期望行为

期望：持续读取的客户端收到完整的增量与终止事件，不出现中断提示。实际：长回答在中途被判为“慢消费者”而断开；网页端随后通过会话快照恢复（`web/src/features/search/useAgentConversation.ts:321,335`），但用户先看到错误提示。

## 现状证据

- 事件缓冲 `Queue(maxsize=256)`，`publish` 用 `put_nowait`，满时断开并发出 `answer.interrupted`：`server/service/agent_chat.py:144,150-177`。
- SSE 读取循环每个事件两次经线程池做来源权限复核，并对完整消息做投影与 JSON 序列化：`server/api/agent.py:764-800`。
- `answer.snapshot` 携带累计全文，长回答的单事件成本随长度增长（推断，未测单事件耗时）。
- 实测（`outputs/verification/video-outline-20261104/chat-runs/`）：

| 用例 | 结束事件 | 客户端耗时 | 服务端快照数 |
| --- | --- | --- | --- |
| fix41-video-2 | `answer.interrupted` | 100.0 s | 1135（执行 120.7 s 完成） |
| fix41-specific-2 | `answer.interrupted` | 124.7 s | 561（执行 125.9 s 完成） |
| ov-series-1 | `answer.interrupted` | 45.9 s | 待统计 |

同一构建另外 8 次回合正常完成。该缓冲与读取循环在 `dev` `cd6bed14` 中相同，问题不由 #41、#44 引入，回答变长使其更易触发。

## 负面影响

整体性问题的回答通常较长，正是最容易触发中断的场景；用户看到“连接未能及时接收回答”，以为回答失败。

## 本次边界

解决：持续读取的客户端不再因快照积压被断开。不解决：真正停止读取的客户端仍按现有语义断开并恢复；不改 SSE 事件合同与前端。必须保持：终止事件、证据事件和顺序不丢失；`answer.interrupted` 的恢复路径不变。

# 3. 改造方案与建模

在 `publish` 中合并相邻快照：若缓冲尾部是尚未取走的 `answer.snapshot`，新快照替换它而不是追加。非快照事件照常追加，因此事件相对顺序不变，`sequence` 只出现跳号（两个前端消费者已容忍跳号，待单元测试核对）。缓冲满（全是非快照事件或消费者停止读取）时保持现有断开语义。

备选：加大缓冲只推迟溢出；阻塞写入会拖慢模型执行；减少每事件权限复核可另行优化。
