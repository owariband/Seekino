# 1. 问题与现状

本需求修复聊天页的连接提示误显示与重复渲染开销。提出日期：2026-11-12。分支：`perf/chat-frontend`；PR：[前端性能修复 #126](https://github.com/owariband/Seekino/pull/126)，目标 `dev`。当前执行状态统一见[工作台](../../dev/workbench.html)的 `CHAT-PERF-01`，不在本设计另设任务看板。

聊天页在输入、流式输出、更新思考过程、切换历史和结束回答时出现卡顿，Kino 的动作与状态切换也受影响。页面已有完整回答时，底部仍可能显示“正在连接助手…”，同时保留停止按钮。期望连接提示只覆盖本次请求尚未受理的阶段；完成后不倒退成连接中。输入和一条回答的增量更新，不应重新解析所有历史回答。

已确认的执行路径：

- `SearchPage.tsx` 以 `searching && 没有 PROCESSING 消息` 判断连接中；`useAgentConversation.ts` 的 `sending` 则到 POST SSE 结束才清除。终态先于 EOF 到达时，两者会产生误显示。React 可能合并更新，不能据此声称每轮都会闪现。
- 消息直接在 `SearchPage` 内渲染。`MarkdownAnswer` 没有缓存边界，输入和 conversation 状态更新会带动历史 Markdown 执行。2026-11-12 在 `236bdd8c` 的临时 jsdom 探针中，20 条历史回答下，输入一个字符、仅更新 reasoning、更新一条消息，各执行 20 个 Markdown；这是组件执行次数，不是浏览器掉帧或输入延迟。
- Kino 用定时器更新 6/10/15 fps 的像素姿态，跳跃位移已有 rAF。纯栅格化与 SVG 路径生成微基准的 p95 最大 0.064 ms，不包含 React、布局和绘制；该结果不足以认定线上动画流畅。

本次基线取最新 `origin/dev` 的 `1adac5d3`。它已合入 [#124](https://github.com/owariband/Seekino/pull/124) 对 Kino 收尾和播放进度的验收，完成后的 `happy`、`sleep` 与跨气泡移动按当前实现保留，不能照旧排查报告恢复“完成即卸载”的行为。原探针将在本次基线上重测，原始结果保留于对应验收目录。

已有流式合同见 [Chat 流式](chat-streaming-trd.md)、[正文增量交付](chat-text-delta-stream-trd.md)（#49）和 [慢消费者合并](chat-stream-snapshot-coalescing-trd.md)。这些上游均按基线中的实际接线复核；本 PR 单独向 `dev` 集成，不新开第二个实现或发布 PR。

本次只修改前端聊天状态、渲染与滚动及直接相关的测试。保留毫秒时间、原文和卡片顺序、权限投影、幂等、取消、刷新及断线恢复、真实首字计量、现有 Kino 交互和无障碍行为。后端 `eventTrace` 瘦身、数据库、模型与部署不在已确认改动中；先测载荷，再记录是否需要后续处理。

# 3. 改造方案与建模

状态处理属于 `useAgentConversation`，消息排版及滚动属于 Search feature，Kino 的像素动作属于现有共享引擎。沿用 React、现有 SSE 事件和请求身份，不增加全局 store、Worker、Canvas、通用状态机框架或新依赖。

请求阶段由已有消息状态及本次受理身份推导：

| 阶段 | 显示 | 提交与取消 |
| --- | --- | --- |
| 请求发起、尚未受理 | 正在连接助手 | 提交阻塞，不能取消尚无 ID 的消息 |
| 当前消息 PROCESSING | 当前执行阶段及 Kino | 沿用停止能力 |
| 中断后等待可信状态 | 恢复提示，保留已有正文 | 不虚构完成态 |
| 当前消息已完成或失败，传输仍收尾 | 显示可信终态，不显示连接中或无效停止按钮 | 保留发送按钮但禁用，EOF 后放开；沿用页面和 hook 已有的发送阻塞判据 |
| 无运行或收尾请求 | 正常输入 | 可提交 |

React state 增加一位 `accepted`，在 `answer.started` 或幂等探测确认接收后设置；连接提示由 `sending && !accepted` 推导，不再依赖“没有 PROCESSING”。传输结束前保留既有发送守卫，停止按钮单独看真实 PROCESSING。复用本次幂等 key 作为 `active.requestKey`，旧请求的探测和 finally 对账写回前核验它未变化，覆盖新请求已经结束的交错场景；不能只判断 controller 又变回 null。

消息提取为有明确职责的渲染边界，已完成 Markdown 按文本和必要标识缓存；`SeekContext` 的 value 及缺省数组保持稳定。旧快照带来新消息对象时，允许消息容器更新；不通过不完整字段白名单保留可能过期的权限或媒体投影。输入更新不再执行历史 Markdown，正文更新只执行变化的块。

滚动按显示帧合并，只在用户仍跟随底部时运行；图片、卡片和思考面板等实际高度变化纳入观察。程序滚动不能把用户上滚误判为跟随，也不能在每个 delta 启动平滑滚动。是否需要在绘制前修正位置由浏览器证据决定。

若实测要求合并 delta：接收时校验 sequence，缓冲仅属于当前请求；snapshot、block、progress 和终态按原顺序处理，边界前先提交增量，最终快照保持权威。取消、切换会话与卸载均清除旧缓冲。不能按空行拆 Markdown，也不能把入场动效当作降低解析开销。

已按最小复现、当前基线、Flash 实现、主 Agent 复核及同条件对照推进。首个提交 `df7a9128` 只包含本 TRD；后续全部沿用 #126。OpenCode DeepSeek Flash 完成实现与主要回归测试，Codex 补强晚到对账用例、保留原卡片选择判据，并运行验证。实现提交为 `1392bfa8`。

# 4. 对照实验与结果分析

保留 `1adac5d3` 的 detached 基线 worktree，用相同锁文件、消息和事件回放比较实现提交 `1392bfa8`。组件探针统计解析执行次数；生产构建 Chrome 157、1440 × 900、4 倍 CPU 降速，分别回放 1/20/60 条历史，每场景预热后 30 次输入、100 个 SSE 增量及每秒一次全量快照。没有连接业务数据库或模型。完整条件、各场景数据和复跑命令见[验收报告](../../report/web/chat-frontend-performance-20261112.md)及[配套 JSON](../../report/web/chat-frontend-performance-20261112.json)。

| 指标 | 基线实测 | 方案实测 | 判断 |
| --- | --- | --- | --- |
| 终态后连接提示及无效停止 | 三个场景均出现 | 均未出现，发送保持禁用直到 EOF | 通过；单测覆盖 failed / interrupted 和晚到对账 |
| 20 条历史下输入 / reasoning / 单消息更新的 Markdown 次数 | 20 / 20 / 20 | 0 / 0 / 1 | 通过；两类探针确认 |
| 60 条历史的输入观察 p50 / p95 | 36.6 / 38.6 ms | 15.4 / 16.0 ms | 中位数下降，p95 下降约 59% |
| 同场景 SSE 到 DOM 观察 p50 / p95 | 35.3 / 38.8 ms | 11.0 / 18.4 ms | p95 下降约 53%，100/100 增量均观察到 |
| 同场景流式显示帧间隔 p95 | 50.0 ms | 16.7 ms | 说明显示帧机会改善，不等于 Kino 姿态改成 60 fps |
| Kino progress 到状态属性的三次更新 | 43.5 / 38.8 / 35.9 ms | 2.9 / 2.4 / 2.3 ms | 三次诊断值，不作尾部或物理绘制结论 |
| 手动上滚、返回底部、草稿与结束后提交 | 通过 | 通过 | 沿用正确性护栏 |

原始证据保留在 `outputs/verification/chat-frontend-performance-20261112/`；回放脚本为 `web/tests/chat-frontend-performance.mjs`。p95 只描述这批样本，不代表线上 SLO。1 条历史的输入 p95 从 16.6 ms 变为 16.9 ms，没有测出收益；两版在本轮窗口内均未记录超过 50 ms 的 long task。历史打开只采了一次就绪时间，不据此推断冷启动收益。

# 5. 试点验证与方案取舍

受控试点采用隔离长会话、固定 SSE、真实前端组件及新旧请求交错，不消耗业务模型或操作持久数据。类型检查、生产构建及 33 个文件的 658 项前端测试通过；新增测试覆盖停止与恢复、终态先于 EOF、全量快照先完成、旧请求晚到时新请求也已结束、滚动及观察器清理。

现有聊天布局与流式浏览器用例为 6 项通过、1 项失败。失败是公开范围提示位置断言；未改动的同版基线在同一行以相同坐标失败，未修改测试期望掩盖结果。该既有布局问题留给 `CHAT-HEADER-01` 核对，本 PR 不新增第二个交付分支或 PR。

渲染隔离已把长历史更新压回一帧附近，本轮不增加 delta 缓冲、Markdown 分段或 Kino 引擎改写。全量快照仍可更新证据投影；只缓存未变化的 Markdown，不按不完整字段冻结业务事实。

若历史解析次数未下降、内容或卡片顺序变化、用户滚动被覆盖或恢复状态退化，继续修正本 PR。若未测因素才是主要瓶颈，保留失败证据，收缩结论；不通过引入大框架或扩大后端改造掩盖结果。回退为撤销本 PR 的前端实现，不涉及数据迁移。
