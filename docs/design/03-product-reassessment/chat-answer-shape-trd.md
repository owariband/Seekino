# 1. 问题与现状

**Chat 回答形态 TRD。状态：初稿（2026-11-05）。** 分支 `fix/chat-answer-shape`，PR [#51](https://github.com/owariband/Seekino/pull/51)。关联：[chat-text-delta-stream-trd.md](chat-text-delta-stream-trd.md)（PR #49，正文增量交付，已合并，本需求不改其交付合同）；并行需求 [chat-card-event-boundaries-trd.md](chat-card-event-boundaries-trd.md)（视频卡范围对齐，独立分支，同改 `agent/chat/supervisor.py` 的不同位置）。触发：2026-11-06 面向面试官演示，回答的可读性与观感直接决定演示效果。

## 背景与触发场景

2026-11-05 在演示环境（dev `4eb4231b`，端口 19641）提问「和我说说这个课程讲了些什么，如果我想要训练一个LLM，我该怎么做？我的目的是把offline改造成online，即流式理解的模型」。回答 2,783 字，结构为：两句过程播报（「我先看一下这两个系列……」「课程结构已经拿到了……」）、两行「查找视频资料 已完成」工具行、约 2,000 字的正文（其中一段约 300 字由「→」串成），最后三张视频卡。Seekino 的长处是把回答落到原片的精确时间段，这条回答却读起来像一篇通用教程，视频片段排在末尾。

## 实际与期望行为

- 期望：先直接回答；要点用列表，单段短；视频片段和时间码是主角；完成后的回答里没有过程播报和工具状态行；视频未覆盖的内容简短说明来源。
- 实际：见下方现状证据。

## 现状证据

1. **过程播报是 Prompt 要求的。** `agent/chat/supervisor.py` 系统提示写明「调用耗时的视频检索、网页搜索或当前视频理解工具前，先用一句简短自然的正文说明准备核验什么」以及「得到证据后，如仍需继续核验，可简短说明已发现的内容和下一步核验目标」。模型照做，播报留在最终回答里。
2. **工具行在完成后仍逐条显示。** `web/src/features/search/SearchPage.tsx` 对每个 `tool` 渲染块都输出一行标签与状态，不区分进行中与已完成。
3. **单个换行被合并。** 回答用 `react-markdown` + `remark-gfm` 渲染，未启用 `remark-breaks`；模型在加粗小标题后只写一个换行时，标题与正文连成一行。截图回答中出现 2 处，是次要问题。
4. **用户消息下的「可用视频范围：…」** 在发布模式也显示，属于调试信息。
5. **基线测量**（`outputs/verification/course-loop-dev-20261104/score_answers.py`，LOOP-08 九个门禁，`gates/loop08-dev-4eb4231b.json`）：

## 本次边界

- 解决：过程播报、回答结构与篇幅、完成后的工具行、单换行渲染、发布模式下的调试信息。
- 不解决：视频卡时间范围对齐（并行 TRD）；工具串行与回合耗时（发布后跟进）。
- 2026-11-05 晚补充范围：门禁重跑后（`gates/loop08-shape-60974360-rerun.json`）回答形态已基本达标，剩余问题是版式。LP01 的三张视频卡集中排在正文前（模型 21:48:00–02 先提交全部视频卡，21:48:03–08 才写正文），正文又在每条推荐里重复时间范围，用户需要自己对照；视频卡说明是加粗长段并重复时间码；完成后保留整行状态框和睡眠吉祥物。本次一并解决：视频卡就近放在对应推荐下方、正文不再重复已有视频卡的时间、视频卡与正文排版、完成状态的展示。思考过程展示另立需求（见 [chat-reasoning-display-trd.md](chat-reasoning-display-trd.md)），依赖本分支。
- 保持：调试模式（`displayMode === "debug"`）照常显示工具行、检索目标与范围；进行中的工具行照常显示，作为任务已开始的反馈；限定句数、先回应再检索等既有规则不变。

# 2. 影响因素、假设与评价指标

## 因素与假设

| 因素 | 证据 | 假设 | 验证 |
| --- | --- | --- | --- |
| Prompt 要求播报 | 系统提示原文 | 删除要求并明确「正文只写给用户的回答」后，播报基本消失 | 门禁重跑，统计播报率 |
| Prompt 缺少回答结构约束 | 长段、箭头串、通用知识大段展开 | 加入「先结论、列表、短段、未覆盖内容一两句带过并标注」后篇幅与段长下降，视频证据不减少 | 门禁重跑，字数、段长、视频卡数 |
| 前端逐条显示工具行 | `SearchPage.tsx` 渲染循环 | 发布模式下完成后隐藏工具行不影响进行中反馈 | 前端单测 + 浏览器截图 |
| 单换行合并 | 渲染插件配置 | `remark-breaks` 让单换行按模型意图换行 | 前端单测 |

假设一旦不成立：删除播报要求后若首个可见反馈明显变慢，用户会以为系统卡住。进行中的工具行已在工具开始时出现，预期不受影响；以门禁的首个工具行时间与旧首字时间对照。

# 3. 改造方案与建模

1. **Prompt（`agent/chat/supervisor.py`）**
   - 删除两处播报要求，改为：不写过程说明或进度播报，界面会根据真实调用显示查找状态；正文只写给用户的回答。
   - 增加回答结构：先用一两句话直接回答；要点与步骤用 Markdown 列表，不用「→」把多步串成长句，单段不超过约 120 字；视频未覆盖的内容用一两句说明并标明来自通用知识，除非用户要求详细，不展开成教程；除非用户要求详细，整条回答控制在约 800 字以内；加粗小标题后空一行再写正文。
   - 「先回应再检索」场景的前置正文属于用户要求的内容，规则保留。
2. **前端（`web/src/features/search/SearchPage.tsx`）**
   - 发布模式下，消息不在 PROCESSING 时不渲染 `tool` 块；调试模式与进行中保持原样。
   - Markdown 渲染加入 `remark-breaks`。
   - 「可用视频范围」仅在调试模式显示。
3. **视频卡就近放置（Prompt + 前端，不增加模型轮次）**
   - 原 Prompt 允许交替写正文与提交视频卡，但每次交替多一轮模型调用，模型实际上先提交全部视频卡再写正文。改为：先提交视频卡，正文中在对应推荐下方单独一行写 `[[视频N]]`，N 为 `submit_video_item` 返回的 `video_item_count`；已有视频卡的片段，正文不再写时间码；视频卡的 claim 作为卡片标题，约 30 字以内、不含时间码。当前播放视频的纯文本时间码规则不变。
   - 前端在发布模式下按标记把第 N 张视频卡渲染在标记位置；未被引用的视频卡排在回答末尾，不丢失；标记文本本身（包括流式中尚未写完的标记前缀）不显示；调试模式保持按产生顺序展示。
4. **版式**：视频卡改为紧凑卡片（缩略图、标题、系列·集数·时间），去掉序号和「视频片段 N 段」标题；正文标题与列表间距调整；完成后的状态改为一行浅色文字，不再显示整行状态框和睡眠吉祥物。

不做前端启发式隐藏「工具行前的正文」：先回应再检索时，这段正文就是用户要的内容，隐藏会丢答案。播报只从源头（Prompt）去除。
