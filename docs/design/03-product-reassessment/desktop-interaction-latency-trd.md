# 1. 问题与现状

2026-11-24，原生桌面 0.2.14 已接入观看、搜索、导入和 Kino。用同一份三部视频的样例库，在 Mac 上复现了四个等待。返回首页反复解码刚看过的封面，拖动进度条要松手才有新画面，搜索输入框已经取得焦点时整页仍在淡入，首次打开窗口时资料库要约五秒才可用。此修复使用分支 `perf/desktop-interaction-latency`，依赖[上游观看工作流 PR #186](https://github.com/owariband/Seekino/pull/186) 的桌面入口，合并时应先集成上游。

# 2. 影响因素、假设与评价指标

| 操作 | 0.2.14 基线 | 验收方法 |
| --- | --- | --- |
| 反复从同一系列返回首页 | 三张卡片和主图每次解码四次，后三次全部就绪中位数 208 ms。诊断进程复用解码画面后约 50 ms | 同样窗口和素材，重复访问命中缓存时原片解码计数为零，耗时低于基线。播放期间保存进度应无需重新提取隐藏封面 |
| 拖动时间轴 | 拖动中没有目标帧，松手到帧可用的三个样例中位数为 44–96 ms | 按住滑块跨多个位置，在松手前看到目标帧；松手处正确，连续操作不会排队播放旧预览，原播放状态、倍速和命中范围正确 |
| 打开搜索 | 5 次取得焦点用 0.9–9.1 ms，淡入接近结束的中位数 294 ms | 在相同窗口测近乎不透明的耗时，目标低于 160 ms；输入首字及后续字符都保留，系统减少动态效果仍可用 |
| 启动 | 开始创建窗口至资料库就绪约 4.8–5.3 s，首次载入后端模块 3.4–3.8 s | 新进程重复打开三部视频资料库，沿用真实就绪信号，记录启动减少的时间以及首次调用相关能力的成本 |

# 3. 改造方案与建模

按资料库、媒体验证结果、目标时间和尺寸复用已有封面，限制内存，回到首页再取最新续看位置。播放器使用现有进程内 FFmpeg 解码，在指针移动时合并过时的预览请求，松手时提交最终位置。打开搜索时立即交付可见输入区域，并保留短过渡。对启动先定位不属于打开资料库的依赖，再决定延迟加载或预编译的范围。

# 4. 对照实验与结果分析

用同一台 Mac、1080 × 700 窗口和独立样例库复测。封面就绪、解码帧可用、Qt 提交帧、取得焦点各有不同起止点，分别计时。实际比较数据待补充。用正常桌面入口复查导入、续看、命中跳转、片内查找和引用问答，另外检查 Ark 与 OpenAI 兼容协议、离线回放和已有库恢复。

# 5. 试点验证与方案取舍

在新签名的 Mac 包上走通上述交互，检查包内业务资源与 Windows 包的一致性，再安装到本机原资料库。记录本机实际可验证的窗口、数据和系统。若出现旧帧覆盖、错集、漏字、破坏资料库或现有播放能力退化，候选包须先修复。
