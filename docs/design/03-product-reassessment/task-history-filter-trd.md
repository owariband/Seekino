# 1. 问题与现状

日期：2026-10-30。分支：`fix/task-history-filter`。PR：创建后回填。

用户在任务页把 Karpathy 历史失败版本误认成当前任务失败，且找不到重试按钮。TasksPage 获取所有分页与版本，却只允许最新版本操作；Server 的 can_retry 同样要求 observation.is_latest。最新版本判断已按 videoId/version 实现，但仅用于操作按钮。删除入口以 UploadSession 为粒度，会影响整个视频，不能用于清理一条历史记录。

范围：默认仅显示各视频最新任务，提供当前／历史／全部版本筛选与历史说明；保留记录和既有操作权限，不增加删除接口、不修改解析执行。

# 2. 影响因素、假设与评价指标

假设：版本与状态分开筛选，可避免把已被替代的失败误认为当前失败。列表已通过 listAllVideoParseTasks 获取完整分页，可复用现有最新版本映射；必须先算全量最新版本，再应用状态筛选。

| 指标 | 基线 | 目标 | 验证 |
| --- | --- | --- | --- |
| 默认历史失败卡片 | 混在列表 | 0 | 同视频多版本组件测试 |
| 历史可追溯 | 可见但无明确解释 | 历史筛选可见版本与替代说明 | 组件测试、页面检查 |
| 当前失败重试 | 服务授权时可操作 | 保持 | 原回归 |
| 分页与筛选 | 全分页加载 | 最新成功不能被旧失败状态替代 | 跨页测试 |

# 3. 改造方案与建模

前端复用全量任务的 latestVersionByVideo，新增版本范围筛选，默认当前任务；范围之后再筛选状态。统计随版本范围更新，不受状态筛选影响。历史卡显示版本与已被新版本替代的说明，并避免通用“请重试”提示误导。保留原操作权限，所有历史操作继续不可用。新增中英文文案，适配窄屏。

# 4. 对照实验与结果分析

计划用同一视频失败 v1、成功或运行 v2，验证默认隐藏旧记录、历史／全部切换、历史失败不提供操作。测试最新版本位于后续分页的情况。修改前后以相同数据比对；结果待测。

# 5. 试点验证与方案取舍

先运行任务页回归和 TypeScript 检查，再构建。可在独立前端连接当前只读任务 API 检查真实列表；不重启解析 Consumer，不触发任务变更。未部署之前不声明用户当前任务页已生效。
