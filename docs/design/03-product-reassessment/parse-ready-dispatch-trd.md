# 3. 改造方案与建模

1. 协调器按解析任务维护已提交块、窗口的成员位和可领取的具体 ID，恢复时用轻量持久状态初始化。第九个不同块提交可开放下一批；窗口位首次齐全可领取 refine；一次 refine 提交新放行的块直接进入 index。三条队列可混跑。仅在数据库提交成功后向下游发布，旧版本、延迟通知及重复通知不能绕过租约、暂停、到期、ASR、声纹或各阶段容量。
2. 分发按 ID 校验并领取。数据库继续序列化实时与后台共享的容量。零间隔跳过派发时间写入，非零时保留跨消费者间隔。重试持久化后按到期时间派发，重启或进程外改动通过恢复扫描发现。
3. 缩小成果提交事务读取和锁定的窗口集合。摘要在末窗口就绪后读取完整输入并复核指纹；索引先核验发布、生成代和内容版本，收尾只使用任务状态与版本。租约回收按到期节奏运行，协调器退出后仍能完成或恢复。
4. 仅调短轮询或提高并发不能消除重复读取；搬迁向量/计时数据需要迁移历史记录。先采用具体 ID 和 SQL 状态投影，复用当前表和恢复协议。

# 5. 试点验证与方案取舍

先用隔离队列验证混合阶段、版本重建、租约失效和多消费者共享容量。以同一视频、并发、embedding/ES 配置比较索引吞吐、空槽和收尾，分别记录模型请求用时及整体时长；保持原结果可用。状态遗漏、提前完成或出现重复索引时暂停推广，通过持久状态恢复。模型费用、真实 ES 可见性和持续运行效果按实际覆盖报告。
