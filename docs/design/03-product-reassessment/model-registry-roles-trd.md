# 1. 问题与现状

工作分支 `feat/model-registry-roles`，依赖 [模型设置 #74](https://github.com/owariband/Seekino/pull/74) 的 YAML 编辑、密钥保护和 cloud 权限。首个提交为本文，PR 创建后回填。聊天设置能够登记连接，画面解析、转写、OCR、向量和重排仍靠运维编辑具名绑定。相同模型使用两把 Key 时，用户需要按连接区分计费和用途。

# 2. 影响因素、假设与评价指标

| 因素 | 原状 | 验收 |
| --- | --- | --- |
| 协议、凭据与模型能力 | 网页只投影可聊天的模型 | 同地址的两个连接可登记同一模型并独立保存凭据，一个连接可登记多个模型 |
| 配置用途 | 界面只能选择对话模型 | 六个用途仅列实际支持的候选，保存后可从同一 YAML 独立加载 |
| 真实调用 | 保存模型名无法证明请求用到指定配置 | 用隔离的模型服务核对正常 Gateway 调用、模型 ID 与认证，验证解析默认值和索引合同 |
| 安全与兼容 | 上游屏蔽游客访问并保护密钥 | 老配置与会话仍可用，cloud 游客无法读取或修改注册与用途，旧修订不覆盖新修改 |

# 3. 改造方案与建模

设置分为模型服务和模型用途。连接保存协议、地址和凭据，注册的模型用稳定引用区分来源和能力。延用 `model_sources` 和 `models`，用途选择以引用写入部署 YAML。聊天选择器复用兼容的候选，只在用户选定的会话上保存覆盖。服务端验证模型种类、图片输入、认证状态及向量维度，解析快照保留任务已选的绑定。页面区分已保存的默认值与尚需重启或重建索引的变更。

# 4. 对照实验与结果分析

计划以相同模型 ID 在两条合成连接上产生可区分的请求，分别选择聊天和解析。验证自定义转写、嵌入、OCR 和重排的候选过滤与实际调用，测试手填模型 ID、获取列表、切换默认、恢复默认、权限及修订冲突。

# 5. 试点验证与方案取舍

使用独立配置、合成凭据和本机测试服务。前端从设置、聊天打开设置和窄屏入口复核，比较页面选中项与文件及运行时合同。保留开发机已有部署配置和 Kino 界面改动。
