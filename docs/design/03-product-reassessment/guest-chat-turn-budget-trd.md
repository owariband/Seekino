# 1. 问题与现状

2026-11-10 23:21（UTC+8），公开课程的游客询问当前视频讲了什么。CPU 日志与用量账本显示，同一条消息的四次 DeepSeek 调用都成功，大纲和五段源证据也已读取。第四轮提交了一个片段，再次调用模型前执行器终止，整轮用时 13.977 秒。请求已经通过每日额度检查。游客在同一会话的下一问用两次模型调用完成。

分支 `fix/guest-chat-turn-budget` 面向 `dev`，先合入修复，再通过独立发布 PR 同步到 `main`。沿用[用户与租户合同](../02-agent-harness/user-tenant-trd.md)的请求准入与并发控制。PR 创建后回填链接。

# 2. 影响因素、假设与评价指标

| 指标 | 旧行为 | 验收条件 |
| --- | --- | --- |
| 游客消息选项 | 在全局预算之上将模型默认值与最高值压到 4，工具压到 8 | 展示 Chat Service 的默认值和最高值，默认发送与合法自选值进入实际执行 |
| 已获准的回答 | 固定四轮工具调用后，第五次模型调用被拒 | 使用有六次模型预算的同一脚本，能执行第五次调用并收尾 |
| 服务端校验 | 游客的超大请求被静默压低 | 遵守与普通云端 Chat 相同的上界校验 |
| 访客请求次数 | Chat 和搜索按 IP 共用窗口，默认 20 次 / 86400 秒 | 窗口用尽返回 429，已有并发、鉴权和资料范围校验继续生效 |

# 3. 改造方案与建模

移除消息选项和发送入口各自的游客模型、工具预算裁剪。发送入口传递可选参数，由已有 Chat Service 统一解析默认值、验证上界，然后交给 Supervisor。停用 `SEEKINO_AUTH_GUEST_MAX_MODEL_CALLS`，旧部署即使保留这项设置也能启动。日额度继续来自 AuthConfig，经 Redis 在请求开始前预留。没有数据库迁移。单轮使用更多证据可能增加模型调用，普通 Chat 的单轮预算及执行超时继续约束成本。

# 4. 对照实验与结果分析

固定模型、工具顺序与配置，对照旧预算 4 与服务默认 6。通过隔离 cloud HTTP 用例检查访客可见选项、实际默认与显式预算、越界请求，以及下游查询与 Supervisor 的预算。用独立 Redis 验证相同 IP 的额度、到期及并发释放。结果待测。

# 5. 试点验证与方案取舍

在 CPU 上核对发布镜像 SHA、公开站点、游客消息选项，以及按同一公开课程发送一条概览提问的终态。已发布的内容保留原片、数据库和索引，API 替换后验证已有模型通道。发布检查失败时使用前一可用镜像。真实模型每轮选择的工具数量可能变化。
