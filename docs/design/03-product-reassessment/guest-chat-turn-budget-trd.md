# 2. 影响因素、假设与评价指标

| 指标 | 旧行为 | 验收条件 |
| --- | --- | --- |
| 游客消息选项 | 在全局预算之上将模型默认值与最高值压到 4，工具压到 8 | 展示 Chat Service 的默认值和最高值，默认发送与合法自选值进入实际执行 |

| 访客请求次数 | Chat 和搜索按 IP 共用窗口，默认 20 次 / 86400 秒 | 窗口用尽返回 429，已有并发、鉴权和资料范围校验继续生效 |

# 3. 改造方案与建模

移除消息选项和发送入口各自的游客模型、工具预算裁剪。发送入口传递可选参数，由已有 Chat Service 统一解析默认值、验证上界，然后交给 Supervisor。停用 `SEEKINO_AUTH_GUEST_MAX_MODEL_CALLS`，旧部署即使保留这项设置也能启动。云端把全局 Agent 运行设置独立保存。首次启动从当前模型文档中只承接其他运行参数，以程序常量为模型及工具设置 100 次的默认值和上界。管理员仍可通过全局 Agent 设置调整，保存时只写运行文件。日额度继续来自 AuthConfig，经 Redis 在请求开始前预留。没有数据库迁移。单轮使用更多证据可能增加模型调用，普通 Chat 的单轮预算及执行超时继续约束成本。

# 4. 对照实验与结果分析

固定模型、工具顺序与配置，对照旧预算 4 与服务默认 6。通过隔离 cloud HTTP 用例检查访客可见选项、实际默认与显式预算、越界请求，以及下游查询与 Supervisor 的预算。实际执行同一组大纲、五次证据读取、一次片段提交，预算 4 时四次模型调用成功，第五次前出现 `LOOP_LIMIT`；预算 6 时第五次生成最终回答，两组各执行七次工具。模型响应使用脚本替身，Gateway 和工具循环实际运行。

旧实现四个 HTTP 对照用例均失败。修复后游客看到模型默认 6、最高 12，工具默认 24、最高 48。省略参数和显式选择 5/9 均传到执行器，分别超过模型或工具最高值均返回 400。云端访问、实际 Supervisor、Chat Service 与 Gateway 等七个测试文件共 361 项通过、8 项跳过。另用本机独立 Redis 7.4.2 跑额度和鉴权两个测试文件，54 项全部通过，覆盖按 IP 跨身份计数、窗口到期、并发与异常释放。两组含重合用例。需独立 MySQL 的并发测试尚未执行。

100/100 对照从与生产一致的旧预算启动。8 个并发读取只初始化一个私有运行文件，四个预算均为 100。管理员调低工具默认值后，其余参数和模型文件字节保留；再改旧文件的模型预算不能覆盖新设置。HTTP 验证默认 100/100、显式 100/100、显式 5/9 以及 101 的拒绝。复放同一故障序列，预算 100 在第五次模型调用生成最终回答，工具仍执行七次。12 个文件的回归中，Gateway 有三项关于仓库模型模板的断言在修改前后同样失败，独立 MySQL 并发用例跳过。

# 5. 试点验证与方案取舍

生产试点还将读取游客默认和上限的全部四个数字，检查一次公开课程回答。随后在 CPU 上核对发布镜像 SHA、公开站点、游客消息选项，以及按同一公开课程发送一条概览提问的终态。已发布的内容保留原片、数据库和索引，API 替换后验证已有模型通道。发布检查失败时使用前一可用镜像。真实模型每轮选择的工具数量可能变化。
