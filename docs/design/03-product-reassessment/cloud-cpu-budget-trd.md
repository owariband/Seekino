# 1. 问题与现状

**4 核 CPU 主机的容器预算与远端 CUDA 接入**，2026-11-07。分支 `perf/cloud-cpu-resource-budget`，PR 在创建后回填，目标分支 `dev`。承接已集成的[云端部署设计](cloud-docker-deploy-trd.md)及 [PR #57](https://github.com/owariband/Seekino/pull/57)。本次交付生产 Compose、CPU 宿主端模型接线和解析准入，可独立于队列性能优化 [PR #70](https://github.com/owariband/Seekino/pull/70) 集成。

CPU 主机现有 4 个逻辑核、7,429 MiB 内存。只读采样中 MemAvailable 为 4,349 MiB，API 容器使用约 266 MiB，ES 约 1.52 GiB，MySQL 约 524 MiB。API 和 ES 的 Docker 硬内存限制均为 0，主机自启动以来 OOM kill 为 0。此前 Mac 上三集同时有 5 个理解任务和 8 个 Refine 窗口，单次理解的图像编码量中位约 21 MiB。这些样本说明在哪里会产生负载，Linux 并行整集的峰值待测。

生产环境从私有 env 派生，上游 Compose 的并发默认值可能被本机的 3/10/10 覆盖。[队列](../../../server/mq/video_parse_queue.py)还按各视频固化的配置发放子租约。CPU 机负责 HTTP、媒体、队列、MySQL、ES 与 Redis。GPU 机承载 WhisperX、Qwen embedding 和 StartLux，视觉、对话和查询改写沿用已有远端 API。CPU 配置交付与线上容器切换、GPU 部署分别验收。

# 2. 影响因素、假设与评价指标

| 指标与口径 | 基线 | 本次目标和测法 |
|---|---|---|
| 常驻容器内存硬上限之和 | API、ES 均无硬上限 | 常驻总额不超过 5.75 GiB，额外计入一次初始化仍给宿主留至少 1 GiB，核对合并 Compose |
| CPU 配额之和 | 主服务共享宿主 | 常驻总额至多 3.75 核，为 API/FFmpeg、SQL 与索引分别设配额 |
| 解析竞争 | 视频快照可允许 10 路及以上 | 同时准入新视频 1 个。生产库中理解、Refine、索引的在途子租约合计至多 2 个，覆盖恢复及实时领取。用隔离库验旧快照、竞争和释放 |
| 远端模型入口 | 云端公开模板使用 Ark ASR/向量和 Jev | 从模板走三个实际适配器核对 URL、请求、路由及向量合同，视觉与对话继续走原绑定 |
| 用户负载下的存活与进度 | Linux 三集对照待测 | 同配额隔离部署提交三个代表视频，同时访问健康和检索，任务最终可搜索。观测 `memory.peak`、OOM 计数增量、容器重启和完成耗时 |

# 3. 改造方案与建模

生产叠加文件限定各服务的 CPU、内存及 swap，ES 堆维持 1 GiB 并在容器内留出堆外空间。单独给一次性初始化预算。生产配置固定低并发，关闭调试媒体正文跟踪。通过已有数据库领取事务增加可选的在途子租约总数限制，覆盖显式上传配置及旧任务，保持内容、帧率、版本、重试规则与索引合同。其他部署沿用原策略。

采用 Gateway 已有的音频转写和 llama.cpp 向量 HTTP 协议。沿用已有样例索引对应的文本模型、1,024 维和查询指令。StartLux 使用 GPU 上的 Decision 服务，通过 HTTPS 的 `/v1/systemone` 发送同一组路由问题，4B AutoThink 使用 `think_mode=never`。既有 Jev 配置继续按原协议发送。CPU 容器不启动模型进程。

# 4. 对照实验与结果分析

计划使用同一份仅含占位凭据并含高并发值的 env 分别渲染基础 Compose 和生产叠加文件。核算 cgroup 上限、实际应用环境、端口与容器依赖。再用高并发冻结任务及多个消费者验证容量与恢复，通过 Gateway 传输测试区分 Jev 与 StartLux 请求。静态合同和模拟传输的结果分别记录。

# 5. 试点验证与方案取舍

在相同 CPU/内存配额、隔离的业务库及 ES 索引上，由部署维护者用真实 GPU 私有地址先接通三个服务，再跑一集、同时提交三集。记录初始/结束 OOM 与重启数、任务可检索状态及每集耗时。若租约饥饿、容器被杀或前台请求持续不可用，保留证据并回退本次部署配置。限制并发预期牺牲批量吞吐，实际代价待测。
