# 1. 问题与现状

2026-11-07，分支 `perf/frame-link-lease-checks`，目标 `dev`，[PR #75](https://github.com/owariband/Seekino/pull/75)。MyGO 第 3 集在 `19054aad` 上的 30 个主理解请求共使用了 5,931 张已抽取的帧图。把一块的 198 帧和一份音频硬链接到 worker 临时目录时，实测取得 200 次父行锁、200 次子行锁。媒体服务对每个文件调用 `check_active()`，实际执行的是 chunk 续租事务。这个成本随文件数增长。[上游解析调度设计](parse-ready-dispatch-trd.md) · [已合入的 PR #70](https://github.com/owariband/Seekino/pull/70)

# 2. 影响因素与指标

对已发布清单、有效租约下的一次 `use_episode_chunk` 调用计数。1 帧加音频的基线为 3 次租约检查，198 帧加音频为 200 次。目标是两组都恰好检查两次。核对硬链接的源文件、帧顺序和时间戳，并验证在链接期间失去租约时，调用方拿不到这批媒体。

# 3. 改造方案

沿用清单就绪后的第一次租约检查。把循环里的检查移到最后一次 `os.link` 成功之后、`yield PreparedVideoParseMedia` 之前。末次检查失败时，由现有 workspace 上下文清理本次临时链接。失租后可能继续完成这批本地硬链接，交付前的检查负责拦截。等待清单时仍检查消费者和准备者，运行期间由既有定时心跳维护租约。

# 4. 对照实验

在 `19054aad` 和 `be8d4d5d` 上各测五轮，逐轮交换运行顺序。macOS arm64、专用 MySQL 8.4.13 Unix socket、真实队列租约和硬链接。每组清单有一份音频以及 1 或 198 个独立帧文件。计时从进入 `use_episode_chunk` 到取得媒体，逐个核对帧时间、次序及指向的源文件。

| 已备输入 | 指标 | 改前 | 改后 |
| --- | --- | ---: | ---: |
| 1 帧 + 音频 | 父行 / 子行加锁次数，每轮 | 3 / 3 | 2 / 2 |
| 198 帧 + 音频 | 父行 / 子行加锁次数，每轮 | 200 / 200 | 2 / 2 |
| 198 帧 + 音频 | 该调用中的全部 SQL，每轮范围 | 566–587 | 6 |
| 198 帧 + 音频 | 子租约 UPDATE，每轮范围 | 166–187 | 2 |
| 198 帧 + 音频 | 交付耗时，中位数 | 174.316 ms | 42.450 ms |

[逐轮数据](../../report/server/service/frame-link-lease-checks-20261107.jsonl)记录两侧提交号、耗时及 SQL 计数。原始探针、调用命令和测试日志在本地 `outputs/verification/frame-link-lease-checks-20261107/`。

# 5. 试点与取舍

在最后一个硬链接创建后调用正式暂停接口，撤销数据库里的 chunk 租约，再观察媒体是否交给调用方。改前 5/5 次交出了旧租约的媒体，改后 5/5 次在交付前抛出失租异常，临时链接全部清理，源文件可读。后续模型准入和正式结果提交另有各自的校验边界。

# 6. 验收

两种输入每轮都只取得两次父行锁和两次子行锁。新增的检查时机与失租断言在原实现上失败，调整后通过。媒体、worker、队列、暂停、派发与持久化回归共 518 项通过，另有 31 项真实 MySQL 用例通过。批次交付的验收达到目标，整集耗时需要完整成功的解析另行测量。[Devlog](../../dev/devlog.md#devlog-frame-link-lease-20261107) · [工作台](../../dev/workbench.html)
