 对，顺序就应该这样：

  > 产品定位可以从一开始就是多用户动画检索平台，但第一阶段先完成本地单用户的端到端闭环。

  这两件事不矛盾。产品定位决定未来架构边界，MVP 决定现在优先验证什么。

  ## 第一阶段真正要验证的核心

  不是注册登录，也不是 RocketMQ，而是这条链到底能不能成立：

  导入一部动画的 3～5 集
          ↓
  识别剧集与视频信息
          ↓
  生成 VideoChunk、抽帧、提取语音文本
          ↓
  生成 VideoChunk 解析信息
          ↓
  构建文本、视觉、事件索引
          ↓
  输入：“惊世一跪是什么？”
          ↓
  召回候选 VideoChunk
          ↓
  返回：
  第几集 + 时间戳 + 关键帧 + 文本证据
          ↓
  点击结果，播放器跳转到对应位置

  只要这条链还没有跑通，用户系统、MQ、Redis、MinIO 都只是在外围搭架子，不能证明 AniVAG 的核心价值。

  而且第一版措辞最好叫：

  > 动画名场面自然语言召回与定位

  暂时不要叫“自动识别名场面”。因为“识别”容易被理解成系统会自动判断整部动画里哪些 VideoChunk 算名场面；我们的第一版主要是用户带着一个模糊概念来查询，然后系统定位证
  据。自动发现与名场面热度排序可以作为后续能力。

  ## 本地 MVP 不等于写一个一次性脚本

  虽然第一阶段不做多用户，但仍然要有一个最小产品壳：

  Web 前端
     ↓
  AniVAG API
     ↓
  本地 Job Worker
     ↓
  VideoRAG Adapter
     ↓
  本地视频 / 索引 / 元数据

  第一版至少应该有：

  - 动画库页面
  - 导入本地视频
  - 剧集列表
  - 建库任务进度
  - 搜索输入框
  - 召回结果卡片
  - 集数、时间戳、关键帧和证据文本
  - 点击后跳转播放
  - 失败信息与重新执行

  这已经是一个完整产品，而不只是运行 VideoRAG 示例代码。

  ## 第一阶段暂时不要做的东西

  先不做：

  - 注册登录
  - 用户角色与权限
  - 手机验证码
  - OAuth
  - 会员系统
  - RocketMQ
  - 分布式锁
  - MinIO 集群
  - 管理后台
  - Kubernetes
  - 多租户计费
  - 大规模视频调度

  因为这些都不能回答最关键的问题：

  > 用户输入“惊世一跪”，系统究竟能不能找对 VideoChunk？

  我们必须优先把这个结果展示出来。

  ## 但可以提前留一个很轻的多用户边界

  不需要开发用户系统，但数据模型不要彻底写死成全局单例。

  可以从一开始设置一个默认工作空间：

  workspace_id = "local-default"

  核心对象按下面组织：

  Workspace
    └─ Series
         └─ Video
              └─ VideoChunk
                   ├─ IndexJob
                   └─ VideoChunkEvidence

  本地版本只有一个：

  Local Default Workspace

  将来多用户版本变成：

  User
    └─ Workspace
         └─ Anime Library

  这样后续只是增加：

  - User
  - WorkspaceMember
  - 资源鉴权
  - 存储隔离
  - 配额

  不需要推翻动画、剧集、索引、证据这些核心模型。

  不过也不要为了所谓“未来扩展”给每一张表塞十几个租户字段。第一版只保留一个明确的 workspace_id 边界就够了。

  ## 推荐的开发阶段

  ### M0：算法底座跑通

  目标：确认上游 VideoRAG 真能服务我们的场景。

  本地视频路径
    → VideoRAG 建库
    → 自然语言查询
    → 候选 VideoChunk

  用 3～5 集动画验证：

  - 中文查询是否能工作
  - 动画画面描述是否足够准确
  - ASR 是否能正确处理角色对白
  - 召回能否定位到正确剧集
  - 时间戳误差有多大
  - 上游返回的数据能否转换成产品需要的证据格式

  这一阶段甚至可以用命令行，但必须留下真实结果和 Bad Case。

  ### M1：本地端到端产品

  目标：做出可以录视频、发 B 站和小红书的版本。

  导入动画
    → 展示建库进度
    → 输入名场面描述
    → 返回候选结果
    → 点击跳转播放

  这时增加：

  - Web UI
  - AniVAG 后端
  - VideoRAG Adapter
  - 本地持久化
  - 基础 Job 状态机
  - 错误展示
  - 结果证据卡片

  这是第一个真正可以传播的版本。

  ### M2：检索质量与评测

  目标：让项目不只是“看起来能跑”，而是能够回答面试官的算法问题。

  建立 20～30 条人工 QA：

  - MRR
  - 查询延迟
  - 每集建库时间
  - 每小时视频的 API 成本

  然后做对比：

  仅语音文本
  仅视觉描述
  文本 + 视觉
  文本 + 视觉 + 事件索引

  这才形成真正的算法含金量。

  ### M3：多用户平台化

  核心闭环被证明以后，再做：

  用户注册登录
      ↓
  Workspace 隔离
      ↓
  视频上传到 MinIO
      ↓
  创建持久化任务
      ↓
  RocketMQ 分发
      ↓
  多个 Index Worker 消费
      ↓
  Checkpoint 与失败恢复
      ↓
  SSE 推送进度

  这一阶段增加：

  - Spring Security/JWT
  - User/Workspace
  - MinIO
  - MySQL
  - Redis
  - RocketMQ
  - 分布式限流
  - 幂等消费
  - 死信队列
  - 管理员重放
  - 存储配额和模型调用配额

  这时才有足够真实的业务理由使用这些组件。

  ## 最关键的优先级

  应该保持这个顺序：

  1. 找得到
  2. 找得准
  3. 展示得爽
  4. 任务跑得稳
  5. 支持多人使用
  6. 支持大规模处理

  不能倒过来变成：

  先登录注册
  → 再 Redis
  → 再 RocketMQ
  → 再 MinIO
  → 最后才发现“惊世一跪”根本召回不出来

  所以我们现在的第一目标非常明确：

  > 先在本地跑通“动画导入 → 建库 → 名场面召回 → 时间证据 → 点击跳转”的完整纵向切片。

  产品对外可以从第一天就叫“面向多用户动画内容库的名场面检索平台”，但开发上先用一个 local-default Workspace 承载单用户。等检索效果和演示成立，再把它扩展成真
  正的多用户、异步、分布式平台。
