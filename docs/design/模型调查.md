# AniVAG 模型调查

> 最后更新：2026-09-13  
> 当前状态：Qwen3-VL-8B 与 MiniCPM-V 2.6 已完成同 Schema 的 VideoRAG 15×3 中性证据 A/B；MiniCPM 质量未过线，主模型仍未定案。

除另有说明外，外部资料访问日期与“最后更新”日期相同。

本文调查 AniVAG 的“有序抽帧 + 时间标签 + 候选 ASR/字幕 → 事件级 JSON 时间线”模型。调查重点是 VideoRAG 使用的 `MiniCPM-V-2_6-int4`，以及可自托管的 Qwen3-VL 8B/30B 档位。

文中严格区分：

- **官方事实**：官方仓库、模型卡或论文明确给出的信息。
- **当前仓库事实**：AniVAG 或内置 VideoRAG 源码中能直接验证的行为。
- **工程判断**：基于权重体积、输入长度和当前机器的可行性推断，不代表官方性能承诺。
- **待实测**：不写猜测的 token/s、峰值内存或动画质量结论，由固定样本 A/B 填写。

## 1. 当前结论

1. **VideoRAG 的 MiniCPM-V 2.6 已作为 Mac GGUF 基线实测，但不适合成为 AniVAG 当前生产降级模型。** 它小、快、三组都能返回合法 Schema，但在 45 帧测试里出现严重跨帧字幕涂抹和事实复读：48 条观察只有 9 种视觉事实、30 个非空字幕只有 6 种文本。VideoRAG 使用它不等于它适合完整 VideoChunk 的稠密事件抽取。
2. **`Qwen3-VL-8B-Instruct` Q4_K_M + Q8_0 视觉投影仍是两个本地 8B 候选中质量较好的视觉证据模型。** 官方明确支持动画识别、时间戳对齐和抽帧列表视频输入；本机实际 Ollama blobs 合计约 5.78GB。它的中性证据仍有重复、说话者过度归因和推断，因此也尚未达到正式 Timeline 质量。
3. **`Qwen3-VL-30B-A3B-Instruct` Q4_K_M 是质量升级档，不是默认档。** 只有 8B 在人物连续性、微动作、因果拆分或指令遵循上不足时才测。A3B 节省每 token 的激活计算量，不代表只需加载 3B 权重。
4. **不先下载 BF16/FP8。** 先用体积小、回滚成本低的 Q4_K_M 验证正确的问题；Q4_K_M 若已不达标，再判断是量化损失还是模型规模不足。
5. **自托管只移除供应商外层 `content_filter`，不保证质量或绝对不拒答。** 结构化解码只保证 JSON 形状，事件事实、时间边界和人物归属仍由 AniVAG Engine 校验。

## 2. AniVAG 的实际负载

这不是普通的单图问答，也不要求模型直接解码原始视频。单次分析需要：

- 按时间严格递增的 15 或 33 张动画抽帧；
- 每帧的 AnalysisWindow 相对毫秒标签；
- 候选 ASR/烧录字幕文本，且必须记录该次 ASR 是否为空；
- 人物、动作、对话、镜头、歌曲等细粒度事件；
- 符合现有 Pydantic Schema 的 JSON；
- `0 <= start_ms < end_ms <= duration_ms`、时间单调、点事件 `+1ms` 等本地约束。

任何抽帧模型都不能为未抽到的瞬间提供直接视觉证据，也不能从静态图片恢复纯语音；基于上下文的猜测不得当作 observed event。因此帧密度与 ASR 仍是独立证据通道，模型替换不能取代它们。

## 3. VideoRAG 实际依赖什么

VideoRAG 靠的是“粗索引 + 查询时精读”，而不是让一个视频大模型完整理解每一秒：

```text
视频
  → 30 秒输入窗口
  → 均匀抽 5 帧 + Whisper ASR
  → MiniCPM-V 2.6 生成粗描述
  → ImageBind 视觉向量 + 文本/知识图谱索引
  → 查询召回候选窗口
  → 候选窗口均匀抽 15 帧 + transcript
  → MiniCPM-V 2.6 生成精描述
  → 文本 LLM 组织回答
```

| 组件 | VideoRAG 默认选择 | 作用 | 是否本地 |
| --- | --- | --- | --- |
| 画面描述 | `MiniCPM-V-2_6-int4` | 粗/精粒度 frame caption | 是 |
| 语音识别 | `faster-distil-whisper-large-v3` | transcript | 是 |
| 视觉检索 | ImageBind Huge | 视频窗口/查询跨模态向量 | 是 |
| 文本推理 | GPT-4o/GPT-4o-mini，也有 DeepSeek/Ollama 配置 | 实体抽取、图谱与最终回答 | 可本地或 API |

当前子模块源码可直接验证：

- `videorag.py:65-74`：30 秒输入窗口，粗解析 5 帧，精解析 15 帧。
- `README.md:91-109`：下载 MiniCPM-V 2.6 INT4、Distil-Whisper 和 ImageBind 三套权重。
- `_videoutil/caption.py:9-86`：帧统一缩放到 1280x720，按顺序与 transcript 一起送入 MiniCPM，输出自由文本 caption。
- `_videoutil/feature.py`：使用 ImageBind 生成视觉/文本特征。
- `_llm.py:157-196`：默认文本 LLM 配置是 GPT-4o/GPT-4o-mini，不是 MiniCPM 包办整条链路。

还要注意以下边界：

- VideoRAG 保存了抽帧时间作为检索元数据，但没有将每帧的绝对时间标签送给 MiniCPM；模型只知道顺序。
- VideoRAG 的目标是召回和问答，不是整集稠密事件时间线。其小模型结论不能无条件外推到 AniVAG。
- VideoRAG 官方只说明在英文环境测试过，caption prompt 也硬编码要求英文输出；日语动画还要同时验证 OCR、Whisper 语言配置和下游英文 caption 的信息损失。
- 参考实现把每帧直接 resize 到 1280×720，并设置 `max_slice_nums=2`、`use_image_id=False`。这可能压缩小字幕、拉伸非 16:9 画面，也减少“描述绑定第几帧”的显式锚点。
- 官方所说 RTX 3090 24GB 足够，指 MiniCPM、Whisper、ImageBind 等完整索引流水线；MiniCPM BNB INT4 模型卡约 7GB 显存是单模型口径，两者不能互换。

官方论文与实现：[VideoRAG 论文](https://arxiv.org/pdf/2502.01549) · [HKUDS/VideoRAG](https://github.com/HKUDS/VideoRAG)

## 4. 本地候选模型比较

### 4.1 资源与部署

> 权重/下载文件体积 **不等于** 峰值运行内存。实际运行还需要 KV cache、计算 buffer、视觉 token、图片解码、推理服务和操作系统内存。

| 候选 | 官方文件/资源信息 | 当前 M5 Pro 48GB | 建议 |
| --- | --- | --- | --- |
| MiniCPM-V 2.6 BNB NF4（int4） | 约 5.97GB 权重；官方标称约 7GB NVIDIA 显存 | 不能直接沿用 VideoRAG 锁定版本的 CUDA/bitsandbytes 路径 | 不作 Mac 直接候选 |
| MiniCPM-V 2.6 GGUF Q4_K_M | 官方文件约 4.68GB 语言模型 + 1.04GB mmproj；本机 Ollama 显示下载 5.7GB | **实测加载 6.7GB、100% GPU 层放置、32K context，容量很充足** | 仅保留 VideoRAG 世代基线；当前质量失败 |
| Qwen3-VL-8B-Instruct Q4_K_M | 本机已下载 5.03GB 语言模型 + 0.75GB Q8_0 mmproj，合计约 5.78GB；官方另有约 1.16GB F16 mmproj | **实测 Ollama 已加载大小约 15GB、100% GPU 层放置、64K context，容量可行** | 当前两个本地 8B 中质量较好，但仍非正式事实生成器 |
| Qwen3-VL-8B-Instruct BF16 | 官方仓库约 17.5GB | 容量上大概可行，但比 GGUF 路径更挑框架/内核 | Q4_K_M 质量疑似受量化影响时再测 |
| Qwen3-VL-30B-A3B-Instruct Q4_K_M | 18.6GB 语言模型 + 1.08GB F16 mmproj，合计约 19.68GB | **条件可行**；需限制 context/视觉 token 并实测 | 8B 不达标后的质量升级档 |
| Qwen3-VL-30B-A3B-Instruct FP8 | 官方仓库约 32.3GB | 不建议；官方主路径是 vLLM/SGLang + CUDA | 留给 48GB+ NVIDIA 服务器 |
| Qwen3-VL-30B-A3B-Instruct BF16 | 官方仓库约 62.2GB | 权重本身已超 48GB，不可行 | 80GB 级 GPU 或多卡的部署档 |

对 Qwen 的“高置信可行/条件可行”是容量层面的工程判断，不是官方 M5 Pro 性能数据。官方没有发布“48GB M5 Pro + 33 帧 + 长 JSON”的峰值内存和速度。

### 4.2 任务能力

| 维度 | MiniCPM-V 2.6（底模能力；BNB NF4 / GGUF Q4_K_M 后端另测） | Qwen3-VL-8B | Qwen3-VL-30B-A3B |
| --- | --- | --- | --- |
| 世代/定位 | 2024，已列为 Legacy Model | 当代中型多模态模型 | 当代 MoE 质量升级档 |
| 顺序多帧 | 支持有序 PIL Image 列表；官方视频示例将采样 cap 设为 64 帧 | 支持多图，也支持将已抽帧列表作为 `video` | 同 8B |
| 时间对齐 | 知道顺序，但官方示例没有每帧绝对时间语义 | `sample_fps` + 时间 token；非均匀帧仍应显式传真实时间 | 同 8B |
| 上下文 | 配置上限 32K | 原生 256K，可扩展到 1M | 原生 256K，可扩展到 1M |
| 视觉压缩 | 官方称 1.8M 像素图约 640 visual tokens | 应通过分辨率/`total_pixels` 约束总视觉 token | 同 8B，但语言侧权重更大 |
| Anime 证据 | 官方未做动画专项承诺 | 官方明确列出 anime recognition | 同 8B |
| 日文字幕 | 官方多语列表未明确列日文；必须实测 | Qwen3 文本底座支持日文；VL 报告评测 39 种 OCR 语言，其中 32 种准确率超过 70%；动画小字仍必须实测 | 同 8B；更大语言模型不代表小字像素一定更清晰 |
| 严格 JSON | 官方 Transformers `model.chat` 与 VideoRAG 原实现没有约束解码；GGUF 后端可另加 grammar | 依赖 llama.cpp/vLLM 约束解码 + Pydantic 二次校验 | 同 8B |
| 预期优势 | 资源占用低，已有 VideoRAG 参考集成 | 新一代时序/动画能力，资源低 | 更可能改善跨帧整合、人物连续性和复杂事件拆分 |
| 主要风险 | 旧、无精确时间语义、日文未验证；BNB 与 GGUF 的质量/多帧 parity 未验证 | Q4_K_M 可能损失小字 OCR、微动作和复杂 JSON 语义 | 内存带宽、视觉预填充和推理框架可能使 Mac 速度不可接受 |

Qwen3-VL 8B 与 30B 使用同代视觉架构。因此“30B 更可能改善跨帧整合和事件拆分”是合理工程推断，不能写成“30B 一定成比例改善 OCR”。官方也没有 Q4_K_M 在 AniVAG 日文动画时间线上的保真数据。

## 5. 模型详细记录

### 5.1 MiniCPM-V-2.6-int4

**官方事实**

- SigLip-400M + Qwen2-7B，总计约 8B 参数。
- 支持单图、多图和将调用端预先解码/抽取的 PIL Image 列表作为视频输入；支持 spatial-temporal dense caption。它不直接读取视频容器或音轨。
- 支持任意宽高比、最高约 1.8M 像素，官方称该尺寸图片约生成 640 visual tokens。
- BNB INT4 官方标称约 7GB NVIDIA 显存；官方 Transformers 路径明确面向 NVIDIA GPU。
- 已归入 MiniCPM-V 主仓库的 Legacy Models。

**VideoRAG 中的实际行为**

- 默认加载 `./MiniCPM-V-2_6-int4`。
- 图片按顺序送入，`use_image_id=False`、`max_slice_nums=2`。
- transcript 放在文本 prompt 里，输出是硬编码要求英文的自由文本 caption，没有约束解码。
- 抽帧时间留在检索元数据中，未作为每帧标签送入模型。
- 依赖说明锁定 `bitsandbytes==0.43.1`、`transformers==4.37.1`，而 MiniCPM INT4 模型卡的测试版本是 `transformers==4.40.0` 并使用 `trust_remote_code=True`；这不证明必然冲突，但属于复现与代码信任风险。

**AniVAG 判断**

- 33 帧低于官方视频示例设置的 `MAX_NUM_FRAMES=64`；64 是示例的采样保护值，不是模型声明的硬上限，也不能证明 GGUF/llama.cpp 可稳定处理 33 帧。
- 1.8M 像素约 640 visual tokens 是官方给出的单图上界口径，不是每帧固定成本。仅按该上界粗算，33 帧约占 21,120 visual tokens，32K context 只余约 11.6K 给 prompt、ASR 和输出；实际开销受 resize、切片与后端实现影响。
- Mac 不应复制 VideoRAG 的 BNB/CUDA loader，应使用官方 GGUF + llama.cpp/Metal。
- 首先验证 llama.cpp 后端能否在单请求中稳定接收 15/33 张图并保持顺序，再传明确的 `frame_index → relative_ms` 映射；不预设它支持 Transformers 路径的逐图交错文本协议。
- 时间范围和事件归属继续由本地 Engine 处理，不能依赖模型自行校准。
- 它适合作为低成本基线/审核故障备用，不应仅因 VideoRAG 使用它就直接定为主模型。

来源：[MiniCPM-V 2.6 官方归档文档](https://github.com/OpenBMB/MiniCPM-V/blob/main/docs/minicpm_v2dot6_en.md) · [BNB INT4 模型卡](https://huggingface.co/openbmb/MiniCPM-V-2_6-int4) · [GGUF 文件](https://huggingface.co/openbmb/MiniCPM-V-2_6-gguf/tree/main)

### 5.2 Qwen3-VL-8B-Instruct

**官方事实**

- 支持多图，也支持把已抽取图片列表作为 `type: "video"` 输入。
- `qwen-vl-utils` 可根据 `sample_fps` 在帧组前注入时间 token；技术报告描述了 Text–Timestamp Alignment。
- 官方明确列出 anime recognition、原生 256K 上下文和可扩展 1M 上下文；技术报告评测 39 种 OCR 语言，其中 32 种准确率超过 70%，但没有单列动画小字号日文字幕结果。
- 官方 GGUF 可通过 llama.cpp/Ollama 在 Apple Silicon/Metal 路径部署。
- 模型与权重许可证是 Apache-2.0。

**AniVAG 判断**

- 对当前均匀 `1, 3, ..., 65s` 的 33 帧，可按 `sample_fps=0.5` 建立内部时间轴，但必须说明第一帧是 `t=1s`，或在输出后统一加 1s。
- 非均匀关键帧不能只依赖 `sample_fps`；应在每帧前显式写真实毫秒标签。
- “图片列表作为 video + sample_fps”是 Transformers/`qwen-vl-utils` 的官方路径。GGUF/llama.cpp 虽支持多模态和 Metal，不应在未测前假定其时间 token 注入完全等价。保守方案是有序多图 + 显式时间文本标签。
- 官方 GGUF 的 Q4_K_M 是语言模型文件；视觉侧 mmproj 另提供 F16 或 Q8_0。本机 Ollama pull 实际取得的是 Q8_0 projector，不是此前计划的 F16；跨帧整合和文字生成仍经过 Q4_K_M 语言侧，不能据此假定端到端视觉质量等同 BF16。
- Q4_K_M 可能影响小字 OCR、微动作和复杂 schema 的语义正确性，官方没有 AniVAG 场景的 Q4_K_M/BF16 对比数据。

来源：[Qwen3-VL 官方仓库](https://github.com/QwenLM/Qwen3-VL) · [8B BF16 文件](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct/tree/main) · [8B GGUF 文件](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct-GGUF/tree/main) · [Qwen3-VL 技术报告](https://arxiv.org/pdf/2511.21631)

### 5.3 Qwen3-VL-30B-A3B-Instruct

**官方事实**

- 约 31B 总参数的 MoE 模型，A3B 表示每 token 约激活 3B 参数。
- 输入、时间对齐、Anime/OCR 和上下文能力与 Qwen3-VL 同代架构一致。
- BF16 仓库约 62.2GB；官方 FP8 仓库约 32.3GB；Q4_K_M 语言模型加 F16 mmproj 约 19.68GB。
- FP8 官方路径主要面向 vLLM/SGLang + CUDA，不是 Apple Metal 的量化替代。

**AniVAG 判断**

- 30B 更可能改善语言侧的跨帧整合、人物消歧、事件因果和长 JSON 指令遵循；这是待 A/B 验证的工程假设。
- 8B 与 30B 使用同代视觉编码架构，所以 30B 不一定成比例提升小字 OCR 和未抽到的瞬间。
- 当前 48GB Mac 只考虑 Q4_K_M；BF16 权重本身已超过统一内存，FP8 也不是适合的 Metal 路径。
- 不能根据 A3B 假定它与 8B 同速，也不能简单写成“必然慢四倍”；内存带宽、MoE 内核和 33 帧视觉预填充会共同决定速度。

来源：[30B 模型卡](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct) · [30B BF16 文件](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct/tree/main) · [30B GGUF 文件](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct-GGUF/tree/main) · [30B FP8 文件](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct-FP8)

## 6. 当前机器与推理路径

当前开发机是 Apple M5 Pro，48GB 统一内存，不具备 CUDA。

### 模型能力 vs 运行时/API

“Qwen3-VL 支持视频”不等于任意推理服务都能把 MP4 直接传给模型。模型本体不解码 MP4 容器字节；它消费的是运行时已经解码、采样并附带时序信息的视觉张量。是否允许调用方提交 MP4，以及由谁完成抽帧和时间信息构造，取决于模型之外的预处理与服务 API。

| 层级 | 视频输入的实际含义 |
| --- | --- |
| Qwen3-VL 模型 | 具备视频时序理解能力，但不负责解析 MP4 容器。 |
| Transformers + `qwen-vl-utils` | 调用侧可以提供本地视频路径、URL 或已抽帧列表；`qwen-vl-utils` 负责解码和采样，并向 Processor 传递 `videos`、`video_kwargs` 与 `video_metadata`。 |
| 当前 Ollama 0.34.0 | 官方公开的 Vision 与 OpenAI-compatible API 只定义图片输入；不能把 `video_url`/MP4 当作当前 Qwen3-VL 实例的原生视频输入。 |
| 最新 upstream llama.cpp | 多模态运行时可借助 FFmpeg/FFprobe 解码视频；CLI 提供 `--video`，Server 的 OpenAI-compatible 接口提供 `input_video`。视频 FPS 是 Server 启动参数而非逐请求参数，且官方仍把多模态 Server 标成 experimental。这是 llama.cpp 的用户态运行时能力，不代表 Ollama 自动暴露了相同入口。 |

macOS/Unix 内核不是这里的限制：Metal 可用于 GGUF 推理，FFmpeg 负责容器解码；差异在用户态 runtime 是否集成并公开视频预处理/API。当前仓库默认仍使用 Ollama 的 **有序抽帧 + 显式相对时间标签** 路径，并已增加可配置的 `llama_cpp/video` Gateway adapter。直接视频仅作为候选，须先在本机用相同 VideoChunk、Prompt 和 Schema 做 A/B；本文不据此虚构速度、内存或质量优势。

### 当前接入选择

当前机器已经下载的是 Q4_K_M 主模型与 Q8_0 projector，而不是 Transformers
Safetensors。因此先接独立 upstream llama.cpp Server 更节省磁盘和运行内存：Gateway
把 MP4 作为 raw Base64 `input_video.data` 提交，Engine 继续复用 `VideoInput`、候选
Transcript、时间线 Schema 与单次内容审核降级。Server 必须显式使用
`--video-fps 0.5`；Gateway 只会拒绝与调用侧 FPS 声明不一致的请求，真实启动参数仍由
部署命令保证。当前 Ollama.app 私有
`llama-server` 以 `MTMD_VIDEO=OFF` 编译，不能承担这条路径，机器上也尚未安装独立
upstream `llama-server`，所以代码接线完成不等于实机视频能力已经验证。

Transformers + `qwen-vl-utils` 仍保留为高精度对照路径。它最贴近 Qwen 官方
Processor：Qwen3-VL 使用 `image_patch_size=16`、`return_video_metadata=True`，并把
`video_metadata` 传入 Processor；但需要另下约 17.5GB BF16 权重和安装 PyTorch、
Transformers、TorchVision、qwen-vl-utils 等依赖，不能复用当前 Ollama GGUF。

llama.cpp direct-video 仍是在 Server 内部解码和采样，不包含音轨。它的价值是把帧组
与时间信息按视频输入交给视觉运行时，而不是让模型跳过抽帧。近期 upstream 曾出现
Windows 长视频管道挂起问题，因此 66 秒窗口必须先做单段超时测试；Gateway 使用 raw
Base64 也兼容了曾经不接受 `data:video/...` 的构建。

来源：[Qwen `qwen-vl-utils`](https://github.com/QwenLM/Qwen3-VL/blob/main/qwen-vl-utils/README.md) · [llama.cpp Server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) · [llama.cpp 多模态](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md) · [llama.cpp 长视频问题](https://github.com/ggml-org/llama.cpp/issues/27587)

来源：[Qwen `qwen-vl-utils`](https://github.com/QwenLM/Qwen3-VL/blob/main/qwen-vl-utils/README.md) · [Ollama Vision](https://docs.ollama.com/capabilities/vision) · [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility) · [llama.cpp 多模态文档](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md) · [llama.cpp Server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

### 可行路径

- MiniCPM-V 2.6 GGUF Q4_K_M + llama.cpp/Metal；
- Qwen3-VL-8B Q4_K_M GGUF + llama.cpp/Metal；
- 条件测试 Qwen3-VL-30B-A3B Q4_K_M GGUF，严格控制 context 和图片像素预算。

### 不直接可行的路径

- VideoRAG 原样 BNB INT4 loader：参考工程锁定的 `bitsandbytes==0.43.1` 路径面向 CUDA，且 ImageBind 实现直接调用 `.cuda()`；不把新版 bitsandbytes 的其他后端支持外推到这份旧实现。
- vLLM/SGLang CUDA 部署：适合 NVIDIA 服务器，不是当前 Mac 的主路径。
- Qwen3-VL-30B BF16：仅权重就超过可用统一内存。

### 结构化输出

- llama.cpp 的 OpenAI-compatible endpoint 支持 `response_format: {type: "json_schema", ...}` 所对应的 grammar constrained decoding，但只支持 JSON Schema 子集。
- vLLM 也支持 OpenAI-compatible Structured Outputs。
- Schema 只限制输出形状，不会自动教会模型字段语义。Prompt 仍须说明时间、证据和事件规则。
- AniVAG 继续使用 Pydantic 做二次校验；`start < end`、范围、单调性、点事件 `+1ms` 和 ownership 不交给 constrained decoding。

来源：[llama.cpp JSON Schema/GBNF](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md#json-schemas--gbnf) · [vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/)

MiniCPM 复用了 Qwen 中性证据实验的三组原始 JPEG：

- `[0,30000)`：每 2 秒一帧，共 15 帧；
- `[30000,60000)`：每 2 秒一帧，共 15 帧；
- `[60000,66000)`：每 0.4 秒一帧，共 15 帧。

输入仍只有有序 Frame 图片与匿名中性证据指令，不提供 SeriesBible、历史 Context、候选
ASR、人物真名、毫秒计算或最终 Timeline Schema。两边使用相同字段：
`evidence_frames`、`subjects`、`visual_fact`、`hard_subtitle`、`visible_speaker`。

人工核验进一步发现：

- 三组都输入 15 帧，但 MiniCPM 每组都输出 16 条 observation，并重复 Frame 15；
- group 0 从舞台全景切到人物近景、麦克风和水瓶，但 16 条里所有 `visual_fact` 都是同一句
  舞台表演描述；
- group 0 把“其实我们是第一次开 Live”复制到后续大量无关帧；group 1 也只用三种字幕
  模板覆盖全部 16 条；
- group 0/1 丢失双语字幕的日文部分，没有遵守“保留原语言”；
- group 1 对全部 observation 都自信填写说话者，并把不同画面压成两种人物模板；
- group 2 对快速交替演奏镜头的粗分类尚可，但最终歌词把“肩落”识别成“肢落”。

所以准确结论是：**MiniCPM 在当前 Ollama/Metal 形态下资源轻、速度快、结构稳定，但对
AniVAG 的多帧动画证据抽取质量显著弱于 Qwen，不能因为 VideoRAG 使用它就替换现有
fallback。** VideoRAG 的 MiniCPM 负责的是检索候选窗口 caption，后面还有 transcript、
ImageBind 检索和文本 LLM；它的成功不能等价为稠密逐帧事实抽取能力。
